# RouteMaker: build specification

## What this is

RouteMaker is a web application for planning bicycle routes collaboratively, targeted at the Washington, DC metro area. It exists to solve two problems that existing tools such as Ride with GPS and Komoot handle poorly: planning a route with other people, and planning for different cycling modalities, where a route that is good for a solo rider is wrong for a dozen people and unusable for a thousand.

Users sign in with Discord, build or import routes, choose a modality that shapes how the router weighs roads, trails, hills, and turns, and put routes up for peer review. Reviewers comment on specific places, report issues and closures, record approvals, and propose alternatives that the owner can merge. Routes export as GPX, FIT, TCX, cue sheets, and marshal documents, and push directly to cycling services where an API exists.

Reader's note on precedence: decisions recorded as "owner decision" in this document were made by the project owner and are not open to reinterpretation by an implementing engineer.

## Region and data

- **Coverage.** The DC metro, clipped to a polygon covering roughly Frederick and Leesburg to the northwest, Annapolis to the east, and Fredericksburg to the south. Geofabrik extracts for DC, Maryland, and Virginia, merged then clipped with `osmium extract -s smart -S types=any` so boundary relations stay complete. Admin data is built with `valhalla_build_admins` from the merged extract before clipping, and `valhalla_build_timezones` is run so `date_time` requests work.
- **Elevation.** USGS 3DEP. Valhalla's elevation reader accepts only 1 arc-second, 3601 by 3601, big-endian int16 HGT tiles named like `N38W077.hgt`. Resample 3DEP with `gdalwarp` to that grid and write with GDAL's SRTMHGT driver; trim the 6-pixel overlap on 1 arc-second source tiles. The AWS terrain-tiles skadi set, which is 3DEP-derived for the US, is an acceptable shortcut. Elevation tiles are built once and cached on the tiles volume; the weekly rebuild reuses them. Elevation is re-pulled from 3DEP annually or when USGS publishes new coverage for the region; that rebuild is manual.
- **Base map.** A PMTiles file extracted with `pmtiles extract` from the Protomaps daily build against the coverage polygon, served by Caddy with HTTP range requests and read by MapLibre through the pmtiles protocol adapter. Glyphs and sprites are self-hosted. Caddy serves PMTiles, glyphs, and sprites only to requests whose `Origin` or `Referer` matches the app host, with a per-IP range-request limit. Refreshed monthly by the worker. Protomaps basemap layers do not carry surface or cycleway detail, so stress and infrastructure are drawn as an overlay from the application's own segment table. Do not use the public OpenStreetMap tile servers.
- **Stress data.** Stress is derived from OSM tags using the Furth 2017 Level of Traffic Stress tables as implemented by OSM-based classifiers such as BikeOttawa's, reimplemented rather than copied unless that code's license is recorded and compatible. Inputs: `highway`, `lanes`, `maxspeed`, `cycleway*`, `shoulder*`, `width`, `parking:*`, `oneway`, `surface`, with documented default assumptions where any is missing, erring toward the higher-stress reading rather than the lower. DDOT bike lane data from Open Data DC (CC0) is conflated onto OSM ways by buffer overlap with documented precedence. OpenStreetMap is the baseline everywhere. For the Maryland portion of the coverage area it is improved by the Maryland Department of Transportation's statewide Bicycle Level of Traffic Stress layer, published on the state's iMAP catalog under terms that permit free redistribution provided the metadata entry is preserved and derived data credits the State of Maryland, which is compatible with publishing an ODbL derivative. Confirm the license field on the item page before ingest, since the terms above were read from secondary sources.
  That layer earns its place by carrying what OpenStreetMap structurally lacks: traffic volume, alongside speed and facility type. It scores every roadway in the state and adds two values beyond the usual four, zero for shared-use paths suitable for all ages and abilities and five for roadways where bicycle access is prohibited, and the five feeds access tagging directly, which matters for parkways and limited-access bridges. Its companion road-separated bike routes file covers shared-use paths, rail trails, and side paths, which is the sidepath evidence the roadway-versus-sidepath bridge distinction needs. Both are conflated onto OpenStreetMap ways by buffer overlap with documented precedence, and any way the conflation fails to match falls back to the OSM-derived score.
  The District closes the third side. Open Data DC publishes annual traffic volume, dedicated to the public domain under CC0 with attribution requested rather than required, which is the least encumbered of the three and needs no license gate at all. With it, every jurisdiction in the coverage area has the volume input the classifier cannot infer, and stress is computed the same way everywhere from the same tables, rather than being imported from one agency and guessed at elsewhere. The Virginia gap is closed the same way, by the input rather than by a finished score. The Virginia Department of Transportation publishes bidirectional traffic volume through its Virginia Roads open data portal, updated annually, and volume is the one input the classifier cannot infer from OpenStreetMap. Conflated onto OpenStreetMap ways by buffer overlap plus route number and name matching, with documented precedence and a fallback to the OSM-derived score wherever the match fails, it lifts Virginia close to Maryland without a Virginia stress score needing to exist. Where a VDOT dashboard is the entry point, the layer behind it is what to ingest, never the dashboard.
  Coverage is better than Virginia's road-maintenance arrangement would suggest, and the distinction is worth stating because it is easy to get backwards. Under the Byrd Road Act, Arlington and Henrico kept their own secondary road systems and the independent cities maintain their own streets, so VDOT does not maintain much of the dense near-DC grid. Its traffic monitoring program is separate from maintenance and statewide: VDOT publishes volume estimates in about a hundred area books covering the roads within each county along with the cities and towns inside it, and the Virginia Open Data Portal carries the result as a per-locality annual series, Arlington and Fairfax alongside Loudoun, Prince William, and the rest. So the working assumption is that the localities are covered, and the thing to verify at ingest is count density on local streets rather than whether a jurisdiction appears at all. Where a locality also runs its own portal, prefer whichever proves denser on residential streets. Virginia Roads carries no license statement on the state open data catalog and links to separate terms, so its license, and each locality's, must be read and recorded before ingest under the gate below.
- **Speed outranks volume.** The recent attention to volume should not be read as making it the primary variable. In the Furth tables, stress on a road without bike facilities is driven first by speed and lane count, with volume acting as a modifier on two-lane roads, and that ordering is correct for cycling because what makes a road hostile is the speed differential between a bicycle and the traffic passing it. A quiet two-lane road posted at 50 with no shoulder is high stress at almost any volume, while a congested downtown grid posted at 25 is not.
  This is a concrete failure mode rather than a nicety. A naive reading of low volume as quiet would route Trailmaxxing and Group Ride onto exactly the fast rural two-lane roads in western Loudoun, upper Montgomery, and Frederick that a dozen riders should never be on, and it would do so confidently, because those roads really do carry little traffic. The classifier therefore treats a missing speed as the conservative value for the road class rather than an optimistic one, and the reference-route invariants include an upper bound on distance at high posted speed without a shoulder or bike facility for both presets.
  Two qualifications belong in the same place. OpenStreetMap carries the posted limit, while operating speed on a wide rural road with good sightlines often runs above it, so a road's geometry is evidence about speed that the posted value understates. And shoulder presence is what changes the answer at speed: a 45 mile per hour road with a wide paved shoulder is a different proposition from the same road without one, so shoulder and effective width are inputs alongside the posted limit wherever they are tagged, and are a priority for the override table wherever they are not.
- **What volume coverage actually looks like.** Do not infer gaps from who owns or maintains a road, which is the mistake this paragraph exists to prevent. Traffic monitoring follows federal reporting obligations, which run to all public roads, so a state or district count program covers roads it does not maintain: VDOT's area books include the cities and towns inside each county, and the District's volume layer covers the federally owned roadways, Rock Creek Parkway, Beach Drive, the Mall roadways, and the memorial bridge approaches among them. Those are the roads a mass ride most wants, and they are counted. The real variable is density rather than jurisdiction. Count programs concentrate on arterials, so minor residential streets often carry sparse or modeled values, and that is not an error to chase: low volume is the right default for a residential street and the classification tables care most about getting arterials right. Anything genuinely uncounted falls back to the OpenStreetMap-derived score and is a candidate for the override table.
- **Crash history.** VDOT also publishes crash data, including a corridor-level view of the roads with the most crashes. It is worth ingesting, subject to the same gate, but it is advisory and never a routing input, and that distinction is deliberate rather than an omission to be tidied up later. Crash counts are an outcome measure without an exposure denominator: a road nobody rides records no bicycle crashes, so the roads that look safest in the data include both the genuinely safe and the too-hostile-to-ride. Penalizing crash locations in routing would therefore push riders off busy good routes and onto empty bad ones, which is the opposite of what the data appears to say. Bicycle crashes are also badly underreported and rare enough per segment to be statistically noisy, and corridor aggregation, while it blunts both problems and avoids mapping individual collisions, is coarser than the segment the router works on.
  What it is good for is human judgment. Crash history for a segment is a map overlay a reviewer can switch on, it is surfaced automatically when someone opens a safety issue on that segment so the reviewer deciding whether to confirm can see it, and a segment whose crash history disagrees with its stress score is flagged for review, which is the cheapest way to find where the classifier or the tagging is wrong. Bicycle-involved crashes are the subset that matters; all-mode counts are a much weaker signal for this purpose. Montgomery Planning's own stress layer is not ingested, because its terms forbid incorporation into other maps without written permission; it may still be used privately to check the classifier, with none of its values reaching the database or the published derivative.
- **Jurisdiction polygons.** Police jurisdiction, right-of-way owner, and park or trail manager are separate layers. Sources: DC boundary and the Architect of the Capitol jurisdiction polygon (`AOCPly`, the area the Capitol Police polices) from Open Data DC (OCTO, CC0); all NPS unit boundaries inside the coverage polygon from the NPS open data portal, in all three states, including President's Park for the White House complex; Census TIGER county layer (Virginia independent cities are county equivalents), TIGER place layer for municipalities with their own police such as Rockville, Gaithersburg, Takoma Park, Hyattsville, College Park, Laurel, Greenbelt, Bowie, Frederick, Annapolis, Vienna, Herndon, and Leesburg; TIGER military installations for Joint Base Anacostia-Bolling, Fort Myer, Fort Belvoir, and the Pentagon reservation; Arlington National Cemetery and the airport from the NPS and TIGER layers where present; park and trail boundaries from OpenStreetMap, using park polygons and their operator tags rather than the park agencies' own parcel files, which carry the same redistribution terms as the stress layer; state road ownership from OpenStreetMap route and ref tags, with the Maryland SHA and VDOT inventories used only to check that derivation. Federal land outside DC is first class: the GW Parkway and Mount Vernon Trail, Clara Barton Parkway, C&O Canal, BW Parkway, Suitland Parkway, and Greenbelt Park are all NPS.
- **Way-level override table.** A community-editable, admin-approved table of per-way corrections applied during preprocessing: jurisdiction overrides for DDOT arterials that cross NPS units such as Constitution and Independence Avenues through the Mall and Military Road and Massachusetts Avenue through Rock Creek Park, bridge legality corrections, and access corrections. Seeded from the verification fixtures in the Quality bar.
- **Refresh.** A weekly job pulls fresh extracts, runs preprocessing, rebuilds every Valhalla tile variant, validates them, and swaps tiles and the segment table together. See Operations for the swap procedure. The geocoder and basemap are refreshed monthly on their own path.
- **License gate.** Ingested data is OpenStreetMap, Maryland iMAP, Open Data DC (CC0, covering both the bike lane and traffic volume layers), NPS, USGS, and Census TIGER, all of which permit redistribution and ODbL-compatible derivative use. Nothing else is ingested without recording its license first and finding that it permits display, redistribution in exports, and derivative use; a source that fails is replaced by OSM-derived or TIGER data, which is why the park agency and state road inventories are checks rather than inputs. The same applies to any reused classifier code.
- **Licensing.** Every external source is documented with license, URL, and refresh procedure. The OSM extract with injected derived tags is an ODbL derivative database. To satisfy ODbL share-alike, the derived-tag database and the diff the pipeline produces are published under ODbL; the pipeline source code is published under an OSI license such as MIT or Apache-2.0. Contributions that feed preprocessing (issues, closures, override rows) are licensed by their authors under ODbL for data and CC BY-SA for text, stated in the sign-in terms and on the issue and override forms; info card text is CC BY-SA. Attribution "© OpenStreetMap contributors" appears on every map, thumbnail, cue sheet, export download page, and in GPX metadata, alongside "© Protomaps" on maps. USGS 3DEP, Census TIGER, Open Data DC, and NPS are credited on a data page, and the State of Maryland is credited there and in the metadata of anything derived from its layer, as its terms require.

## Architecture and stack

- **Frontend.** React with TypeScript and MapLibre GL. Viewing, commenting, and issue reporting work on phones; the editor is desktop-first and best effort on mobile. No native app and no offline mode.
- **Backend.** Python with Django and Django Ninja. Ninja keeps Pydantic request and response models and an OpenAPI schema, from which the frontend's TypeScript types are generated, while Django supplies the ORM, sessions, CSRF, migrations, and the admin. Django migrations run in a one-shot `migrate` compose service that the API and worker depend on with `condition: service_completed_successfully`.
- **Why Django here.** The choice follows the shape this plan grew into. It carries roughly a dozen permissioned admin surfaces (role mapping, configured guild list, guild remap and re-invite links, five server settings, override row approval, versioned info cards, the audit log, moderation, failed jobs, degraded guilds), which is what Django's admin exists to remove. GeoDjango gives PostGIS field types, spatial queries, and a map widget configured against the self-hosted basemap rather than its default, which would otherwise call the public OpenStreetMap tile servers this plan rules out, so jurisdiction overrides, closures, and way-level corrections are edited by drawing on a map in the admin rather than in a second bespoke editor. Django's migrations handle spatial and custom types more reliably than autogeneration against them. The async argument that once favored a lighter framework has shrunk, since candidate search, exports, pushes, and rebuilds are all worker jobs now and a waypoint drag is a single Valhalla call. Revisit if live collaborative editing comes into scope or candidate search returns to the request path.
- **What Django does not give.** Its permission system is model-level, and this plan's authorization is object-level throughout: per route, per guild audience, per collaborator flag, with guild admin distinct from instance admin. The authorization layer is written by hand either way, and every admin model overrides its queryset and per-object permission checks to respect it. What is saved is forms, list views, filters, and history, never the access rules. An admin view that does not narrow by the viewer's guild is a leak, so the visibility tests cover the admin too.
- **The admin introduces no second credential.** Django's admin ships its own username and password login, which is a credential class this threat model does not have: every other path is Discord-only, with standing from the bot, a deployment-wide ban list, and sessions as the revocation mechanism, and a stored password would bypass all of it and sit in the nightly dump. So the admin login form is disabled and the admin is reached only through the Discord session, no account ever has a usable password, staff status is derived per request from application standing rather than stored as a grant, and no account is a superuser, since superuser short-circuits the per-model permission checks this design depends on. A banned or lapsed admin loses the admin along with everything else, because one answer serves both. The admin is served under a non-obvious path, behind the same session and CSRF rules as the API, and never answers an unauthenticated request.
- **Authorization state is read-only in the admin.** The admin's change forms would otherwise sidestep every audited workflow in this plan: editing the cached membership table grants any role in any guild, editing a route's owning guild does by hand what the remap does with preconditions, confirmation, notification, and an audit row, and editing audience rows, the role mapping, override approval flags, or issue state skips the same guards. The cached membership table, the audit log, the configured guild list, the role mapping, audience rows, and route owning-guild and visibility fields are therefore displayed but not editable, and change only through the actions that own them. The admin's editable surface is the content it exists for: jurisdiction polygons, override rows, closures, info cards, and settings, each behind its own per-object check. Admin writes go to the same audit log as API writes, with the admin as actor.
- **Database.** PostGIS through GeoDjango. Stores users, sessions, routes, route versions, a route audience join table of route and guild, cached guild membership and roles per user, control points, collaborators, segments with attributes, a crossings table for border control nodes, comments, issues, proposals, approvals, notifications, jurisdiction polygons, jurisdiction info cards, the override table, connected accounts, push logs, settings, and an audit log. All user-authored rows use `deleted_at` soft deletes purged after 30 days, including files on the uploads volume owned by purged rows. Each route version stores a frozen copy of the modality weights and jurisdiction settings used, not only a modality id.
- **Worker.** Procrastinate, which is Postgres-backed and has a Django integration, so no broker service is needed; confirm that integration's current state before building. Jobs are idempotent by explicit key such as `push:{route_version_id}:{service}`, retried with exponential backoff up to 5 times, with per-type timeouts (export 2 minutes, push 5 minutes, rebuild 6 hours). The rebuild and the backup are periodic tasks; the rebuild is single-flight. Failed jobs appear on an admin page and alert after the final retry. Nothing slow runs in the request path.
- **Routing engine.** Valhalla, self-hosted, bicycle costing, one process per tile variant.
- **Geocoder.** Photon, self-hosted, for place search in the editor. Photon indexes from a Nominatim database, not from a PBF, so it is populated either from GraphHopper's per-country Photon dump filtered to the coverage bounding box or from a one-off Nominatim import of the clipped extract, documented as the heavier option. It runs with a 3 GB memory limit and a per-user rate limit of 10 requests per second, and is not on the weekly rebuild path.
- **Discord bot.** A small service holding the gateway connection, maintaining the cached membership and role table, answering membership queries for the API, and posting announcements. It is the only component that holds the bot token. A dropped gateway connection is a health check failure, because stale roles are a security problem rather than a cosmetic one.
- **Thumbnail renderer.** A small Node sidecar using `@maplibre/maplibre-gl-native` against the local PMTiles and style, called by the worker over the compose network.
- **Deployment.** Views are synchronous, since the request path is a single routing call plus database queries, and the API runs under gunicorn with a worker count set from the host's cores. The React frontend is built to static assets rather than run as a service, and Django's admin and Ninja assets are collected into the same named volume, which Caddy serves; both are rebuilt on deploy and after a restore. One Docker Compose stack on one AWS host: Caddy for TLS and for serving the built frontend along with the admin and Ninja assets, the API, the worker, the migrate service, PostGIS, Photon, the Discord bot, the thumbnail renderer, and one Valhalla container per active tile variant. `compose.yaml` plus `compose.override.yaml` for local development, secrets via `.env` with a committed `.env.example`, all images pinned, all services `restart: unless-stopped`. The same stack must run locally.
- **Preprocessing pipeline.** Python using osmium, Shapely, and rasterio. It is the core of the product and is built and tested first. It computes per-way derived values and writes them in three places:
  1. Into the PostGIS segment table, keyed by `(osm_way_id, ordinal within way)` plus stored geometry: stress tier, stress time windows, jurisdiction layers, bridge legality split into roadway and sidepath, lane count and width estimate, sinuosity and sharp bends per mile, lit, reviewer penalty, and elevation samples. The pipeline writes to a staging schema; see Operations for the swap.
  2. Into the OSM extract as tags that a project-owned copy of `graph.lua` (configured via `mjolnir.graph_lua_name`) remaps onto Valhalla's existing edge attributes. Valhalla's tile schema is fixed and unknown tags are dropped, so every derived value that must influence routing is expressed through an attribute the bicycle costing already reads. The mapping table is part of the repository and unit tested: stress tier drives `cycleway`, `highway` class, and `maxspeed` overrides; reviewer penalty downgrades `surface` or raises `maxspeed`; bridge legality sets `bicycle=yes/no` per roadway or sidepath way; `lit` is preserved. Jurisdiction is not stored in tiles. The remap is global and shared by every modality; there are no per-preset remaps.
  3. It splits every way where it crosses a state line and inserts a node tagged `barrier=border_control`, which Valhalla treats as a border control node. This makes the existing `country_crossing_cost` and `country_crossing_penalty` request options act as a per-request state crossing penalty with no engine fork. The Lua mapping is verified not to deny bicycle access at those nodes. Each inserted node's OSM id, coordinates, and the two states it separates are recorded in the crossings table, because Valhalla keeps no custom node tags; the application resolves crossing direction from that table.
- **Segment identity across rebuilds.** Comments, issues, closures, cue overrides, and reviewer penalties store a geometry anchor (snapped point or linestring) plus the segment key at the time of creation. After each swap a reconciliation job re-resolves anchors by way id and nearest geometry, flags unresolved anchors for review, and never silently drops them. Route versions store control points, waypoints, modality snapshot, and resulting geometry, never graph edge ids.
- **Stats source.** Per-edge attributes for a route come from `/trace_attributes` with `shape_match: edge_walk` on the route shape. Valhalla edges split at graph intersections, which do not coincide with pipeline segments, so the join uses `edge.way_id` plus linear overlap of the edge shape against stored segment geometry, apportioning length where an edge spans several segments. Turn and left-turn counts come from the maneuver list. Elevation gain and loss come from `elevation_interval` on `/route` with a hysteresis threshold so DEM noise does not inflate gain.

## Routing model

Valhalla's bicycle costing exposes a fixed set of dials. Every modality behavior is assigned to exactly one of four layers, and the code makes the assignment explicit:

1. **Tile build.** Derived tags remapped through `graph.lua`, border control nodes at state lines, and variant tile sets for behavior costing cannot express. Trail-class ways are defined once as `highway` in cycleway, footway, path, pedestrian, bridleway, or steps regardless of bicycle tag, plus sidepath-only bridge ways, because DC-area trails are tagged inconsistently. Variants: standard; mass ride, with trail-class ways removed; e-bike, with `electric_bicycle=no` ways set to `bicycle=no`. Each variant is its own Valhalla process. Variant behaviors are toggles, not sliders. The mass ride and e-bike variants are mutually exclusive until the phase 6 path-avoidance dial; the UI disables "E-bike rules" while bike paths are disallowed and explains why. If the exclusivity proves limiting, a combined mass ride e-bike variant is an additional tile build and Valhalla process, not a fork, and is preferred over advancing phase 6. A closed-course variant that relaxes `bicycle=no` on parkways and limited-access roadways for permitted events is a recorded follow-up after phase 6, not in scope for first release.
2. **Per-request costing options.** `bicycle_type`, `use_roads`, `use_hills`, `avoid_bad_surfaces`, `use_living_streets`, `maneuver_penalty`, `gate_cost`, `gate_penalty`, `country_crossing_cost`, `country_crossing_penalty`. Request-level parameters: `exclude_polygons` for small closure polygons only, `date_time`, `elevation_interval`. Requests use `date_time.type: 3` (invariant) with the planning time, which keeps bidirectional A* and alternates while still evaluating conditional restrictions; types 1 and 2 are used only for an explicit arrive-by request.
3. **A small costing fork**, deferred to phase 6 and kept as a patch set against upstream with a documented rebase procedure: apply the existing `use_lit` and `unlit_factor_` in bicycle costing, and add a path-avoidance dial so the mass ride variant becomes unnecessary. Before implementing, check whether the current release already provides either.
4. **App-level search and scoring.** Dragging a waypoint triggers a single-pass preview using the modality's layer 1 and 2 dials. Layer 4 search runs on release or on an explicit "Find alternatives" action, as a worker job with progress for Mass Ride and Mountain Goat, and presents the ranked candidates with their stats blocks so the owner chooses; the chosen candidate is what gets saved. Multi-pass routing and ranking of candidates on turn count, left turns across traffic, uncontrolled crossings of high-stress ways, road width, sinuosity, unpaved share, lit share, stress breakdown, crowded-trail time windows, and jurisdiction crossings. Candidate generation does not rely on Valhalla `alternates` for multi-waypoint routes, since alternates exist only in bidirectional A* and are disabled for more than two locations; candidates come from per-leg two-location alternates requests or from multi-pass requests with perturbed dials, and the perturbed-dial set always includes at least one pass at high `use_roads` so a road-based alternative is present for sinuosity ranking to choose. The left-turn-across-traffic classifier uses `oneway` on the source and target ways, so a left from a one-way onto a one-way is not counted while a left from a two-way is. Traffic circles are keyed on a curated list, not tags alone, since DC circles are tagged inconsistently.

A modality is a named weight vector over these layers, stored as data. Every dial exists on every preset, so "Mass Ride, Night" or "Group Ride, DC only" are savable customs, subject to the variant exclusivity above.

**User-facing controls.** Sliders in plain language: "Quiet roads to direct roads", "Avoid hills", "Fewer turns and stops", "Paved only to gravel OK", "Ride two abreast", "Stay in home state". Toggles: "Allow bike paths and trails", "Prefer lit streets", "E-bike rules". Mass Ride ships with "Allow bike paths and trails" off; Group Ride ships with it on. A collapsed Advanced panel shows the raw dial mapping. Mountain Goat and Bikepacking show hills, surface, distance budget, and "Stay in home state" by default; the remaining dials are in the Advanced panel.

**State crossing penalty.** Owner decision, superseding an earlier draft that defaulted this high for Mass Ride: crossing a state line is a routine part of riding here and people do it without noticing, so the router does not avoid it for any modality. The default is off everywhere, where off means the request explicitly sends `country_crossing_cost` and `country_crossing_penalty` as zero, since Valhalla's default cost is 600 seconds and would otherwise apply at every border control node. The dial exists for the organizer who has a specific reason to stay in one jurisdiction and turns it up deliberately; it is not a default posture. The three reference trail routes each cross the District line and would be unroutable under the old default. Both are capped at 43200 by Valhalla. Adjustable by the "Stay in home state" slider on every preset from day one. The penalty is symmetric and charges on leaving and on returning.

**Home jurisdiction.** The state of the start control point, or of the first waypoint if no start control point exists, DC, Maryland, or Virginia, overridable per route. Direction of a crossing is resolved from the crossings table.

**Road exposure.** Trailmaxxing is not a trails-only mode, because the trail network is discontinuous and the connectors between trails are roads. The reference trail routes all contain such sections and their author describes them as unavoidable. So rather than pretend otherwise, a Trailmaxxing route reports its road exposure: total distance not on trail-class ways, broken down by stress tier, with each such section listed by location and length so a rider knows in advance where the trail ends. The same report serves Beginner, replacing the bare gap warning with something specific enough to act on. A route with unavoidable exposure is a normal result, not a failure.

**Stats block.** Every route returns: distance, elevation gain and loss, grade profile with maximum grade and flagged steep descents, surface breakdown, turn count, left turns across traffic, intersection summary by control type, stress breakdown by distance, unpaved share, lit share, sinuosity, jurisdiction breakdown by distance for each layer, crossing data, gap warnings, road exposure by stress tier, and freehand distance. The stats block always carries crossing data; the route summary surfaces it as its own section only when jurisdiction warnings are on and otherwise folds it into the breakdown.

**Time-dependent behavior.** `date_time` affects only conditional access restrictions and time zones in Valhalla, so bicycle routing does not change by time of day for roads that are always bike-legal. When no planning time is set, requests assume the next Saturday at 9:00 local time, shown in the editor as an assumption the owner can change, so that conditional restrictions are evaluated rather than ignored. Time-dependent stress, such as the lower Beach Drive and Sligo Creek Parkway weekend car closures, is stored on the segment table as a default value plus windowed values and applied in stats and layer 4 scoring using the route's planning time. Valhalla does not read `oneway:conditional`, so the Rock Creek and Potomac Parkway weekday rush-hour reversal is expressed by preprocessing as directional conditional access restrictions (`bicycle:forward:conditional` and `bicycle:backward:conditional`), verified against the parser's supported keys in a unit test. Reviewer-confirmed closures with date ranges are injected as `access:conditional` at the next rebuild using month-day time domains, since Valhalla time domains carry no year; the rebuild removes them once the end date has passed. While a closure is active before its first rebuild it is supplied as a small `exclude_polygons` entry.

## Jurisdiction model

Jurisdiction is a set of per-segment attributes, not a single value:

- **Police jurisdiction.** DC under MPD; federal units by agency (US Park Police by NPS unit, Capitol Police, Secret Service Uniformed Division for President's Park, military police for installations, MWAA for the airport); Maryland municipality or county; Virginia town, city, or county. Owner decision: US Park Police is the agency that needs flagging, because federal land is where a mass ride's authority question actually changes. Maryland's park police, meaning the county park police forces, are not flagged and sit in the manager layer instead; this overrides a review finding that had placed them in the police layer.
- **Right-of-way owner.** DDOT, NPS, Maryland SHA, VDOT, county, municipality, or park authority.
- **Park or trail manager** where different, such as the Maryland county park agencies, the authority that runs the W&OD, and the Fairfax County Park Authority, all derived from OpenStreetMap operator tags.

The crossing list and the count of "distinct authorities with jurisdiction" use the police layer. The owner and manager layers appear in the breakdown.

**Crossing detection rules.** Crossings shorter than a configurable minimum, default 0.1 mile, are collapsed unless a control point lies inside them, which handles the Jones Point sliver on the Wilson Bridge path and the circles that straddle the DC line. Ways with `bridge=yes` or `tunnel=yes` and nonzero `layer` over a park polygon inherit the adjacent jurisdiction, defined as the jurisdiction of the connected non-bridge ways at each end; if the two ends differ, the bridge is split at its midpoint. Segments on Western, Eastern, and Southern Avenues are treated as DC with a boundary flag listing both authorities; this rule is not surfaced in UI copy as a legal statement. The override table handles DDOT arterials through NPS units.

**Per-route settings.** Two separately editable settings, each stored with an "explicitly set" flag. Changing modality recomputes defaults only for settings the user has not explicitly set, and the UI shows which values are defaults and which are choices. Modality controls routing only.

- **Ride purpose.** Recreational, First Amendment assembly, or special event, each with a one-line plain-language explanation shown when the control is surfaced: a ride for its own sake; a protest, demonstration, or expressive event; a permitted race, charity ride, or festival. It selects which info card copy is shown and appears in the route summary next to the jurisdiction breakdown. The default purpose for Mass Ride is a per-server setting chosen by the server admin. Owner decision: the shipped default is First Amendment assembly. Every other modality defaults to recreational.
- **Jurisdiction reporting.** On or off. Default on when the modality is Mass Ride or the purpose is First Amendment assembly or special event; off only for another modality with recreational purpose. The trigger is about who needs to think about permits, not about whether crossing a line is risky.

| Modality | Purpose | Reporting default |
|---|---|---|
| Mass Ride | Any | On |
| Any other | First Amendment assembly or special event | On |
| Any other | Recreational | Off |

The reason any of this exists is permitting rather than geography. Laws governing a ride, and the body that permits it, differ by jurisdiction, and those differences bite for First Amendment activity and for permitted special events. For a recreational ride they are largely academic, which is why nothing is surfaced there by default even though the same nuances technically exist and the info cards remain available to anyone who opens them.

**When jurisdiction reporting is on:**

- A state line crossing is reported, not warned about. The crossing itself is unremarkable; what changes at the line is which laws apply and which body issues a permit, and that is the whole of the concern. The report names the jurisdiction entered and links its info card, and it appears when a waypoint or control point is placed outside the home jurisdiction as well as in the summary afterward, so an organizer learns which authorities are now involved while there is still time to act. The crossing report supersedes the per-authority notice for the same crossing.
- Entering a federal enclave or other non-home police jurisdiction produces a notice at a per-authority level set by the server admin in that authority's info card: note or warning. Owner decision: the shipped default for every federal enclave inside DC is note, drawn as a map overlay and counted in the breakdown, because in practice passing through is rarely an issue. Admins may raise Capitol grounds or President's Park to warning for their server.
- A control point placed inside a federal enclave gets a note regardless of the pass-through level, because stopping is where problems arise.
- The route summary lists crossings in order with mile markers, miles per jurisdiction, and the count of distinct authorities. A state line crossing where the police authority is unchanged, such as Memorial Bridge onto the GW Parkway, carries the note "authority unchanged: US Park Police". Crossings can optionally appear in cue sheets as "Entering Montgomery County, MD" lines.

**When it is off:** nothing is surfaced. The boundary overlay and the info cards are still available to anyone who wants them, in every modality, because the nuances exist for recreational rides too and an organizer may want to read up regardless.

**Info cards.** Each authority has a community-maintained card: contact, typical lead time, links, notes, and the per-server notice level. Reviewer and above can edit; edits are versioned with author and timestamp and revertable by admins; each card shows "last edited" and the line "community-maintained notes, not legal advice, verify with the agency". The application states facts about jurisdictions and never makes legal claims in code.

## Route model

- **Structure.** A route has a name, description, tags, a modality snapshot, waypoints that shape the path, and control points with a type: start, finish, rest, regroup, marshal post, SAG or medical, sweep, bail-out. Control points are distinct from waypoints. A route has an owning guild, chosen by the owner at creation from the configured guilds the bot confirms they are in, defaulting to their only one, and an audience, a set of guilds that always includes the owning guild. Reviewers and server visibility, the routes index, and the Needs review queue resolve against the audience, so a ride co-organized by several clubs is reviewed by all of them. Per-server settings, the default purpose, and the per-authority notice levels come from the owning guild alone so they are never ambiguous. A single-guild deployment sees no difference. A route has an optional planning date and time, a planning speed, and an optional expected rider count, used only to set `date_time` on routing requests, compute ETAs on cues, drive time-window scoring, and feed the peloton length estimate and marshal ETAs. This is not an event.
- **Visibility.** Private (owner and named collaborators), reviewers (owner, collaborators, and users with the reviewer role), server (all signed-in members of any audience guild), link (anyone with the link, unlisted), or public (listed and readable by anyone). The default tier for new routes is a per-server setting, shipping as private, and a club whose rides are mostly public sets it to reviewers or server so nobody clicks up from private every time. The setting cannot default to link or public: world-readable is a choice a person makes per route, with the confirmation described below, never a state a route arrives in. The tiers are cumulative: each admits everyone the tier below it admits. Link adds anyone holding the token to the audience-guild readers that server admits, and public adds anyone at all; neither removes member access. Listing in the members' routes index and the Needs review queue follows audience-guild membership at every tier from reviewers upward, so a route shared outward is still found by its own reviewers; unlisted and listed describe only the public index and crawlers. Unpermitted rides commonly keep the route secret until ride day, so nothing about a route is broadcast without an explicit owner action. Link visibility exists because committees routinely need one outside person, an agency liaison or a club officer who is not on the Discord, to see a route; it renders a read-only interactive map, stats, and the rider cue sheet, with no comments, and downloads chosen by the owner from the rider cue sheet PDF (default on), the overview map PDF, and the intersection list PDF (default off, marshal assignment columns omitted), with the GPX track available at public only and also default off. Everything served to an unauthenticated link viewer comes from data stored per version: geometry, stats, compiled cues, and PDFs rendered by the worker when the version is saved; unauthenticated requests never trigger routing, geocoding, thumbnail rendering, or export jobs. Whether link visibility requires login is a server setting `link_requires_login`, editable on the admin settings page; when true the tier is labeled "members with link" and admits members of any audience guild and the unauthenticated surface reduces to the generic OpenGraph card. Owner decision: the shipped default is false. Both modes are covered by the visibility tests. Visibility governs who can open a route in every state; draft additionally excludes the route from the index, the queue, and Discord posting, so a draft at link visibility is reachable only through its link.
- **Public visibility.** Public is link visibility made discoverable and commentable. The route appears in a public index, is served to anyone without login, and is the only tier crawlers may index; every other tier stays `noindex`. Public routes get a stable slug URL alongside the token URL. The owner chooses downloads from the same list as link, extended with the GPX track, default off, since a published community ride wants riders to take the route with them but publishing is not by itself a decision to hand out the track. Public and link viewers see only start, finish, and rest control points. Marshal post, SAG or medical, sweep, and bail-out points, and the marshal cue sheet, are never rendered or downloadable below server visibility, because a page that plots where your people will be tells that to everyone, including agencies you have not spoken to. The intersection list is off by default at public and link, and its marshal assignment columns are omitted when an owner turns it on. Cue overrides anchored to a suppressed control point are omitted from the rider cue sheet below server visibility, since a cue reading "regroup at top" discloses exactly what hiding the regroup point was meant to protect. Reading stays unauthenticated and pre-rendered on the same terms as link: no routing, geocoding, rendering, or export jobs on an anonymous request. Writing requires a Discord login. A signed-in user who belongs to no audience guild has guest standing on a public route: they can comment and open issues, and nothing else. A server setting `public_tier_enabled`, default on, controls whether owners may choose public at all; turning it off reverts existing public routes to link and is audited, so an admin locking a deployment down has one lever that covers the open internet. Whether guests may write at all is a server setting `public_guest_comments`, default on, and an owner can turn it off for one route; with it off, public routes are read-only to non-members and the comment box explains why. Guest content is rate-limited more tightly than member content, is marked as from outside the organizing guilds wherever it appears, and cannot be confirmed into routing penalties by its author, since confirming remains a reviewer action. Choosing public asks the owner to confirm once, because an unpermitted ride's route is exactly what this tier publishes. Setting public on a draft is allowed and behaves as link until the route leaves draft, since draft already withholds a route from every listing. Lowering a route out of public takes effect on the next request, since every read checks current visibility: the slug stops resolving, the route leaves the public index, anonymous reads of its stored PDFs, GPX, and thumbnail are refused, and `noindex` is re-applied. Changing visibility in either direction is audited. The confirmation dialog states that publication cannot be undone for copies already made, and names what becomes public: the map, stats, cues, the ride purpose, and the jurisdiction crossing list.
- **Attribution.** Routes are attributed by default, because designing a good one is work and people should get credit for it. The route page, the index, exports, cue sheets, share cards, and announcements name the author and the contributors who shaped it.
  Ride purpose is the exception. When a route's purpose is First Amendment assembly, authorship is suppressed by default on everything that leaves the organizing guilds: the link and public tiers, OpenGraph metadata and thumbnails, every exported file, the social share card, and announcements. Inside the owning guild attribution stays visible, since the committee already knows who drew what and needs to. Club attribution is a separate toggle, also defaulting off for this purpose, because an organization may well want to claim a ride the individual does not. An owner can re-enable either, per route.
  Suppression is a presentation rule, never a deletion. The audit log always records the real actor, approvals stay attached to the reviewer who gave them, and the owning guild's admins see both; the protection runs outward, not against the deployment itself. In files it means the GPX author element is omitted and the creator is the application rather than a person, while the OpenStreetMap copyright element is always preserved, because attribution to the map is required regardless.
- **Named collaborators.** Added and removed by the owner or an admin, and notified when added. A collaborator can view the route in any state, comment, open issues, and submit proposals against it. A named collaborator may be any signed-in Discord account, identified by user id or username, whether or not they belong to a configured guild. This is the path for a partner club that will not invite the bot, and it needs nothing from that club's admins. An owner-granted per-collaborator `edit` flag, recorded in the audit log, allows saving new versions, because committees often have two people drafting one route. A second per-collaborator `review` flag, also audited, lets that person record approve or request changes on that route alone, since approvals are the artifact a co-organized committee actually wants and a partner reviewer should not need a bot invite to give one. Adding a partner guild to the audience is the right choice for an ongoing partnership; a single co-organized ride is not worth it. Merge, reject, state changes, and Discord posting remain owner only. A viewer-role member added as a collaborator gains those abilities on that route only.
- **Share links.** A per-route 128-bit random token, revocable and regenerable by the owner. Unauthenticated OpenGraph metadata (name, distance, elevation) and the static PNG thumbnail are served for link and public visibility, since Discord fetches OpenGraph data whenever a link is pasted and for a secret route the thumbnail is the secret. At private, reviewers, and server visibility, unauthenticated requests receive a generic card with the name only and no route data, and the thumbnail is served only to logged-in users the visibility admits. Thumbnails are rendered by the worker when a version is saved on a route at link or public visibility or in review or published, cached per version. Share pages send `Referrer-Policy: same-origin`, and `X-Robots-Tag: noindex` on every tier except public; Caddy and API access logs redact the token segment of share-link paths.
- **Versions.** Every save creates a version with a history view. Published and in-review routes are never re-routed automatically; the owner may still save new versions. Geometry and compiled cues are stored per version, and re-routing happens only on an explicit owner action. Active closures and weekly rebuilds produce alerts on affected routes, never silent re-routes. The rebuild emits a drift report listing routes whose segments changed attributes or lost their edges.
- **States.** Draft, in review, published, archived. A draft at reviewers visibility is openable by reviewers but accepts comments and proposals only from named collaborators. Requesting review pins a version and requires visibility of at least reviewers; if the route is private, the request dialog prompts the owner to raise visibility first. Archived is read-only and hidden from lists; it accepts no new comments or proposals, existing threads stay readable, and share links still resolve subject to visibility.
- **Proposals.** A proposal replaces the sub-range between two points shared with the base version and is merged by splicing, which matches how committees actually work: "take your detour around Thomas Circle, keep the rest". A whole-route proposal is the degenerate case. Proposals carry `base_version_id` and a state: open, merged, rejected, withdrawn, or superseded, where superseded means the proposer pushed a rebased proposal against a newer base, closing the earlier one and linking to the replacement. A proposer can push new versions to an open proposal until it closes. Merging creates a new head version whose provenance records the proposal and author. If the base has advanced past the proposal's base, the compare view shows base, current head, and proposal, and the owner either asks the proposer to rebase or splices manually. A rejected proposal is retained and readable and can be reopened as a new proposal via fork.
- **Approvals.** Reviewers, and named collaborators holding the `review` flag, record approve or request changes against the pinned version. The owner can re-pin the current version from the review panel; existing approvals remain attached to the version they were recorded on, and the summary shows "approved on version N, current version M" and whether the current version differs from the last approved one.
- **Forking.** Any contributor or above can fork a route they can see.
- **Editor.** Draggable waypoints, insert and delete waypoints mid-route, snapped and freehand segments, reverse, close loop, out-and-back, split the route into two routes at a point, undo and redo, place search via Photon, an elevation profile with hover synced to the map, cue override editing, visibility and collaborator management, planning time, speed, and rider count inputs, delete route, and the share link.
- **Closures.** A closure is an issue with a date range and a polygon or segment set. Confirmed closures feed the router as described in Routing model and produce alerts on routes that cross them. The closures table is seeded from a checked-in list of known long-term closures in the coverage area, verified at build time.

## Collaboration and peer review

**Permissions.** Admin is scoped to a guild. A guild admin may, within their guild, delete or moderate routes whose owning guild is theirs, hide content on them, edit that guild's server settings and role mapping, revert info cards, and suspend a user's access to that guild's routes. Instance admin is a deployment-level role that belongs to no club, which is the point once several clubs share a deployment: someone has to hold the powers that cross guilds, and no single club's admin should. It is the only role that may ban a Discord id deployment-wide, disable guest writing server-wide, approve override table rows (which change routing for every guild), and delete any route. Without this split, one guild's admin could moderate every other guild's routes. Every instance-admin action is audited.

Three properties make the role workable across clubs. It is **managed in the application**, not in a file: the environment holds one bootstrap Discord id for a new deployment, and after that instance admins are added and removed in the admin, audited, with the last one impossible to remove so a deployment cannot lock itself out. It is **independent of every guild**, deriving from the instance-admin list alone and never from guild membership, role mapping, the bot, or the membership cache, so the people who can fix a broken bot can still sign in when every guild is degraded; the only hard dependency is Discord's own login, and if that is down nobody signs in, which is the accepted cost of a single identity provider. It is **visible to the clubs it holds power over**: the current instance admins are listed to every guild admin, and a cross-club action, meaning a deployment-wide ban, a route deletion outside the actor's own guild, an override approval, or a server-wide setting change, notifies the affected guilds' admins with the audit row, the same way a guild remap already does. Holding instance admin does not confer guild admin anywhere; an instance admin who also runs a club holds that separately. In the table below, the Admin column is the guild admin; instance-admin actions are listed separately.

Role permissions:

| Action | Viewer | Contributor | Reviewer | Admin |
|---|---|---|---|---|
| View routes visible to them, comments, info cards | Yes | Yes | Yes | Yes |
| Create and edit own routes, change own route state | | Yes | Yes | Yes |
| Comment, open issues, submit proposals, fork | | Yes | Yes | Yes |
| Confirm and resolve issues and closures | | | Yes | Yes |
| Record approve or request changes | | | Yes | Yes |
| Record approve or request changes on one route via the per-route `review` flag | Yes | Yes | Yes | Yes |
| Edit info cards and propose override table rows | | | Yes | Yes |
| Hide comments and issues | | | Yes | Yes |
| Delete or moderate routes owned by their guild, edit that guild's settings and role mapping, revert cards, suspend access to their guild's routes | | | | Yes |

Instance-admin actions, not available to guild admins: approve override table rows, delete any route in the deployment, ban a Discord id deployment-wide, disable guest writing server-wide, edit the configured guild list, issue a guild re-invite link, remap a configured guild id, and reclassify a guild loss.

Guest standing is a floor, not an alternative role: on a public route with `public_guest_comments` on, any signed-in user who does not already hold comment rights through an audience guild may comment and open issues. A viewer-role member of an audience guild gets the same floor, so a member a club deliberately held at viewer is never worse off than a stranger. Roles above contributor are unaffected. Guest standing grants nothing else: no forking, proposing, approving, or confirming, and no access to any route beyond public routes and any link route whose token the person holds.

Owner-scoped actions, available to the route owner and to admins of the owning guild: edit the route and save versions (also collaborators with the `edit` flag), change state, re-pin, merge or reject proposals, add or remove collaborators, add or remove audience guilds (only guilds the owner belongs to, recorded in the audit log), transfer ownership to a named collaborator who is a member of the owning guild (recorded in the audit log), set visibility, choose link and public downloads, regenerate the share link, post to Discord. Ownership transfers only to a collaborator who belongs to the owning guild, so the new owner can always manage the audience and is governed by settings from a guild they are in. To hand a route to a partner club, the owning guild's admins first reassign the owning guild to another audience guild, which is audited and notifies both guilds' admins. Adding an audience guild is a sharing action and the main way a secret route leaks, so the audience is shown on the route summary next to the visibility tier. Admins of the owning guild moderate the route; an admin of any other audience guild can remove their own guild from the audience, which is their only lever over someone else's route. Removing a guild revokes its members' access but retains their comments, issues, and approvals, which display as from a guild no longer in the audience and stop counting toward the approval total.

Comments, issues, and proposals are open on in-review and published routes. Draft routes accept comments and proposals only from named collaborators. Confirming an issue records reviewer id and timestamp in the audit log.

**Comments.** Belong to a route, record the version they were made on, and carry a map anchor (point, or way id plus offset, with geometry). On a later version, a comment is shown at its anchor if the segment is still on the route and listed as "from an earlier version" otherwise. Comments are never deleted by geometry changes. Comments on a proposal form the proposal thread; a merged proposal's thread is linked from the resulting version's history, and a rejected proposal's thread stays readable. Comments and issue descriptions are capped at 5,000 characters. Guest comments on a public route form a separate public feedback thread, excluded from the Needs review queue's open-comment counts, because they are mostly rider logistics rather than route review. An owner or reviewer can promote one into a review comment or an issue.

**Issues.** Attached to map segments or polygons, not to a route. Categories: safety, surface, closure, navigation, other. Lifecycle: open, confirmed, resolved, won't fix. Any route whose geometry touches an open or confirmed issue shows it, with the reporting route recorded as context. An issue opened by a guest starts in a `reported` state, visible only on the route where it was opened and to reviewers of that route's owning guild; a reviewer accepting it makes it an ordinary open issue on the shared map, and declining closes it with no map-wide effect. Without this step a stranger's report would surface on every other club's routes, private ones included, before any member had read it. Confirmed safety and surface issues feed the reviewer penalty tag at the next rebuild. Crash history informs that confirmation but never bypasses it, so the path from a crash record to a routing penalty always runs through a person.

**Discovery.** A routes index with list and map views filtered by state, modality, owner, distance range, start-area bounding box, and name text, showing only routes the viewer's visibility admits. A "My routes" view. A public index of public routes, reachable without login and the only listing crawlers see. A "Needs review" queue of in-review routes and open proposals sortable by age with counts of open comments and issues, showing the routes of every guild the viewer belongs to, with a per-guild filter. If several organizations repeatedly co-plan, an admin may define a named coalition, a saved set of guilds an owner can add to the audience in one action; this is convenience over the audience list and is not required for first release.

**Notifications.** In-app notification list. Events: proposal submitted (owner), proposal merged or rejected (proposer), comment or reply on a thread (owner and participants), guest activity on a public route (owner, as a daily digest rather than one notification per comment), issue confirmed or resolved (reporter), approve or request changes recorded (owner), collaborator saved a new version (owner), added as collaborator (collaborator), ownership transferred (new owner), route crosses a newly confirmed closure (owner and collaborators with the edit flag), drift report affects a route (owner and collaborators with the edit flag). Discord DMs are out of scope.

**Discord channel posting.** An explicit per-route action by the owner, never automatic, honoring visibility. The bot posts to the configured channel of whichever audience guilds the owner selects, defaulting to the owning guild's. A channel is validated when it is set and the bot's permission to post there is re-checked before each post, since a bot can sit in a guild without being able to speak in that channel; a failed post surfaces to the owner with the reason instead of failing silently. Posts set `allowed_mentions` to none, truncate user text to 500 characters, and are rate-limited to one message per route per 10 minutes.

**Moderation and abuse limits.** GPX uploads: max 20 MB, max 100,000 track points, parsed with `defusedxml`, rejected if not well-formed GPX 1.0 or 1.1. Per-user rate limits enforced in the API: routing 60 per minute, import 10 per hour, export 30 per hour, comments and issues 30 per hour, and for guests on public routes 5 per hour with a total cap per route per day. A Discord account younger than a configurable age cannot post as a guest. Guild admins can hide guest content on their guild's routes and suspend a user's access to them; instance admins can ban a Discord id deployment-wide and disable guest writing server-wide. Every such action is audited. All unauthenticated paths, including the public index, OpenGraph, thumbnails, the read-only view, stats, cue sheet, and downloads, are limited at Caddy to 60 requests per minute per IP, with file downloads limited to 10 per minute per IP. Mountain Goat and multi-pass searches cap candidates at a configured number. An `audit_log` table records actor, action, target, and before and after. A Django history package covers before and after on model rows, but about half of what must be audited is not a model change with a request user behind it: bans, revoke-now, loss reclassification, re-invite issuance, redemption and expiry, remap counts, grace-window lapses, and anything a worker does, which has no request and so no actor unless one is threaded in. Those are written explicitly to the same table with the actor passed in, and audit rows outlive the soft-delete purge. Covered events include issue lifecycle changes, closure confirmation, info card edits, override approvals, proposal merge and reject, approvals, collaborator changes, audience changes, ownership transfers, hide actions, role-mapping changes, and bans.

**Review is asynchronous.** Live collaborative editing is out of scope.

## Import and export

- **Import.** GPX tracks and routes. Tracks are downsampled or chunked to stay inside Valhalla's `trace.max_shape` and `trace.max_distance` limits, or the limits are raised in config. Run `trace_attributes` first to classify points as matched, interpolated, or unmatched; split at unmatched runs; `trace_route` each matched run; unmatched runs become freehand segments flagged in the UI. GPX routes with at most 25 route points (configurable, well inside Valhalla's default bicycle `max_locations` of 50) are routed through `/route` with each point as a `through` location, falling back to the track path if a point snaps to a `bicycle=no` way and the request fails; denser routes, which is how Ride with GPS, Komoot, and Garmin export them, are treated as tracks and map-matched. Imported waypoints are kept as generic cue overrides at their position along the route, or as control points when their name matches start, finish, or rest patterns, and the user can promote or discard them. The turn model emits an "Enter unmapped section, continue N mi" cue at the start of a freehand run and a normal cue at re-entry; freehand distance counts toward mile markers.
- **Compiled artifact.** Every export starts from one compiled route: Valhalla directions plus a per-route cue override layer where the owner can add a cue at a location, edit cue text, suppress a cue, or merge adjacent cues, so cues like "CAUTION rail tracks, cross at right angle", "single file on bridge", and "regroup at top" are first class. Overrides are anchored by a snapped geometry point, not by index or distance; distance-along is recomputed at compile time, so reverse, split, and out-and-back preserve them, and the compiler reports overrides whose anchor no longer lies on the route. Cue types: left, right, slight and sharp variants, straight, u-turn, roundabout exit with exit number and cross street, summit, valley, water, food, danger, generic, and jurisdiction. Each format has a documented mapping from these types. Bear-versus-turn thresholds are tuned against the reference routes because the L'Enfant diagonals produce acute intersections.
- **Formats.** GPX track with waypoints for cues and attribution in metadata; FIT course with course points pinned to the nearest record; TCX; rider cue sheet as HTML and PDF; handlebar-format narrow cue sheet; marshal cue sheet with control points, regroup holds, and ETAs; intersection list as CSV and PDF; printable overview map PDF with numbered turns. The marshal cue sheet and the marshal assignment columns are never rendered or downloadable below server visibility; see Public visibility. The intersection list covers every intersection with cross traffic, with mile marker, control type distinguishing signal, all-way stop, route stops, cross traffic stops, uncontrolled, and circle entry from OSM stop and direction tags, marked "unknown, verify" where tags are missing, turn direction, and blank columns for marshal assignments; alleys and driveways are excluded by default with a toggle. For Mass Ride, the marshal cue sheet and intersection list print front and rear ETAs computed from planning speed and the peloton length estimate. Exports accept a max-cue budget per device profile and drop lowest-priority cues first, since older head units truncate beyond roughly 200 course points; the budget applies to GPX waypoints as well as FIT and TCX course points, because Garmin and Hammerhead convert GPX waypoints to course points on import. Owner-added cues and danger-type cues are never dropped. FIT files are written with the Garmin FIT Python SDK under the FIT Protocol License, or fit-tool under BSD-3; the choice and license are recorded in the data-source document.
- **Social share card.** A rendered image of the route sized for social platforms, produced by the worker through the same headless renderer as thumbnails and cached per version, per style, and per size. Sizes: square at 1080 by 1080, portrait at 1080 by 1350, story at 1080 by 1920, and landscape at 1200 by 630, which shares its path with the OpenGraph thumbnail. A share panel on the route page previews the card, toggles its blocks, picks the size and a light or dark theme, and downloads or copies the result.
  Blocks are individually toggleable: the route line, name, distance, elevation gain, an elevation profile strip, the modality, the planning date, the owning club, and a QR code. The elevation profile and the QR code are both off by default, so a card is a picture unless someone asks for more. The profile is drawn from the same per-version samples as the stats block, so the card and the page can never disagree. Attribution for OpenStreetMap and the basemap is drawn into the image itself and stays legible at the rendered size, because an image posted to a social platform is a produced work that travels without the page's attribution.
  The card discloses no more than the public and link tiers do: start, finish, and rest control points only, never marshal posts, medical, sweep, or bail-out points, and no cue override anchored to a suppressed point. A start-only announcement style draws the start point, date, time, and distance with no route line, for the common case of announcing a meeting point without publishing the course. Generating a full-route card for a route below link visibility warns, in the same words as publishing, that the image discloses the route wherever it is posted and cannot be recalled. When the QR is turned on it encodes the share link, and only at link or public visibility, since a token rendered into a public image is the link; below those tiers the toggle is unavailable and says why.
- **Clean exports.** Attribution and incidental metadata are different problems and get different rules. A byline is a deliberate credit governed by the attribution rule above. Incidental metadata is everything a file picks up from the tools that touched it: author elements, athlete and account identifiers, device names and serial numbers, software creator strings, and recording timestamps. None of that is ever chosen by anyone, and it leaks identity into files that circulate, so no export carries any of it at any visibility or ride purpose.
  Every exported file is built from the compiled route rather than passed through from an import, which is what makes this reliable. An imported file's metadata is read for what the application needs, the route name and any waypoints worth promoting to control points, and then discarded; it is never retained for re-emission. A route imported from a member's Strava account therefore cannot carry that member's athlete identifier into the marshal documents a committee hands out. The same applies within a format's own conventions: a FIT course omits device serial and user profile fields, a GPX omits the author element and names the application as creator, and a cue sheet PDF omits document author and producer fields.
  What an export does carry is fixed and short: the OpenStreetMap copyright, which is required; the route name; the application as creator; and a byline only where attribution is on. Exports are reproducible, so the same route version yields byte-identical files rather than embedding the moment of export, which both makes caching honest and lets a test assert cleanliness by comparing against a known-good file.
- **Delivery tiers.** Direct push where an API exists, manual upload to a hub the device syncs from, and download with per-device instructions. Every route always has the download path.
- **Integrations, as verified at the time of writing and to be re-verified before implementation.** Direct push: Wahoo (Cloud API, `POST /v1/routes` with a FIT file, `routes_write` scope, sandbox then production review; pushes set `external_id` to the route id and `provider_updated_at` to the version timestamp so re-pushes update in place) and Hammerhead (Developer Platform public API, self-serve developer account and API license, supports webhooks). Garmin's Connect Developer Program has paused new partner applications; the Courses API is implemented only if the program reopens and is not scheduled. Ride with GPS's supported v1 API does not create routes, and Strava's API is read and export only for routes, so Ride with GPS, Strava, Komoot, and COROS are manual-upload hubs with per-service instructions. COROS and Komoot partner APIs are not attainable for a community app.
- **Connected accounts.** Per-user OAuth tokens per service, encrypted in the application layer as described in Operations. Each account records provider, provider user id, scopes, expiry, last refresh, and status: ok, reconnect required, revoked. Refresh is serialized per account with a row lock; a failed refresh sets reconnect required and stops pushes rather than retrying forever. A provider deauthorization webhook or a 401 on refresh sets status revoked and stops pushes. Each push records the provider route id and the version pushed, so a new version updates the remote route rather than duplicating it; archiving a route does not delete it remotely. Disconnect calls the provider revoke endpoint where one exists. Push logs are visible to the user and retained 90 days.

## Auth and community

- **Discord login, bot authorization.** Login uses Discord OAuth with the `identify` scope alone, which is a light consent prompt that asks for nothing but the account identity. The user's access token is used once to read that identity and is then discarded: no Discord token is stored, refreshed, or encrypted, so authorization never depends on a user token staying valid. Membership and roles are answered instead by a bot that sits in each configured guild and queries them with the bot token, server-side, at any time.
- **The bot.** One application bot with Public Bot disabled, so only the application owner can invite it. The bot token is an instance-wide secret held like the other secrets in Operations. It needs the server members privileged intent, a portal toggle that is granted automatically below the scale at which Discord reviews it; verify the current threshold before launch, and treat crossing it as a launch-blocking item for the project owner. If the intent is denied or later revoked, the bot falls back to a per-user member lookup over REST on login and on each sweep, with the sweep interval shortened to an hour, so revocation lands within an hour instead of seconds; the admin page records the degraded mode and instance admins are alerted. A guild invites the bot when it wants its own roster, roles, index, and review queue in the deployment; reviewing one route needs only a named collaborator or a link, so a partner club is never blocked on a volunteer admin who reads Discord weekly and would balk at granting an intent that reads their whole roster. The bot also posts route and review announcements to configured channels, replacing the webhook, so posts carry the application's identity and can be edited later.
- **Guild lifecycle.** A guild joins in two steps: an instance admin adds the guild id to the configured list and sets its role mapping, then a guild admin invites the bot. A guild the bot is in but that is not configured is inert, ingesting no members, caching nothing, and granting no standing, and the bot leaves it automatically after a configurable period; without this, anyone who could invite a bot would self-onboard their server and push an arbitrary roster into the database. Removing a guild from the configured list purges its cached membership rows. Because only the application owner can invite the bot, an instance admin can issue a per-guild re-invite link from the admin page, and the degraded and removal alerts sent to a guild's admins carry one; otherwise a guild admin who kicked the bot by accident, which is one right-click in the member list, would be stuck until the application owner answered on a Friday evening. The link is an OAuth install URL pinned to that guild id with guild selection disabled, carrying only the bot and application-commands scopes and the bot's fixed permission integer, wrapped in a single-use token expiring in 24 hours. It is not a login and confers no session, role, or standing, and whoever clicks it must already hold Manage Server in that guild, since Discord and not this application decides who may install a bot; that is what makes email an acceptable channel for it. Redemption, expiry, and revocation are audited and alert instance admins, and issuing a new link invalidates any outstanding one for that guild. Redemption re-admits the bot and nothing else: it does not extend a grace window, reclassify a loss, or restore standing, which resumes only from the backfill once the bot is back in. An instance admin can remap a configured guild id to a new one in a single audited action, so a club that rebuilds its server after a raid, moves off a founder's personal server, or merges two chapters does not orphan its routes; the owner-scoped reassignment cannot cover this, since it needs the old guild's admins to act and both guilds to be in the audience, and the old server may already be gone. Routes, owning-guild and audience references, server settings, and the guild's identity carry across. The role mapping and cached standing do not: role ids are per-guild snowflakes, so the old ones mean nothing in the new guild, and the cases this feature exists for are exactly the cases where the rosters differ, since a server rebuilt after a raid is rebuilt to shed accounts. The remap requires the bot to be present in the new guild with its initial backfill complete, which proves the new guild is real and reachable, and the admin must map the new guild's role ids before it grants any standing. Standing is rebuilt from the new roster, so a member of the old server who was not carried over gets nothing. While the mapping is incomplete the guild is configured but unmapped: routes remain, owners and named collaborators keep read-only access to their own routes for 72 hours, and no role-derived standing is granted. The confirmation names both guild ids, the new guild's name as the bot sees it, and the count of routes, audience rows, and collaborators affected, and the admin retypes the new guild id. Remapping onto a guild id already configured is refused; merging two configured guilds is a remap of one followed by adding the other to the audience. The audit row records actor, both ids, the counts, and the prior role mapping, route owners and both guilds' admins are notified, and an instance admin can reverse a remap within 7 days, restoring the prior ids and mapping but never cached standing.
- **Permission resolution.** A config table `guild_id, role_id, permission` maps Discord roles to application roles. Application permission is the maximum across configured guilds of the mapped roles. A user's permission on a given route is the maximum across only those audience guilds they belong to, so a reviewer in one club does not gain reviewer powers on another club's routes. Membership and role ids are cached in PostGIS per user per guild with the time they were last confirmed. The cache stores the guild id, role ids, timeout expiry, and last-confirmed time keyed by Discord user id, and nothing else: no usernames, avatars, nicknames, or join dates. For a tool whose threat model includes unpermitted rides, who organizes with whom is the sensitive part, so rows for people who have never signed in are purged after 30 days, and the cache is excluded from the nightly dump, rebuilt on restore by the bot's startup backfill and the sweep as set out in the restore runbook. Absence of a row is absence of standing; the cache is never read as unknown-therefore-allow, and the API refuses standing from a row older than the grace period. On start the bot backfills every configured guild before reporting healthy, and a guild whose initial backfill has not finished grants no standing.
- **Re-validation.** The bot holds a gateway connection and updates the cache from member add, update, and remove events, so a role change or a departure takes effect in seconds rather than waiting for a poll. Requests read the cache and never call Discord inline. A six-hourly worker sweep reconciles the cache against the bot's view and repairs anything the gateway missed during a disconnect, and a user's standing is confirmed on login regardless of cache age. Sign-in is open to any Discord account, because the public tier accepts comments from people outside the organizing guilds; membership in a configured guild is what determines standing, not whether a session may exist. A user in at least one configured guild holds the mapped role permission there. A signed-in user in no configured guild holds guest standing only, which grants nothing beyond commenting and opening issues on public routes with `public_guest_comments` on, and a banned Discord id holds no standing at all. Losing all configured-guild membership downgrades a user to guest standing rather than revoking their sessions, and immediately removes access to every private, reviewers, and server route and to any route where their only standing came from that guild. When a user loses their last standing in a route's owning guild, write access ends immediately, but the owning guild's admins are notified at once with a list of that user's routes in review or published and a one-click reassignment, the route's share links, exports, and cue sheets keep working, and the former owner keeps read-only access to routes they own for 72 hours, the window an accidentally degraded guild gets, so a ride three days out is not stranded with its marshal documents unprinted. Three member states are not plain membership and are treated as absent for standing: a member who has not cleared membership screening, shown as pending; a member serving a timeout, cached with its expiry timestamp and treated as restored automatically at that time, since Discord emits an event when a timeout is applied but none when it lapses; and any member of a guild the bot can no longer see.
- **When the bot loses a guild.** Accidental loss and deliberate removal are opposite signals and get different windows. Cause is read from Discord's guild-delete signal: an outage flag means accidental, its absence means removal. A guild found missing on reconnect with no such event is classified deliberate, since Discord marks outage guilds unavailable rather than omitting them; an instance admin can reclassify it as accidental from the admin page, audited, which restores the longer window, but only while the deliberate window is still open. Once standing has lapsed the remedy is re-inviting the bot and rebuilding from the backfill; reclassification never restores an individual role removal, timeout, or ban already processed. Accidental loss, meaning a gateway failure, a revoked intent, or a Discord outage, marks the guild degraded and honors cached standing for a grace period, default 72 hours running from the alert rather than the disconnection, granting nothing new or elevated during it. Deliberate removal of the bot from a guild ends that guild's standing within 15 minutes, because a guild that ejects the bot has left the deployment and because the slow path would otherwise be a moderation-evasion route: a member with Manage Server who is about to lose their roles could kick the bot and keep cached standing. Either way an instance admin, or an admin of the affected guild, can collapse the window at once with an audited revoke-now action, and role removals and timeouts already delivered by the gateway are never resurrected by a later degraded window.
  The affected guild's own admins are alerted in-app and by email at the same time as instance admins, because they are the only people who can fix it and the bot can no longer reach them in Discord. When a window lapses nothing is deleted: that guild's members lose access, share links and public routes keep resolving, owners keep read-only access to routes they own, and re-inviting the bot restores full standing on the next gateway sync, so a volunteer admin who removed the bot without understanding it loses nothing but access.
- **When the bot itself is down.** The same bound applies at the larger scope. If the gateway has been disconnected, or the bot has not confirmed its guilds, for longer than the grace period, every configured guild is marked degraded on the same terms and standing lapses when it expires. The API decides from the last-confirmed time on each cached row rather than a global flag, so a frozen cache expires on its own even when no component is left running to mark it. Failing closed at once would let a single mistaken kick lock out an entire club, and failing open indefinitely would leave stale grants standing.
- **Revocation by the user.** Because no user token is retained, revoking the application in Discord's authorized-apps settings does not end a RouteMaker session. Sessions end by logging out, by admin suspension or ban, or by account deletion. The account page says so plainly and offers a sign-out-everywhere action.
- **Denial messages.** A refusal names its cause rather than reading as a broken site: not a member of any club on this deployment; membership pending, accept that server's rules in Discord, which catches long-standing members who joined before the gate existed; access paused while a Discord timeout is in effect, with the end time; or that guild is temporarily unavailable. A guild admin viewing a member sees the same reason.
- **Sessions.** Django's server-side sessions, rows in Postgres referenced by an HttpOnly, Secure, SameSite=Lax cookie; 30 days idle, 90 days absolute. State-changing requests require a CSRF token, which Django's middleware supplies. Discord login is a custom authentication backend rather than a third-party social-auth package, because standing comes from the bot and not from the OAuth response.
- **Account deletion.** Revokes all sessions immediately, revokes tokens at each cycling service where an endpoint exists, deletes connected-account and push-log rows and the cached guild membership rows, which the hashed-id tombstone then keeps the bot from recreating on the next gateway event or sweep even though the person is still in the guild, assigns authored comments, issues, and proposals to an anonymous sentinel user, and retains only a hashed Discord id tombstone for ban enforcement. Owned routes with named collaborators or recorded approvals are transferred to the first collaborator who has the edit flag and belongs to the owning guild; if none exists, the owning guild's admins are notified to reassign within 30 days before purge, because route leads change every season. Owned routes with no collaborators and no approvals at private or reviewers visibility are soft-deleted and purged after 30 days, since no remaining viewer could fork them and an unpermitted ride's route should not outlive its owner; such routes at server, link, or public visibility are archived and remain forkable. Approvals, info card edits, and override rows keep their audit rows. Audit log rows keep the numeric actor id and display "deleted user".

## Operations

- **Secrets and tokens.** Per-user OAuth tokens for the cycling services, the only per-user tokens the system holds now that no Discord token is retained, are encrypted in the application layer with AES-256-GCM, never in SQL. The key-encryption key is stored as an SSM SecureString, which is KMS-backed, and read once at process start; locally it comes from the environment file. It is never written to the database and is not in dumps. Each ciphertext row carries a `key_id`; rotation adds a new id, re-encrypts rows in a worker job, and retires the old id. Discord client secret, the bot token, the Django secret key, and partner app credentials get the same handling; rotating the Django secret key invalidates every session, which is the intended effect. Production settings are pinned and checked in CI: debug off, explicit allowed hosts and trusted CSRF origins, the proxy SSL header set for Caddy so cookies are marked secure and client IPs are read from the forwarded header rather than Caddy's own, and the session and CSRF cookie flags set to what Sessions states. The bot token is instance-wide and its rotation is a restart of the bot service, not a re-encryption job. S3 access uses the instance IAM role.
- **Backups.** A Procrastinate periodic task runs `pg_dump -Fc` through a sidecar with the matching client version, uploads to S3 with SSE-KMS and 30-day retention, verifies the upload with `pg_restore --list`, and writes a success row that the alert reads. A daily EBS snapshot of the data volume, retained 14 days, covers uploaded GPX originals, exported PDFs, and thumbnails. The `.env` file, the key-encryption key, the bot token, and the Django secret key are stored in SSM so a host rebuild can recover everything it needs. Tiles and graphs are rebuildable and not backed up. Restore runbook: provision host, pull compose, restore secrets from SSM, `pg_restore` the latest dump, run migrations, collect static assets and rebuild the frontend bundle, rebuild tiles from cached extracts, run the membership sweep to convergence before opening the site because restored membership is as stale as the dump and the gateway replays nothing, and run the reference-route tests as a smoke check. Target RPO 24 hours, RTO 4 hours. A restore drill runs before first public release and quarterly.
- **Rebuild and swap.** Valhalla does not reload tiles at runtime. The rebuild writes tiles to a dated directory and packs a tile extract per variant, and writes the new segment table and derived attributes to a staging schema. It starts a second Valhalla container per variant against the new extracts and runs the reference-route tests against them. The segment and derived-attribute tables are unmanaged models, so migrations never create, alter, or touch the staging schema, and the connection's search path is what points the ORM at the live schema. On pass, the swap is one step: rename staging to live inside a single transaction, then repoint the API upstream per variant through a settings table the API watches, reloading its HTTP client without a restart, and stop the old containers. On fail, drop staging, keep the old tiles, and alert. The previous extracts are retained for rollback. The reconciliation job and drift report run after the swap against the live table. Disk is sized for two full sets of every variant plus build scratch. The rebuild container has a memory limit so a build cannot take down PostGIS.
- **Observability.** JSON logs to stdout with a request id propagated to worker jobs, Docker log rotation. Prometheus-style `/metrics` on API and worker: request latency, routing latency, queue depth, job failures. Health checks: PostGIS `SELECT 1`, Valhalla a canary route between two fixed DC points per variant, worker a heartbeat row, the bot a live gateway connection with the time of the last event received. External uptime check on `/healthz`. Alerts by email or an ops Discord channel, except that gateway and degraded-guild alerts go by email only, since the component being reported on is the one that would otherwise carry the message. Alert on: the bot's gateway disconnected for 5 minutes or any guild marked degraded, worker heartbeat silent for 10 minutes (independent of the backup alert, so a stalled worker is caught before the backup window), backup not succeeded in 26 hours, rebuild failed or not completed in 8 days, disk over 80 percent, canary route failing.
- **Host sizing and hardening.** Initial host: 8 vCPU, 32 GB RAM, 200 GB gp3. Compose memory limits: each Valhalla 2 GB, Photon 3 GB, PostGIS 4 GB, rebuild 8 GB, renderer 1 GB, bot 512 MB, API 2 GB, worker 2 GB, Caddy 256 MB, migrate 256 MB; the rebuild container exits before the validation containers start, so the build and the duplicate Valhalla processes are never resident together, which is what keeps the peak inside the host; the sum including swap-time duplicate Valhalla containers must stay under host RAM, verified in CI by a script that reads the compose limits and fails on any service that has none. Security group allows 443 and 80 only, SSH via SSM Session Manager, unattended security updates, named volumes for PostGIS data, Caddy data for certificate persistence, tiles, and uploads.
- **Legal text.** ODbL and Protomaps attribution as in Region and data. A liability disclaimer that routes reflect map data and community reports, that jurisdiction information is community-maintained and not legal advice, and that riders are responsible for their own safety.

## Quality bar

- **Unit tests** for the stress classifier, the conflation step, the jurisdiction tagger and crossing rules, the border control node insertion and crossings table, the directional conditional access remap for the parkway reversal, the Lua remap producing the intended Valhalla attributes for each stress tier, the turn model and left-turn classifier, and the cue type mappings per format.
- **Reference routes** live in `fixtures/reference-routes/` with a README recording their measured properties. Four real DC Bike Party mass rides are supplied and are the ground truth for the Mass Ride preset. They bound it in ways the preset had left open: 5 to 7.5 miles, 63 to 164 feet of gain with brief pitches near 6 percent, 2 to 4 turns per mile, entirely within the District, point-to-point from a fixed start with a near-loop as the occasional case, and no route revisiting its own line. Three real trail routes are also supplied, of 15, 32, and 76 miles, and they bound Trailmaxxing quite differently: 701 to 2333 feet of gain, pitches to 12 percent, and a crossing of the District line on every one. Two design decisions rest on them. Grade tolerance is per-modality rather than global, since one cap would either reject these or be useless for mass rides. And the state-crossing penalty is rightly off by default outside Mass Ride, because all three would be unroutable with it on. Turn density, at 2.3 to 2.9 per mile, is the one measure that does not separate the two sets, so turn count alone never distinguishes a trail route from a road one. A known good group ride loop is still wanted. For each, routing its waypoints with its intended modality must reproduce at least a per-route percentage of the reference geometry by distance, initially 80. Per-modality invariants asserted on every reference route: Mass Ride includes zero trail-class distance, stays between 4 and 9 miles, keeps gain under 250 feet, exceeds 6 percent grade on no more than a token distance, averages under 5 turns per mile, and revisits no location, each bound drawn from the reference routes with headroom; Group Ride includes zero distance on ways traversed at dismount speed and a trail-class share at most the reference route's own; Beginner includes zero top-tier stress distance, or where the router degraded to a penalty the stats block carries a gap warning and the flagged distance equals the top-tier distance; Recovery gain is at most Default gain; Mountain Goat gain is at least Default gain; Fast turn count is at most Default turn count; Trailmaxxing reproduces the trail routes within the same geometry threshold, reports road exposure greater than zero on each, and is not penalized for crossing the District line.
- **Authorization tests.** A role removed in Discord revokes the matching application permission once the gateway event is processed. A pending member, a timed-out member, and a member of a guild the bot cannot see all resolve to absent standing. A guild marked degraded honors cached standing within the grace period, grants nothing new during it, and lapses to none after it. No Discord token is persisted anywhere. A guild the bot is in but that is not configured grants no standing and produces no cached rows. A cached row older than the grace period grants nothing even with no component running to mark it degraded. A deleted user still present in a guild is not re-cached. After a remap, a user in the old guild but not the new one has no standing, and no standing is granted until the new guild's role mapping is set.
- **Warnings default test.** Jurisdiction warnings depend only on the per-route setting, and its default is computed from modality and purpose exactly as in the table. Explicitly set values survive a modality change.
- **Visibility tests.** No admin list view shows a route, comment, or membership row the viewing admin's guild scope excludes, and an instance-admin-only action is refused to a guild admin through the admin as well as through the API. A guild admin cannot edit a membership row, a role mapping, or a route's owning guild through the admin, and the attempt is refused and audited. No account holds a usable password or superuser status, and the admin login form does not answer. An instance admin retains admin access when every configured guild is degraded and the bot is down, and removing the last instance admin is refused. A private route is unreachable by share link, index, queue, bot announcement, and thumbnail. A reviewers-visibility route's thumbnail and metadata are unreachable without login. Only link and public routes serve OpenGraph data and thumbnails unauthenticated, and at `link_requires_login` true only public does. A reviewers-visibility route whose audience is guild A alone is unreachable by a reviewer whose only membership is guild B, and becomes reachable only after guild B is added to the audience, which writes an audit row. A user holding the reviewer role in one audience guild and none in another gets reviewer permission on the route. An in-review route at link visibility and one at public visibility both appear in the Needs review queue of every audience guild. A First Amendment assembly route omits author and club from its public page, OpenGraph data, thumbnail, every export, and its share card, while the audit log and in-guild views still name the actor; a recreational route attributes on all of them. A draft never appears in the index, queue, or Discord posting, and a draft set to public behaves as link, staying out of the public index until it leaves draft. Only public routes appear in the public index and omit `noindex`. A guest can comment on a public route and can do nothing else, including on that same route: no fork, proposal, approval, or confirmation. With `public_guest_comments` off, or with it off for one route, a guest write is refused.
- **Export consistency test.** One compiled route exported as GPX, FIT, TCX, and each cue sheet yields identical ordered turn lists after applying the format's cue mapping. Exporting the same route version twice yields byte-identical files. A route imported from a file carrying an author element, an athlete identifier, a device serial, and a creator string exports with none of them present in any format, asserted by scanning the output bytes, while the OpenStreetMap copyright survives. A social card carries the same distance and elevation gain as the stats block for that version, renders attribution at every size, omits every suppressed control point, and in the start-only style contains no route geometry.
- **End-to-end tests** for: create, save, share link; submit, compare, merge, and reject a proposal including the advanced-base case; comment anchoring surviving a version change; issue confirm feeding the penalty tag after a rebuild; a closure producing an alert on a crossing route; a request with explicit zero crossing costs paying nothing at a state line.

A checked-in list of DC traffic circles (Dupont, Logan, Thomas, Scott, Washington, Columbus, Chevy Chase, Westmoreland, Grant, Sherman, Ward, Tenley, Sheridan, Barney, Randle, and the Lincoln Memorial circle) with expected cue text. ## Working conventions

- Ask before choosing between materially different approaches. Do not ask about routine implementation choices.
- Keep any Valhalla fork as a patch set with a documented rebase procedure.
- Document every external data source with its license, URL, and refresh procedure, and re-verify partner API terms before implementing each integration.
- Partner API registrations are project-owner tasks: Wahoo sandbox and production review, Hammerhead developer account and API license, Garmin only if the program reopens. Build against the download path first and stub the push adapters.
- Never present jurisdiction, permit, or access information in the UI as a legal statement.
