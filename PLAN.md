# RouteMaker: build specification

## What this is

RouteMaker is a web application for planning bicycle routes collaboratively, targeted at the Washington, DC metro area. It exists to solve two problems that existing tools such as Ride with GPS and Komoot handle poorly: planning a route with other people, and planning for different cycling modalities, where a route that is good for a solo rider is wrong for a dozen people and unusable for a thousand.

Users sign in with Discord, build or import routes, choose a modality that shapes how the router weighs roads, trails, hills, and turns, and put routes up for peer review. Reviewers comment on specific places, report issues and closures, record approvals, and propose alternatives that the owner can merge. Routes export as GPX, FIT, TCX, cue sheets, and marshal documents, and push directly to cycling services where an API exists.

Reader's note on precedence: decisions recorded as "owner decision" in this document were made by the project owner and are not open to reinterpretation by an implementing engineer.

## Region and data

- **Coverage.** The DC metro, clipped to a polygon covering roughly Frederick and Leesburg to the northwest, Annapolis to the east, and Fredericksburg to the south. Geofabrik extracts for DC, Maryland, and Virginia, merged then clipped with `osmium extract -s smart -S types=any` so boundary relations stay complete. Admin data is built with `valhalla_build_admins` from the merged extract before clipping, and `valhalla_build_timezones` is run so `date_time` requests work.
- **Elevation.** USGS 3DEP. Valhalla's elevation reader takes big-endian int16 HGT tiles, 1 arc-second at 3601 by 3601 or 3 arc-second at 1201 by 1201, gzipped or not, in latitude-band subdirectories, so a tile is at `<dir>/N38/N38W077.hgt`. Use 1 arc-second. Resample 3DEP with `gdalwarp` to that grid with explicit extent and size and write with GDAL's SRTMHGT driver; the resample is what produces the grid, so do not trim by hand, since 3DEP 1 arc-second tiles are 3612 by 3612 with a six-pixel overlap per side and a literal trim yields 3600 by 3600 rather than the 3601 the format needs. The AWS terrain-tiles skadi set is an acceptable shortcut, but it is a multi-source mosaic with its own attribution list rather than simply 3DEP-derived, so taking it means either crediting per that list or restricting the shortcut to tiles confirmed 3DEP or SRTM across this coverage polygon; the choice is recorded in the data-source document. Elevation tiles are built once and cached on the tiles volume; the weekly rebuild reuses them. Caching the tiles is not the same as using them: `valhalla_build_tiles` runs with the elevation directory configured for every variant, so `weighted_grade`, `max_upward_grade`, `max_downward_grade`, and `mean_elevation` are baked onto edges. Without that step `use_hills` is inert on every preset that sets it, Mass Ride's grade cap has no `max_grade` to read from `/trace_attributes`, and the Recovery and Mountain Goat gain invariants both fail as ties. The elevation stage is part of the weekly rebuild even though the HGT data is cached, and a build validation check confirms that a known steep edge reports a nonzero weighted grade before the swap is allowed. Elevation is re-pulled from 3DEP annually or when USGS publishes new coverage for the region; that rebuild is manual.
- **Base map.** A PMTiles file extracted with `pmtiles extract` from the Protomaps daily build against the coverage polygon, served by Caddy with HTTP range requests and read by MapLibre through the pmtiles protocol adapter. Glyphs and sprites are self-hosted. Caddy serves PMTiles, glyphs, and sprites only to requests whose `Origin` or `Referer` matches the app host, with a per-IP range-request limit. Refreshed monthly by the worker. Protomaps basemap layers do not carry surface or cycleway detail, so stress and infrastructure are drawn as an overlay from the application's own segment table. Do not use the public OpenStreetMap tile servers.
- **Stress data.** Stress is derived from OSM tags using the Furth 2017 Level of Traffic Stress tables as implemented by OSM-based classifiers such as BikeOttawa's, reimplemented rather than copied unless that code's license is recorded and compatible. Inputs: `highway`, `lanes` normalized per direction, `maxspeed`, `cycleway*`, `shoulder*`, `width`, `parking:*`, `oneway`, `surface`, `tracktype`, `smoothness`, and annual average daily traffic with its year and its definition, with documented default assumptions where any is missing, erring toward the higher-stress reading rather than the lower. Volume belongs in this list because three later paragraphs turn on it, and it is normalized to one definition across the three jurisdictions before the classifier reads it: VDOT publishes bidirectional counts, the District publishes AADT, and Maryland's is embedded in a finished score, so without a common definition the same road takes different tiers on either side of a line. DDOT bike lane data from Open Data DC (CC0) is conflated onto OSM ways by buffer overlap with documented precedence. OpenStreetMap is the baseline everywhere. For the Maryland portion of the coverage area it is improved by the Maryland Department of Transportation's statewide Bicycle Level of Traffic Stress layer, published on the state's iMAP catalog under terms quoted verbatim and resolved under Licensing below: free redistribution provided the metadata entry is not modified or deleted, and derived data must acknowledge the State of Maryland in the metadata. Those conditions bind downstream recipients, which is the case the gate exists for, so the layer feeds the deployment's own tiles through a separate collective-database table while the published derivative carries the OSM-only tier for Maryland segments, pending a waiver.
  What is taken from that layer is its volume attribute, not its finished score. The earlier draft ingested the score and fell back to the OSM-derived one where conflation failed, which cannot coexist with the claim two paragraphs down that stress is computed the same way everywhere from the same tables; and the scales differ, since Maryland's runs zero to five while the Furth tables the rest of the region uses run one to four, so "top-tier stress" would mean different things on either side of the District line while Beginner's invariant and the road-exposure report both key on it. One scale, computed once, from the same tables, everywhere. Where the finished score is nonetheless consulted, it is consulted as a check-only source under the rule below, and every segment's stress carries the provenance of the inputs that produced it.
  That layer earns its place by carrying what OpenStreetMap structurally lacks: traffic volume, alongside speed and facility type. It scores every roadway in the state and adds two values beyond the usual four, zero for shared-use paths suitable for all ages and abilities and five for roadways where bicycle access is prohibited, and the five is evidence about parkways and limited-access bridges rather than an access determination. An agency's modelled stress class is not a legal access finding, and translating it into `bicycle=no` would make ways unroutable for every modality with no review, bypassing the override table that this document elsewhere makes the sole audited path for access corrections and sitting badly with the rule never to present access information as a legal statement. So a five seeds a candidate row in the override table for admin approval; the routing input stays OSM `bicycle` and `access`. Its companion road-separated bike routes file covers shared-use paths, rail trails, and side paths, which is the sidepath evidence the roadway-versus-sidepath bridge distinction needs. Both are conflated onto OpenStreetMap ways by the same matching rule every agency layer uses, since plain buffer overlap mis-assigns on exactly the geometries this plan depends on: divided carriageways and parallel sidepaths, which carry the roadway-versus-sidepath bridge split and the parkways. A match requires bearing agreement within a stated tolerance and either a minimum overlap fraction or a bounded Hausdorff distance, and assignment is one-to-one so a single agency feature cannot claim both carriageways. Precedence is explicit and ordered: a local agency's own facility layer, then the state layer, then the OSM-derived value, with the loser recorded rather than discarded. The result is asserted against the checked-in Potomac and Anacostia crossings fixture, and any way the conflation fails to match falls back to the OSM-derived score.
  The District closes the third side. Open Data DC publishes annual traffic volume, dedicated to the public domain under CC0 with attribution requested rather than required, which is the least encumbered of the three and needs no license gate at all. With it, every jurisdiction in the coverage area has the volume input the classifier cannot infer, and stress is computed the same way everywhere from the same tables, rather than being imported from one agency and guessed at elsewhere. The Virginia gap is closed the same way, by the input rather than by a finished score. The Virginia Department of Transportation publishes bidirectional traffic volume through its Virginia Roads open data portal, updated annually, and volume is the one input the classifier cannot infer from OpenStreetMap. Conflated onto OpenStreetMap ways by buffer overlap plus route number and name matching, with documented precedence and a fallback to the OSM-derived score wherever the match fails, it lifts Virginia close to Maryland without a Virginia stress score needing to exist. Where a VDOT dashboard is the entry point, the layer behind it is what to ingest, never the dashboard.
  Coverage is better than Virginia's road-maintenance arrangement would suggest, and the distinction is worth stating because it is easy to get backwards. Under the Byrd Road Act, Arlington and Henrico kept their own secondary road systems and the independent cities maintain their own streets, so VDOT does not maintain much of the dense near-DC grid. Its traffic monitoring program is separate from maintenance and statewide: VDOT publishes volume estimates in about a hundred area books covering the roads within each county along with the cities and towns inside it, and the Virginia Open Data Portal carries the result as a per-locality annual series, Arlington and Fairfax alongside Loudoun, Prince William, and the rest. So the working assumption is that the localities are covered, and the thing to verify at ingest is count density on local streets rather than whether a jurisdiction appears at all. Where a locality also runs its own portal, prefer whichever proves denser on residential streets. Virginia Roads states open data with no restrictions, which clears it against all three questions of the gate below: it may be redistributed, it carries nothing that binds a downstream recipient and so nothing that would conflict with relicensing the derivative under ODbL, and with no attribution condition to satisfy the credit on the data page is courtesy rather than obligation. That makes VDOT volume the second-least encumbered source in the region after the District's CC0, and it is recorded that way rather than re-litigated at ingest. Where a locality publishes its own series on a different portal, that portal's terms are recorded at ingest like every other source's, which is the standing procedure rather than a doubt about Virginia.
- **Speed outranks volume.** The recent attention to volume should not be read as making it the primary variable. In the Furth tables, stress on a road without bike facilities is driven first by speed and lane count, with volume acting as a modifier on two-lane roads, and that ordering is correct for cycling because what makes a road hostile is the speed differential between a bicycle and the traffic passing it. A quiet two-lane road posted at 50 with no shoulder is high stress at almost any volume, while a congested downtown grid posted at 25 is not.
  This is a concrete failure mode rather than a nicety. A naive reading of low volume as quiet would route Trailmaxxing and Group Ride onto exactly the fast rural two-lane roads in western Loudoun, upper Montgomery, and Frederick that a dozen riders should never be on, and it would do so confidently, because those roads really do carry little traffic. The classifier therefore treats a missing speed as the conservative value for the road class rather than an optimistic one, and the reference-route invariants include an upper bound on distance at high posted speed without a shoulder or bike facility for both presets.
  Two qualifications belong in the same place. OpenStreetMap carries the posted limit, while operating speed on a wide rural road with good sightlines often runs above it, so a road's geometry is evidence about speed that the posted value understates. And shoulder presence is what changes the answer at speed: a 45 mile per hour road with a wide paved shoulder is a different proposition from the same road without one, so shoulder and effective width are inputs alongside the posted limit wherever they are tagged, and are a priority for the override table wherever they are not.
- **What volume coverage actually looks like.** Do not infer gaps from who owns or maintains a road, which is the mistake this paragraph exists to prevent. Traffic monitoring follows federal reporting obligations, which run to all public roads, so a state or district count program covers roads it does not maintain: VDOT's area books include the cities and towns inside each county, and the District's volume layer covers the federally owned roadways, Rock Creek Parkway, Beach Drive, the Mall roadways, and the memorial bridge approaches among them. Those are the roads a mass ride most wants, and they are counted. The real variable is density rather than jurisdiction. Count programs concentrate on arterials, so minor residential streets often carry sparse or modeled values, and that is not an error to chase: low volume is the right default for a residential street and the classification tables care most about getting arterials right. Anything genuinely uncounted falls back to the OpenStreetMap-derived score and is a candidate for the override table.
- **Crash history.** VDOT also publishes crash data, including a corridor-level view of the roads with the most crashes. It is worth ingesting, subject to the same gate, but it is advisory and never a routing input, and that distinction is deliberate rather than an omission to be tidied up later. Crash counts are an outcome measure without an exposure denominator: a road nobody rides records no bicycle crashes, so the roads that look safest in the data include both the genuinely safe and the too-hostile-to-ride. Penalizing crash locations in routing would therefore push riders off busy good routes and onto empty bad ones, which is the opposite of what the data appears to say. Bicycle crashes are also badly underreported and rare enough per segment to be statistically noisy, and corridor aggregation, while it blunts both problems and avoids mapping individual collisions, is coarser than the segment the router works on.
  What it is good for is human judgment. Crash history for a segment is a map overlay a reviewer can switch on, it is surfaced automatically when someone opens a safety issue on that segment so the reviewer deciding whether to confirm can see it, and a segment whose crash history disagrees with its stress score is flagged for review, which is the cheapest way to find where the classifier or the tagging is wrong. Bicycle-involved crashes are the subset that matters; all-mode counts are a much weaker signal for this purpose. Montgomery Planning's own stress layer is not ingested, because its terms forbid incorporation into other maps without written permission; it may still be used privately to check the classifier, with none of its values reaching the database or the published derivative.
- **Jurisdiction polygons.** Police jurisdiction, right-of-way owner, and park or trail manager are separate layers. Sources: DC boundary and the Architect of the Capitol jurisdiction polygon (`AOCPly`, the area the Capitol Police polices) from Open Data DC (OCTO, CC0); all NPS unit boundaries inside the coverage polygon from the NPS open data portal, in all three states, including President's Park for the White House complex; Census TIGER county layer (Virginia independent cities are county equivalents), TIGER place layer for municipalities with their own police such as Rockville, Gaithersburg, Takoma Park, Hyattsville, College Park, Laurel, Greenbelt, Bowie, Frederick, Annapolis, Vienna, Herndon, and Leesburg; TIGER military installations for Joint Base Anacostia-Bolling, Fort Myer, Fort Belvoir, and the Pentagon reservation; Arlington National Cemetery and the airport from the NPS and TIGER layers where present; park and trail boundaries from OpenStreetMap, using park polygons and their operator tags rather than the park agencies' own parcel files, which carry the same redistribution terms as the stress layer; state road ownership from OpenStreetMap route and ref tags, with the Maryland SHA and VDOT inventories used only to check that derivation. Federal land outside DC is first class: the GW Parkway and Mount Vernon Trail, Clara Barton Parkway, C&O Canal, BW Parkway, Suitland Parkway, and Greenbelt Park are all NPS.
- **Way-level override table.** A community-editable, admin-approved table of per-way corrections applied during preprocessing: jurisdiction overrides for DDOT arterials that cross NPS units such as Constitution and Independence Avenues through the Mall and Military Road and Massachusetts Avenue through Rock Creek Park, bridge legality corrections, and access corrections. Seeded from the verification fixtures in the Quality bar.
- **Refresh.** A weekly job pulls fresh extracts, runs preprocessing, rebuilds every Valhalla tile variant, validates them, and swaps tiles and the segment table together. See Operations for the swap procedure. The geocoder and basemap are refreshed monthly on their own path.
- **The ingest procedure**, which is the operational part and the only part an implementer acts on. Record the item page's terms in the data-source document at ingest. Put them to the three questions below. Proceed unless one fails; escalate a failure to the project owner; substitute OSM-derived or federal data where it cannot be resolved. Already cleared: Open Data DC under CC0, USGS 3DEP, Census TIGER, and NPS. Failed and substituted: the Montgomery Planning layer, now check-only. Also cleared: Virginia Roads, which states open data with no restrictions. Conditional: Maryland iMAP, resolved below on its actual terms rather than a secondary reading. The two bullets that follow record why the gate is shaped this way; they are reasoning rather than instructions, and none of it is legal advice.
- **The Maryland terms, recorded verbatim**, because everything about the Maryland side turns on two sentences and an earlier draft characterized them from a secondary source. The additional license terms disclaim warranty at length and then say: "The Data can be freely distributed as long as the metadata entry is not modified or deleted. Any data derived from the Data must acknowledge the State of Maryland in the metadata."
  The disclaimer is not a restriction and does not reach the gate. The last two sentences do, and they are the CC-BY-shaped case the second question exists to catch: both bind a recipient of the derived data, not only this project. They are also light as such conditions go, an attribution-in-metadata requirement with no share-alike, no non-commercial clause, and no bar on derivatives, so this is a fit problem rather than an incompatibility of substance.
  The tension is specific. Publishing a derivative under ODbL gives a downstream recipient ODbL's terms alone, which do not require preserving a Maryland metadata entry, so this project can either add that requirement, which ODbL forbids imposing on a derivative database, or leave the recipient free to drop an acknowledgment Maryland says must travel with derived data. One reading says a notice placed in the database's own metadata satisfies Maryland and is then carried by ODbL's own attribution clause, which is how a good-faith compliance would look. The other says a condition that must survive redistribution is exactly the term ODbL bars. Both readings are available on this text, and a build spec is the wrong place to pick between them by assertion.
  So the decision is shaped to be correct under either reading, and it costs little because a narrowing was already made for unrelated reasons. Only Maryland's volume attribute is taken, never its finished score, and stress is computed from the same tables everywhere. The State of Maryland is acknowledged in the derived database's metadata, in the alterations file, on the data page, and in the metadata slot of every export format that has one. FIT has no such slot and carries the credit on the download page instead, under the carve-out already recorded, and that is the one place the fit to "in the metadata" is inexact rather than merely arguable.
  Until an explicit waiver is in hand, nothing this project publishes carries a condition it cannot pass on. Maryland-derived values live in a separate collective-database table that the deployment's own tiles read, while the published derivative and the alterations file carry the OSM-only stress tier for those segments, flagged by the per-segment provenance the classifier already records. The running system therefore has Maryland volume and the published database does not depend on it. Requesting a waiver in the pattern the OpenStreetMap Foundation uses for state agencies is a launch-blocking task for the project owner rather than a nicety: it is a short request, agencies grant it routinely, and it collapses all of the above into merging the layer normally. If it is refused, the fallback is demotion to check-only alongside Montgomery Planning, and the cost of that is stated plainly, which is that Maryland loses the one input OpenStreetMap cannot supply.
- **Why the gate is not uniform.** Federal works sit outside copyright by statute, which is why USGS elevation, National Park Service boundaries, and Census TIGER get a light check rather than an examination. Light rather than none: the statute covers works prepared by federal officers and employees, not contractor-produced datasets an agency merely publishes or copyright assigned to the government, and a federal download portal's own terms are a contract question the same way any other portal's are. So for a federal source the check is to confirm no contractor or third-party layer is bundled in and to record the portal's terms, after which it is treated as public domain here. That statute binds the federal government only. State, county, and municipal works are not automatically public domain, and neither Maryland nor Virginia broadly disclaims copyright in its own material, so the same assumption applied downward is how a project ends up redistributing something it may not. The District's CC0 dedication is an affirmative choice its open data programme made, not a default it inherited.
  "Open data" on the portal is a good prior and has held for most sources here: the District's is CC0, Maryland's permits redistribution with credit. It is a programme name rather than a licence, though, and the one source that failed this project was published on a hub carrying exactly that label. So the check is calibrated rather than suspicious: record what the item page says at ingest, which the data-source document requires anyway, and put the terms to three questions rather than one. May it be redistributed at all. May it be relicensed under ODbL without carrying its own conditions onto downstream recipients. Is its attribution satisfiable by the produced-work notice. The second is the one a single conflict test misses: ODbL forbids imposing on the database or a derivative any term that alters or restricts the license, so a condition binding downstream recipients, such as preserving a metadata entry or crediting the state in derived data, is such a term even though it conflicts with nothing about redistribution as such. This is why the OpenStreetMap Foundation asks for an explicit waiver for CC-BY-shaped government data rather than treating attribution-only terms as automatically compatible. A source that fails the second question takes one of three routes: a waiver in that pattern, a separate collective-database table never merged into the published derivative, or demotion to check-only. The Maryland stress layer is re-examined against this gate before it feeds the published derivative, since the Maryland and Virginia side of the stress pipeline rests on that one decision.
  A check-only source may never be the sole basis for an override row or a tuned constant. A reviewer who reads a restricted value and then edits a row to match has put that value into the published derivative in substance, which the carve-out exists to prevent. A discrepancy a check-only source surfaces is recorded as a question and resolved by independent re-derivation from OSM, federal, or CC0 inputs, with the resolving evidence cited on the row. No source is held up waiting for a reading; a source whose terms turn out to conflict is swapped for OSM-derived or federal data, which is what happened once and cost nothing.
  Copyright is in any case the weaker half of the question. Facts are not copyrightable, so traffic counts, boundary lines, and road geometry carry thin protection at best. What actually binds is the terms accepted on download, which is a contract and holds whether or not any copyright exists. That is exactly the Montgomery Planning case: a clause forbidding incorporation into other maps blocks publishing an ODbL derivative regardless of what could have been asserted. None of this is legal advice, and a source worth relying on is worth a lawyer's minute.
- **License record.** Ingested data is OpenStreetMap, Open Data DC (CC0, covering both the bike lane and traffic volume layers), Virginia Roads (open data, no restrictions stated, covering the VDOT volume series), NPS, USGS, and Census TIGER, all of which permit redistribution and ODbL-compatible derivative use. Maryland iMAP is ingested under the conditional arrangement set out above: its volume attribute is read, the State of Maryland is acknowledged wherever a metadata slot exists, and its influence is kept out of the published derivative until a waiver is granted, so no condition this project cannot pass on ever reaches a recipient. Every source's license is recorded in the data-source document as it is ingested, alongside its URL and refresh procedure, and a source whose terms turn out to forbid redistribution in exports or derivative use is replaced by OSM-derived or TIGER data. That is how the park agency and state road inventories became checks rather than inputs. The same applies to any reused classifier code.
- **Licensing.** Every external source is documented with license, URL, and refresh procedure. The OSM extract with injected derived tags is an ODbL derivative database. To satisfy ODbL share-alike, the derived-tag database and the diff the pipeline produces are published under ODbL; the pipeline source code is published under MIT. Owner decision: the application is MIT too, one license across the repository rather than a split, so the pipeline and the app it serves carry the same terms and a club that wants to run its own copy can, modified or not, without asking. The share-alike obligation lives where ODbL puts it, on the derived database and its alterations file, and is unaffected by the code license. Contributions that feed preprocessing (issues, closures, override rows) are licensed by their authors under ODbL for data and CC BY-SA for text, stated in the sign-in terms and on the issue and override forms; info card text is CC BY-SA. Attribution "© OpenStreetMap contributors" appears on every map, thumbnail, cue sheet, export download page, and in GPX metadata, alongside "© Protomaps" on maps. USGS 3DEP, Census TIGER, Open Data DC, and NPS are credited on a data page, and the State of Maryland is credited there and, where its layer's terms survive the gate above, in the metadata of anything derived from it.
  Because attribution has to land somewhere concrete in each format, the slot is named per format rather than left to the exporter: GPX 1.1 `metadata/copyright` with no hardcoded year, TCX `Course/Notes`, CSV a header comment, PDF a footer, HTML the page footer, the social card and thumbnail a rendered credit line. FIT has no free-text notice field at all, so it carries attribution in the course name suffix where it fits and otherwise on the download page and in the accompanying README, recorded as an explicit carve-out rather than an omission; the cleanliness test asserts that carve-out for FIT and the embedded notice for every other format. The basemap credit follows the renderer rather than the surface name, so anything drawn from the basemap carries it, thumbnails and share cards included. Text contributions and info cards are CC BY-SA 4.0. Geocoder results appear in the editor's search panel, which carries the same OpenStreetMap credit a map view does.
  The exported artifacts are also classified, since a recipient needs to know what they hold. The overview map PDF, the cue sheet PDFs, thumbnails, and the social card are produced works. The GPX, FIT, and TCX geometry and the intersection list CSV are extracts of the derivative database, and a single route's geometry is treated as an insubstantial extract with the reasoning recorded rather than assumed. The license line and a link to the ODbL alterations file appear on the export download page and on the public route page, because the alterations file has to be offered to recipients of produced works rather than merely published somewhere.
  Users grant a license too, which the earlier draft covered only for preprocessing inputs. The sign-in terms carry a user-content clause covering routes, descriptions, and cue text as well as issues, closures, override rows, and info card text: the operator may host, render, export, and distribute them for the service, and other users may fork and export a route at the visibility its owner chose. What a public route's viewers may do with it is stated on the route page, consistent with the assembly-purpose suppression rule.

## Architecture and stack

- **Frontend.** React with TypeScript and MapLibre GL. Viewing, commenting, and issue reporting work on phones; the editor is desktop-first and best effort on mobile. No native app and no offline mode.
- **Accessibility**, which nothing in the earlier drafts addressed and which splits cleanly in two. Everything that is not the map canvas is an ordinary document and is held to WCAG 2.2 AA: the cue sheets, the route summary and stats, the review queue, comments and issues, info cards, the admin, and every form, all operable by keyboard alone, with visible focus, labelled controls, and errors announced rather than shown only in red. The exported PDFs are tagged with a reading order, because a cue sheet is the artifact a rider is most likely to need read aloud. Nothing anywhere encodes meaning in color alone: the stress overlay, the boundary layers, and the grade profile each pair color with a pattern, a label, or a shape, which also makes them legible in the printed black-and-white a marshal actually carries. Contrast is checked in CI against the palette rather than by eye.
  The map canvas is the honest exception. Dragging a waypoint on a WebGL canvas has no good keyboard equivalent, so rather than claim one, every route-shaping action has a non-canvas path: waypoints are listed, reorderable, and editable as addresses or coordinates; control points are placed from that list; and the whole route can be built, reviewed, and exported without touching the canvas. The route page states which surfaces are conformant. An accessibility pass is a phase 2b deliverable rather than a post-launch cleanup, since retrofitting is what makes it expensive.
- **Backend.** Python with Django and Django Ninja. Ninja keeps Pydantic request and response models and an OpenAPI schema, from which the frontend's TypeScript types are generated, while Django supplies the ORM, sessions, CSRF, migrations, and the admin. Django migrations run in a one-shot `migrate` compose service that the API and worker depend on with `condition: service_completed_successfully`.
- **Why Django here.** The choice follows the shape this plan grew into. It carries roughly a dozen permissioned admin surfaces (role mapping, configured guild list, guild remap and re-invite links, five server settings, override row approval, versioned info cards, the audit log, moderation, failed jobs, degraded guilds), which is what Django's admin exists to remove. GeoDjango gives PostGIS field types, spatial queries, and a map widget configured against the self-hosted basemap rather than its default, which would otherwise call the public OpenStreetMap tile servers this plan rules out, so jurisdiction overrides, closures, and way-level corrections are edited by drawing on a map in the admin rather than in a second bespoke editor. Django's migrations handle spatial and custom types more reliably than autogeneration against them. The async argument that once favored a lighter framework has shrunk, since candidate search, exports, pushes, and rebuilds are all worker jobs now and a waypoint drag is a single Valhalla call. Revisit if live collaborative editing comes into scope or candidate search returns to the request path.
- **What Django does not give.** Its permission system is model-level, and this plan's authorization is object-level throughout: per route, per guild audience, per collaborator flag, with guild admin distinct from instance admin. The authorization layer is written by hand either way, and every admin model overrides its queryset and per-object permission checks to respect it. What is saved is forms, list views, filters, and history, never the access rules. An admin view that does not narrow by the viewer's guild is a leak, so the visibility tests cover the admin too.
- **The admin introduces no second credential.** Django's admin ships its own username and password login, which is a credential class this threat model does not have: every other path is Discord-only, with standing from the bot, a deployment-wide ban list, and sessions as the revocation mechanism, and a stored password would bypass all of it and sit in the nightly dump. So the admin login form is disabled and the admin is reached only through the Discord session, no account ever has a usable password, staff status is derived per request from application standing rather than stored as a grant, and no account is a superuser, since superuser short-circuits the per-model permission checks this design depends on.
  Django does none of that by default, so the mechanism is specified rather than implied. `is_staff` becomes a read-only property on the custom user model resolving to "holds guild admin in at least one configured guild, or is an instance admin", computed by the authorization resolver and cached on the request. A custom admin site subclass answers `has_permission` from that same resolver and returns 404 from its login view. An authentication backend implements `has_perm` and `has_module_perms` from application standing, because with no superuser and no `auth_permission` rows every such call would otherwise return false and the admin would render empty for everyone who reached it. Accounts are created with an unusable password, `is_superuser` is forced false at the model level, and the admin's own log and history views are filtered by the same guild scope as every other queryset. A banned or lapsed admin loses the admin along with everything else, because one answer serves both. The admin is served under a non-obvious path, which is obscurity rather than a control and is not what protects it: the disabled login form, derived staff, and per-object checks are. The path is absent from the OpenAPI schema, the frontend bundle, and its sourcemaps, since Ninja and admin assets are collected into the same Caddy-served volume. The admin sits behind the same session and CSRF rules as the API and never answers an unauthenticated request.
- **Authorization state is read-only in the admin.** The admin's change forms would otherwise sidestep every audited workflow in this plan: editing the cached membership table grants any role in any guild, editing a route's owning guild does by hand what the remap does with preconditions, confirmation, notification, and an audit row, and editing audience rows, override approval flags, or issue state skips the same guards. The cached membership table, the audit log, the configured guild list, audience rows, and route owning-guild and visibility fields are therefore displayed but not editable, and change only through the actions that own them. The admin's editable surface is the content it exists for: jurisdiction polygons, override rows, closures, info cards, and settings, each behind its own per-object check. Admin writes go to the same audit log as API writes, with the admin as actor.
- **Database.** PostGIS through GeoDjango. Stores users, sessions, routes, route versions, a route audience join table of route and guild, configured guilds with their admin contact address and role mapping, cached guild membership and roles per user, control points, collaborators, segments with attributes, a crossings table for border control nodes, comments, issues, proposals, approvals, notifications, jurisdiction polygons, jurisdiction info cards, the override table,   settings, and an audit log. All user-authored rows use `deleted_at` soft deletes purged after 30 days, including files on the uploads volume owned by purged rows. Each route version stores a frozen copy of the modality weights and jurisdiction settings used, not only a modality id.
- **Worker.** Procrastinate, which is Postgres-backed and has a Django integration, so no broker service is needed; confirm that integration's current state before building. Jobs are idempotent by explicit key such as `push:{route_version_id}:{service}`, retried with exponential backoff up to 5 times, with per-type timeouts (export 2 minutes, push 5 minutes, rebuild 6 hours). The rebuild and the backup are periodic tasks; the rebuild is single-flight. Failed jobs appear on an admin page and alert after the final retry. Nothing slow runs in the request path.
- **Routing engine.** Valhalla, self-hosted, bicycle costing, one process per tile variant.
- **Geocoder.** Photon, self-hosted, for place search in the editor. Photon indexes from a Nominatim database, not from a PBF, so it is populated either from GraphHopper's per-country Photon dump filtered to the coverage bounding box or from a one-off Nominatim import of the clipped extract, documented as the heavier option. It runs with a 3 GB memory limit and a per-user rate limit of 10 requests per second, and is not on the weekly rebuild path.
- **Mail.** Amazon SES, because the recovery paths depend on reaching people the bot cannot. A degraded-guild alert and a re-invite link both have to arrive when the bot is absent from that guild, and Discord is exactly the channel that has failed at that moment. Login asks for `identify` alone and the membership cache deliberately holds no usernames or contact details, so there is no address to harvest and none is harvested: each configured guild carries an admin contact address entered by an instance admin when the guild is configured, stored on the guild row rather than against any user. Without this the one procedure that rescues a kicked bot does not exist.
- **Discord bot.** A small service holding the gateway connection, maintaining the cached membership and role table, answering membership queries for the API, and posting announcements. It is the only component that holds the bot token. A dropped gateway connection is a health check failure, because stale roles are a security problem rather than a cosmetic one.
- **Thumbnail renderer.** A small Node sidecar using `@maplibre/maplibre-gl-native` against the local PMTiles and style, called by the worker over the compose network.
- **Deployment.** Views are synchronous, since the request path is a single routing call plus database queries, and the API runs under gunicorn with a worker count set from the host's cores. The React frontend is built to static assets rather than run as a service, and Django's admin and Ninja assets are collected into the same named volume, which Caddy serves; both are rebuilt on deploy and after a restore. One Docker Compose stack on one AWS host: Caddy for TLS and for serving the built frontend along with the admin and Ninja assets, the API, the worker, the migrate service, PostGIS, Photon, the Discord bot, the thumbnail renderer, outbound mail, and one Valhalla container per active tile variant. `compose.yaml` plus `compose.override.yaml` for local development, all images pinned, all services `restart: unless-stopped`. Secrets are scoped per service rather than handed to every container by a shared `env_file`, which would put the key-encryption key in Photon, Valhalla, and the renderer and contradict the claim that one component alone holds the bot token: the bot token goes only to the bot service, the key-encryption key and the Discord client secret only to API and worker, the database password only to the services that connect, and nothing at all to Photon, Valhalla, the renderer, or Caddy. In production those values are read from SSM at process start; `.env` with a committed `.env.example` is the local-development path.
  No service but Caddy publishes a port. Photon, Valhalla, and the renderer are reachable only through the API, which proxies geocoding behind session authentication at roughly 5 requests per second burst and 60 per minute per user, since Photon has no notion of a user and cannot enforce a per-user limit itself, and a typeahead box does not need more. The bot exposes its membership interface on the internal network behind a shared secret held in its own service environment; it is read-only, and the membership cache is written by the bot alone. The same stack must run locally. Deploys run the migrate one-shot before API and worker start, and every migration must be backwards-compatible with the previous release for one version, so a rollback does not need a down migration and the API can restart without downtime. The frontend bundle is pinned to the API commit its generated TypeScript types were produced from, since a version-skewed pair would typecheck against a schema that is no longer served.
- **Preprocessing pipeline.** Python using osmium, Shapely, and rasterio. It is the core of the product and is built and tested first. It computes per-way derived values and writes them in three places:
  1. Into the PostGIS segment table, keyed by `(osm_way_id, ordinal within way)` plus stored geometry: stress tier, stress time windows, jurisdiction layers, bridge legality split into roadway and sidepath, lane count and width estimate, sinuosity and sharp bends per mile, lit, reviewer penalty, and elevation samples. The pipeline writes to a staging schema; see Operations for the swap.
  2. Into the OSM extract as tags that a project-owned copy of `graph.lua` (configured via `mjolnir.graph_lua_name`) remaps onto Valhalla's existing edge attributes. Valhalla's tile schema is fixed and unknown tags are dropped, so every derived value that must influence routing is expressed through an attribute the bicycle costing already reads. The mapping table is part of the repository and unit tested: stress tier drives `cycleway`, `surface`, `bicycle`, and `lit`; bridge legality sets `bicycle=yes/no` per roadway or sidepath way. `barrier=cycle_barrier`, and bollards carrying a restrictive `maxwidth`, are mapped onto the gate node type, since `gate_cost` and `gate_penalty` apply only at gate nodes while the narrow-gap furniture on trails here is overwhelmingly bollards and cycle barriers, for which Valhalla exposes no cost of its own; the residual is scored at layer 4 from the segment table. `highway` class and `maxspeed` stay canonical and are never rewritten. They are not free attributes: `highway` sets `DirectedEdge::classification()` and `use()`, which decide the hierarchy level an edge lands on, whether shortcuts are built over it, the road-class factor in bicycle costing, hierarchy-limit pruning in bidirectional A*, and whether Odin emits a maneuver at all and with what cue text. Downgrading a high-stress arterial so Beginner avoids it would therefore also penalize it for Mass Ride, which sets `use_roads` at maximum and specifically wants that roadway; demote it out of the arterial hierarchy so long routes stop expanding onto it; and change the maneuver counts that the Fast and Mass Ride invariants are asserted on. One global remap cannot serve `use_roads: 0` and `use_roads: 1` through the same field. The residual stress signal is carried instead by `use_roads` at layer 2 and stress-weighted ranking at layer 4. If a class-level lever ever proves unavoidable it becomes a tile variant, not a change to the shared graph.
  Reviewer penalty downgrades `surface`, bounded so it can never cross the minimum ridable surface threshold of any configured `bicycle_type`. Valhalla hard-excludes an edge whose surface is worse than that threshold, and `avoid_bad_surfaces` does not relax it, so an unbounded downgrade would remove the edge from the graph and return no route rather than a penalized one, which is the opposite of the stated posture that the router degrades rather than fails. A unit test asserts that a maximum reviewer penalty leaves every affected edge traversable under every preset.
  The key is `mjolnir.graph_lua_name`, a direct child of `mjolnir` and not nested under a logging block, verified against the Valhalla source rather than from memory: `valhalla_build_tiles` passes `config.get_child("mjolnir")` into every parse stage, and `PBFGraphParser`'s `get_lua` reads `graph_lua_name` from that subtree. One key covers the ways, relations, nodes, and area-ways stages, since all four receive the same subtree.
  Its failure modes are asymmetric and worth knowing, because only one of them is quiet. A key that is absent or misplaced, for instance nested one level too deep, returns nothing from `get_optional` and Valhalla silently uses its compiled-in script: every derived tag is dropped and routing merely looks a little off. A key that is present but names a file that will not open throws and stops the build, which is the loud case and needs no guard. So the guard is aimed at the quiet one: the build asserts that the parse log contains the `Using LUA script:` line naming the project's own file, and then queries a known edge for a sentinel derived value, which also catches a script that loads but does not do what it is believed to do. The key name is re-checked against the pinned version at upgrade, since this was a historical quirk in older releases and could move again. Jurisdiction is not stored in tiles. The remap is global and shared by every modality; there are no per-preset remaps.
  3. It inserts a node tagged `barrier=border_control` into the node list of every way that crosses a state line, at the intersection point, which Valhalla treats as a border control node. The way is not split and no way id is ever minted or altered by preprocessing, because three mechanisms key on way id and a split would silently break all of them: the segment table key of way id plus ordinal, the `/trace_attributes` stats join on `edge.way_id`, and post-swap anchor reconciliation by way id and nearest geometry. Derived way ids would also drift week to week as the clip polygon or upstream geometry shifted. Valhalla breaks an edge at any node carrying a barrier tag, so the border control node type is created without a split. Synthetic nodes are minted from a reserved negative id range that cannot collide with real OSM node ids, and the range is asserted in the pipeline tests. This makes the existing `country_crossing_cost` and `country_crossing_penalty` request options act as a per-request state crossing penalty with no engine fork. The Lua mapping is verified not to deny bicycle access at those nodes. Each inserted node's OSM id, coordinates, and the two states it separates are recorded in the crossings table, because Valhalla keeps no custom node tags; the application resolves crossing direction from that table.
  The join carries the trace's edge ordinal through, so aggregates are computed per traversal instance rather than per segment row. Without it a route that rides the same way twice, which out-and-back supports and two of the five reference group rides do, attributes both traversals to the same rows and reports stress breakdown, jurisdiction miles, and unpaved share low by a factor of two over those stretches. A fixture asserts that an out-and-back reports twice the one-way distance in its stress breakdown.
- **Segment identity across rebuilds.** Comments, issues, closures, cue overrides, and reviewer penalties store a geometry anchor (snapped point or linestring) plus the segment key at the time of creation. After each swap a reconciliation job re-resolves anchors by way id and nearest geometry, flags unresolved anchors for review, and never silently drops them. Route versions store control points, waypoints, modality snapshot, and resulting geometry, never graph edge ids.
- **Stats source.** Per-edge attributes for a route come from `/trace_attributes` with `shape_match: edge_walk` on the route shape, falling back to `map_snap` when edge walk fails, with the fallback recorded on the stats block. It fails on any shape that does not follow graph edges exactly, which covers every imported route with a freehand run and any route whose shape was produced against a tile set since swapped; freehand runs are skipped rather than traced. The trace goes to the same variant and costing as the route that produced the shape, since tracing a Mass Ride route against the standard variant returns attributes for edges that route could not have used. Valhalla edges split at graph intersections, which do not coincide with pipeline segments, so the join uses `edge.way_id` plus linear overlap of the edge shape against stored segment geometry, apportioning length where an edge spans several segments. Turn and left-turn counts come from the maneuver list. Elevation gain and loss come from `elevation_interval` on `/route` with a hysteresis threshold so DEM noise does not inflate gain.

## Routing model

Valhalla's bicycle costing exposes a fixed set of dials. Every modality behavior is assigned to exactly one of four layers, and the code makes the assignment explicit:

1. **Tile build.** Derived tags remapped through `graph.lua`, border control nodes at state lines, and variant tile sets for behavior costing cannot express. Trail-class ways are defined once as `highway` in cycleway, footway, path, pedestrian, bridleway, or steps regardless of bicycle tag, plus sidepath-only bridge ways, because DC-area trails are tagged inconsistently. Variants: standard; no-trail, with trail-class ways removed, named for what it does rather than for Mass Ride since Group Ride uses it whenever its trail toggle is off; e-bike, with `electric_bicycle=no` ways set to `bicycle=no`. Each is built from the same clipped source extract with its own tag injection rather than from a shared intermediate. Removing trail-class ways outright can disconnect the graph and return no route where the posture elsewhere is to degrade, which is the risk the phase 6 path-avoidance dial exists to retire; until then a no-route result on the no-trail variant reports the disconnection rather than failing blankly. Each variant is its own Valhalla process. Variant behaviors are toggles, not sliders. The mass ride and e-bike variants are mutually exclusive until the phase 6 path-avoidance dial; the UI disables "E-bike rules" while bike paths are disallowed and explains why. If the exclusivity proves limiting, a combined mass ride e-bike variant is an additional tile build and Valhalla process, not a fork, and is preferred over advancing phase 6. A closed-course variant that relaxes `bicycle=no` on parkways and limited-access roadways for permitted events is a recorded follow-up after phase 6, not in scope for first release.
2. **Per-request costing options.** `bicycle_type`, `use_roads`, `use_hills`, `avoid_bad_surfaces`, `use_living_streets`, `maneuver_penalty`, `gate_cost`, `gate_penalty`, `country_crossing_cost`, `country_crossing_penalty`. Request-level parameters: `exclude_polygons` for small closure polygons only, `date_time`, `elevation_interval`. Requests use `date_time.type: 3` (invariant) with the planning time, which keeps bidirectional A* and alternates while still evaluating conditional restrictions; type 2 is used only for an explicit arrive-by request, since type 1 is specified-departure and only type 2 forces the reverse time-dependent algorithm; type 3 is chosen over type 1 because a fixed time lets bidirectional A* evaluate restrictions and therefore keeps `alternates` available.
3. **A small costing fork**, deferred to phase 6 and kept as a patch set against upstream with a documented rebase procedure: apply the existing `use_lit` and `unlit_factor_` in bicycle costing, and add a path-avoidance dial so the mass ride variant becomes unnecessary. Before implementing, check whether the current release already provides either.
4. **App-level search and scoring.** Dragging a waypoint triggers a single-pass preview using the modality's layer 1 and 2 dials. Layer 4 search runs on release or on an explicit "Find alternatives" action, as a worker job with progress for Mass Ride and Mountain Goat, and presents the ranked candidates with their stats blocks so the owner chooses; the chosen candidate is what gets saved. Multi-pass routing and ranking of candidates on turn count, left turns across traffic, uncontrolled crossings of high-stress ways, road width, sinuosity, unpaved share, lit share, stress breakdown, crowded-trail time windows, and jurisdiction crossings. Candidate generation does not rely on Valhalla `alternates` for multi-waypoint routes, since alternates exist only in bidirectional A* and are disabled for more than two locations; candidates come from per-leg two-location alternates requests or from multi-pass requests with perturbed dials. Splitting into independent two-location requests loses the u-turn prohibition that `through` and `break_through` locations carry in a single multi-location request, so each leg would be free to arrive at and leave a shared point in the same direction and a recombined candidate could double back at every waypoint, colliding with Mass Ride's own doubling-back check. So each per-leg request carries the inbound heading from the previous leg, and any recombined candidate that reverses at a shared point is rejected; where cost allows, the recombined candidate is re-issued as a single multi-location request and only survivors are kept. and the perturbed-dial set always includes at least one pass at high `use_roads` so a road-based alternative is present for sinuosity ranking to choose. The left-turn-across-traffic classifier uses `oneway` on the source and target ways, so a left from a one-way onto a one-way is not counted while a left from a two-way is. Traffic circles are keyed on a curated list, not tags alone, since DC circles are tagged inconsistently. The list carries a review date, because it is keyed on geometry rather than tags and geometry changes; the Florida, New York, and 1st NE junction, whose geometry was rebuilt recently and whose tagging changed with it, and Seward Square and Lincoln Park on the Capitol Hill diagonals are on it.

A modality is a named weight vector over these layers, stored as data. Every dial exists on every preset, so "Mass Ride, Night" or "Group Ride, DC only" are savable customs, subject to the variant exclusivity above.

**User-facing controls.** Each control is the kind of control its value actually is, since a slider with no meaningful midpoint teaches people the dial does nothing. Sliders, each labeled as a pair with both ends legible: "Quiet roads to direct roads", "Avoid hills to seek hills", "Direct to few stops", "Paved only to gravel OK", and "Steepest hill I'll accept", in percent. Toggles: "Allow bike paths and trails", "Prefer lit streets", "E-bike rules", and "Room for two riders side by side", which is a yes-or-no property mapping to width scoring rather than a continuum. It is named for the routing effect rather than for the riding behavior, because riding two abreast is regulated differently in the three jurisdictions while this control only scores road width, and the working convention is never to imply a legal statement in UI copy. The home-jurisdiction control is named for the jurisdiction rather than generically, so it reads "Stay in DC", "Stay in Maryland", or "Stay in Virginia" against the route's home jurisdiction, since DC is not a state and a generic label would misname it for a third of the region. It renders as off, low, or high with the default marked off and a plain sentence under it saying that routes cross into Maryland and Virginia freely, since its default is off everywhere and a bare slider would not say so.
  The two hill controls are explained against each other wherever both appear, because two hill dials with no explanation will be confused: the hills dial decides whether the route goes looking for climbs, while the grade cap sets how steep any single pitch may be. The hills dial also changes kind at its midpoint, so it carries a detent at neutral and one line of copy per half. Below neutral it is a costing weight and the preview updates immediately; above neutral it engages the layer 4 climb search, which is a worker job taking seconds, and brings up the distance budget. On Mass Ride the seek half is disabled with the speed-band explanation, the same treatment the grade cap gets, since seeking climbs contradicts both the speed band and the grade cap. Mass Ride does not offer "Allow bike paths and trails" at all: it is fixed off and shown disabled with the reason, because a field of hundreds to thousands does not fit on a path. A shared-use trail here is eight to twelve feet wide, which is two or three riders abreast, so a ride that takes two or more lanes of roadway becomes a column stretching for miles the moment it enters one, blocks the trail for everyone else on it, and loses the marshalled intersection control the modality is built around. This is a capacity fact rather than a preference, which is why it is not a dial. The phase 6 path-avoidance dial replaces the variant switch for every other preset but does not unfix it for Mass Ride; a trail is still available as a start or finish staging area, which is a control point rather than a routed segment. Group Ride ships with the toggle on. Two controls do nothing to the single-pass preview, because they are layer 4 scoring until the costing fork lands: "Prefer lit streets" and "Room for two riders side by side". Time-windowed stress, such as the Beach Drive and Sligo Creek weekend closures, is the same, applied in stats and layer 4 scoring and never reaching the router. All three are marked in the UI as affecting alternatives rather than the preview, rather than appearing to do nothing. A collapsed Advanced panel shows the raw dial mapping and repeats which dials are layer 4 only. Mountain Goat and Bikepacking show hills, surface, distance budget, and "Stay in home state" by default; the remaining dials are in the Advanced panel. The distance budget appears whenever the hills dial is past neutral or the preset's layer 4 scoring uses one, which covers Bikepacking whatever its hills dial reads, since that is where the trade arises.

Presets:

Road admits compacted and better, Hybrid dirt, Cross gravel, Mountain path. Group Ride is Cross rather than Hybrid: the three rural Loudoun references are chosen gravel, and a Hybrid Group Ride could not reproduce them, which would fail the stated invariant that Group Ride reproduces its references in both settings and does not penalize unpaved surface on the rural ones. Trailmaxxing, Bikepacking, and Mountain Goat are Cross or Mountain; Mass Ride, Fast, Beginner, Recovery, and Cargo are Hybrid, since their routes are roadways. A unit test asserts that each preset's configured type admits every surface class present in that preset's reference routes.

**State crossing penalty.** Owner decision, superseding an earlier draft that defaulted this high for Mass Ride: crossing a state line is a routine part of riding here and people do it without noticing, so the router does not avoid it for any modality. The default is off everywhere, where off means the request explicitly sends `country_crossing_cost` and `country_crossing_penalty` as zero, since Valhalla's default cost is 600 seconds and would otherwise apply at every border control node. The dial exists for the organizer who has a specific reason to stay in one jurisdiction and turns it up deliberately; it is not a default posture. The three reference trail routes each cross the District line and would not be reproduced under the old default. Both are capped at 43200 by Valhalla. Adjustable by the "Stay in home state" slider on every preset from day one. An end-to-end assertion checks that every preset, Mass Ride included, sends both options as zero unless the slider has been moved. A penalty would not make a route unroutable in any case, since the cost is additive and capped; the accurate claim is that the reference routes would not be reproduced, which is what the invariant tests. A nonzero crossing cost also adds to the leg's reported duration, so it inflates the ETAs in the stats block. The penalty is symmetric and charges on leaving and on returning.

**Home jurisdiction.** The state of the start control point, or of the first waypoint if no start control point exists, DC, Maryland, or Virginia, overridable per route. Direction of a crossing is resolved from the crossings table.

**The mass ride speed band.** A mass ride runs between 5 and 9 miles per hour, and that is a physical band rather than a preference. Above it a random slowdown propagates backward through a dense field as a shock wave, so the ride surges and stalls. Below it riders drop under the speed at which a bicycle is easy to balance, and the field starts putting feet down. Six is the default rather than the rule: it is what the reference rides plan to and what a deliberately slow front produces, while a ride that actually rolls at eight is inside the band and not a mistake to be corrected. Several constraints elsewhere in this document are consequences of that band rather than independent rules, and they should be implemented as such.
  Distance follows from it. The reference mass rides run 5 to 7.5 miles, which across the band is between about forty minutes and an hour and a half of moving time, so the distance bound is a duration bound wearing different units. The bound itself stays empirical, drawn from the reference routes rather than recomputed from whichever speed the organizer enters. Grade follows from it too: on a steep climb at parade pace riders fall below balance speed and walk, and on a steep descent they must brake continuously to hold the band, which bunches the field. That, rather than fitness, is why the grade cap sits near 6 percent and why descents over it are flagged as sharply as climbs. The cap is set against the bottom of the band, since that is where balance speed binds, so it does not relax when an organizer plans at eight. And the penalties on turns, signals, and stops are the shock-wave problem in another form: every stop a long field makes has to propagate backward and then release, so the cost of a stop scales with the length of the ride behind it.
  Planning speed for Mass Ride therefore defaults to 6 miles per hour, the editor explains the band rather than presenting an arbitrary number, and only a value outside 5 to 9 warns. Inside the band nothing is said, because an organizer entering the pace their own ride actually holds is the case this control exists for; outside it, the warning is about ETAs nobody can ride to.
  Moving time is not the number an organizer needs, though, and the earlier draft reported only that. A mass ride's evening is dominated by intersection holds, regroups, and restarts: six miles is about an hour of moving time and rather more on the street, and the larger figure is what goes on a permit application and what marshals plan around. So every Mass Ride reports estimated elapsed time beside moving time, computed as moving time plus a hold at each signalized intersection of peloton length divided by speed, plus the dwell at each regroup control point. Both durations appear on the marshal cue sheet and in the stats block, and an organizer can enter an observed average from a previous running of the ride, which overrides the computed figure and is labeled as measured rather than estimated.

**Seeking elevation is a dial, not a preset.** For some group rides the climbing is the point, and those rides still want everything else a group ride wants: quiet roads, room to ride two abreast, few winding paths, regroups at the top. Making hill-seeking its own modality forces a false choice between the objective and the posture, so it is a dial instead. The hills slider runs in both directions: toward avoid it lowers `use_hills`, in the middle it is neutral, and toward seek it engages the layer 4 climb search with its distance budget, which is the mechanism Mountain Goat used to own. Any preset can turn it up, so a hill-focused group ride is Group Ride with the slider toward seek, and Mountain Goat survives as the named preset that starts there with everything else permissive.
  Seeking always trades distance, so the distance budget travels with the dial rather than with the preset, and the editor shows the trade directly: how much extra mileage buys how much extra gain. One distinction is worth keeping visible in the stats, since the rural references already climb 74 to 91 feet per mile without anybody asking: gain that the terrain imposes and gain that the rider went looking for are different things, and the summary says which it is by reporting gain against the direct route's gain rather than as a bare number.

**Grade tolerance is a slider, with one exception.** How much climbing a rider will accept is a preference that varies by person and by area, and in hilly country it is not really a choice at all: the Loudoun references reach 19 percent because the terrain offers nothing gentler. So grade tolerance is user-adjustable on every preset, defaulted from the modality and from the reference routes for that setting, and where the terrain forces a route past the setting the router degrades rather than failing, reporting the steep sections the way road exposure is reported rather than returning nothing.
  Mass Ride is the exception, and only partly. Its cap is not a preference but a consequence of the speed band: past roughly 6 percent a climb pushes riders below balance speed and a descent forces the braking that bunches a field. The slider still moves, because an organizer may know something the model does not, but moving it warns and says why rather than silently accepting a number that will not ride.

**Ordering.** Speed first, then facility, then volume, then surface. Stated plainly because two sections argue for parts of it separately and an implementer needs the whole order.

Relaxing surface avoidance needs a quality floor to go with it, or Group Ride will route a rural group onto the worst surface in the county: `tracktype` and `smoothness` carry that distinction, since a maintained gravel road twenty people can ride two abreast and a rutted farm track that sheds half the group share a `surface` value. Conservative defaults apply where either tag is absent, and Group Ride keeps a floor on surface quality however far surface avoidance is relaxed.

**Gravel is a stress choice, not a surface preference.** Rural group rides here favour unpaved roads, and the reason is traffic rather than texture: a gravel road in Loudoun carries almost nothing, so choosing it is choosing low stress. That puts two dials in direct conflict, because surface avoidance pushes away from exactly the roads the rider wants. So for Group Ride outside the built-up area, surface avoidance is relaxed and the stress classifier weights volume above surface quality, which is also the honest reading of the Furth tables: an unpaved lane with no traffic is low stress whatever its surface. This is a property of the setting rather than a separate preset, so Gravel remains available for someone who wants unpaved for its own sake, and Group Ride simply stops fighting the rider in the countryside.
  The rural references also stretch the preset well past what the city ones suggested: 24 to 30 mile loops climbing 74 to 91 feet per mile and reaching 19 percent, against city rides of a few hundred feet total and 13 percent at worst. Group Ride grade tolerance is therefore set from the rural figures, since a cap drawn from city riding would reject half the club's calendar.

**Road exposure.** Trailmaxxing is not a trails-only mode, because the trail network is discontinuous and the connectors between trails are roads. The reference trail routes all contain such sections and their author describes them as unavoidable. So rather than pretend otherwise, a Trailmaxxing route reports its road exposure: total distance not on trail-class ways, broken down by stress tier, with each such section listed by location and length so a rider knows in advance where the trail ends. The same report serves Beginner. Its top-tier summary line is the gap warning, which is a line in this report rather than a separate artifact; the two names in earlier drafts described one thing. A route with unavoidable exposure is a normal result, not a failure.

**Stats block.** Every route returns: distance, elevation gain and loss, grade profile with maximum grade and flagged steep descents, surface breakdown, turn count, left turns across traffic, intersection summary by control type, stress breakdown by distance, unpaved share, lit share, sinuosity, longest stretch without services, which matters on a rural loop, jurisdiction breakdown by distance for each layer, crossing data, the road exposure report by stress tier with its top-tier gap line, and freehand distance. The stats block always carries crossing data; the route summary surfaces it as its own section only when jurisdiction reporting is on and otherwise folds it into the breakdown.

**Darkness is a planning input, not a preference.** The Night preset weights lit streets, but nothing so far computed whether a route is ridden in the dark at all, which is backwards for this region: DC Bike Party rolls after sunset year-round, and in December a 7 pm start is fully dark while the same start in June is not. So from the planning date, the start point, and the pace, the application computes sunset and the end of civil twilight, and reports how much of the route falls after each, by distance and as the mile marker where the light goes. The stats block carries it, the rider and marshal cue sheets print it, and the lit share is reported against the dark portion rather than against the whole route, since lighting on the daylight half is not information. A route that goes dark surfaces the lit share and the unlit sections the way road exposure is surfaced, and suggests the Night preset rather than switching to it. No claim is made about what equipment any jurisdiction requires; that is an info card matter under the not-legal-advice line. Sunset is computed locally from date and latitude with no external service, so it works offline and needs no key.

**Time-dependent behavior.** `date_time` affects conditional access restrictions, time-conditioned turn restrictions, which do matter downtown, and time zones in Valhalla, so bicycle routing does not change by time of day for roads that are always bike-legal. When no planning time is set, requests assume the next Saturday at 9:00 local time, shown in the editor as an assumption the owner can change, so that conditional restrictions are evaluated rather than ignored. Time-dependent stress, such as the lower Beach Drive and Sligo Creek Parkway weekend car closures, is stored on the segment table as a default value plus windowed values and applied in stats and layer 4 scoring using the route's planning time. Valhalla does not read `oneway:conditional`, so the Rock Creek and Potomac Parkway weekday rush-hour reversal is expressed by preprocessing as directional conditional access restrictions (`bicycle:forward:conditional` and `bicycle:backward:conditional`), verified against the parser's supported keys in a unit test, with the supported-key list read from the pinned Valhalla source and checked into the repository so the test compares against something fixed. If those directional keys turn out not to be read, the fallback is named now rather than discovered later: split the carriageway into a directional one-way way pair and put an undirected `bicycle:conditional` on each. Reviewer-confirmed closures with date ranges are injected as `access:conditional` at the next rebuild using month-day time domains, since Valhalla time domains carry no year; the rebuild removes them once the end date has passed. While a closure is active before its first rebuild it is supplied as a small `exclude_polygons` entry. Valhalla caps both the count and the total perimeter of those polygons, and exceeding a cap rejects the whole request rather than degrading it, so a busy week of confirmed closures would silently start failing requests. The service limits are raised to a documented value in config, the application caps the count and total perimeter attached to any one request below that, and when the cap binds it drops the closures furthest from the route corridor and says so in the stats block.

## Jurisdiction model

Jurisdiction is a set of per-segment attributes, not a single value:

- **Police jurisdiction.** DC under MPD; federal units by agency (US Park Police by NPS unit, Capitol Police, Secret Service Uniformed Division for President's Park, military police for installations, MWAA for the airport); Maryland municipality or county; Virginia town, city, or county. Owner decision: US Park Police is the agency that needs flagging, because federal land is where a mass ride's authority question actually changes. Maryland's park police, meaning the county park police forces, are not flagged and sit in the manager layer instead; this overrides a review finding that had placed them in the police layer.
- **Right-of-way owner.** DDOT, NPS, Maryland SHA, VDOT, county, municipality, or park authority.
- **Park or trail manager** where different, such as the Maryland county park agencies, the authority that runs the W&OD, and the Fairfax County Park Authority, all derived from OpenStreetMap operator tags.

All three layers carry info cards and per-server notice levels, not the police layer alone, because the body that issues a permit is frequently not a police agency: the W&OD is NOVA Parks, the Capital Crescent and Sligo Creek are M-NCPPC, the towpath and the Mount Vernon Trail are the Park Service as land manager, and public space in the District is DDOT. Scoping the model to police while calling its purpose permitting would leave out the permit issuer. The ordered crossing list and the count of distinct authorities therefore include an owner or manager wherever it differs from the segment's police authority, and cards are seeded for NOVA Parks, the Montgomery and Prince George's park agencies, the Fairfax County Park Authority, the Park Service as land manager, and DDOT alongside the police agencies.

**Crossing detection rules.** Crossings shorter than a configurable minimum, default 0.1 mile, are collapsed unless a control point lies inside them or the crossing enters or leaves a federal enclave, meaning an NPS unit, an Architect of the Capitol polygon, President's Park, a military installation, or MWAA land, which are never collapsed at any length, since the NPS land at the foot of Memorial Bridge, the Capitol grounds clip at 1st and Louisiana, and the Secret Service edge of President's Park are all short and short is not the same as unimportant when the question is whose permit is needed. The general collapse which handles the Jones Point sliver on the Wilson Bridge path and the circles that straddle the DC line. Ways with `bridge=yes` or `tunnel=yes` and nonzero `layer` over a park polygon inherit the adjacent jurisdiction, defined as the jurisdiction of the connected non-bridge ways at each end; if the two ends differ, the bridge is split at its midpoint. The midpoint heuristic is a fallback rather than the rule for the crossings that matter: the checked-in Potomac and Anacostia crossings fixture carries the expected police authority, right-of-way owner, and manager per bridge alongside the roadway and sidepath legality it already records, the override table is seeded from it, and a listed bridge bypasses the heuristic entirely. Memorial Bridge is one authority end to end, the 14th Street bridges are not, and the Wilson Bridge path is a third case, so a midpoint split gives the wrong answer for each. Segments on Western, Eastern, and Southern Avenues are treated as DC with a boundary flag listing both authorities; this rule is not surfaced in UI copy as a legal statement. The override table handles DDOT arterials through NPS units. Smithsonian grounds under the Office of Protective Services and the Supreme Court grounds carry their own police and are plausible staging areas for a Mall-area ride, so both are in the polygon set where boundaries are available, at notice level note like the other federal enclaves inside DC.

**Per-route settings.** Two separately editable settings, each stored with an "explicitly set" flag. Changing modality recomputes defaults only for settings the user has not explicitly set, and the UI shows which values are defaults and which are choices. Modality sets routing behavior and the defaults for purpose, reporting, and planning speed; it never overrides a value the user set explicitly, with one exception. Switching to Mass Ride clears an explicitly set recreational purpose, because Mass Ride does not offer that value and the route would otherwise hold one its own control cannot display; the owner chooses assembly or special event before saving, and the defaults test asserts that exception alongside the general rule.

- **Ride purpose.** Recreational, First Amendment assembly, or special event, each with a one-line plain-language explanation shown when the control is surfaced: a ride for its own sake; a protest, demonstration, or expressive event; a permitted race, charity ride, or festival.
  Mass Ride is the exception, and recreational is not offered for it. The purpose control for a Mass Ride offers First Amendment assembly or special event and nothing else. It records which the organizer chose and selects which info cards are shown; it makes no statement about what either footing entails, and this document makes none either. Whatever differs by jurisdiction lives in the cards, maintained by the community under the not-legal-advice line they carry.
  The application never characterizes what any law provides or requires. It records which footing the organizer has chosen, shows the info cards for the authorities involved, and leaves the content of those cards to the community that maintains them, under the not-legal-advice line they already carry. It selects which info card copy is shown and appears in the route summary next to the jurisdiction breakdown. The default purpose for Mass Ride is a per-server setting chosen by the server admin. Owner decision: the shipped default is First Amendment assembly. Every other modality defaults to recreational.
- **Jurisdiction reporting.** On or off. Default on when the modality is Mass Ride or the purpose is First Amendment assembly or special event; off for any other modality with recreational purpose. Those are the only two triggers. The trigger is about who needs to think about permits, not about whether crossing a line is risky, and a ride that is not taking the roadway does not need a permit whatever its size.
  Owner decision, rejecting a review finding: rider count is not a trigger and no headcount threshold is added. The finding proposed defaulting reporting on above roughly twenty-five riders, reasoning that a large recreational club ride through a park draws agency attention. That is not how it works here. Permitting attaches to taking over the roadway or to the footing a ride claims, not to how many people show up, and the organizations that have run these rides for over a decade report group rides as a non-issue for jurisdiction. A headcount trigger would surface permit language on ordinary club rides that need no permit, which trains people to dismiss the reporting on the rides that do need it. Rider count stays what it already is: an input to the peloton length estimate and the marshal ETAs on a Mass Ride.

| Modality | Purpose | Reporting default |
|---|---|---|
| Mass Ride | Assembly or special event, the only options offered | On |
| Any other | First Amendment assembly or special event | On |
| Any other | Recreational | Off, at any rider count |

The reason any of this exists is permitting rather than geography. Laws governing a ride, and the body that permits it, differ by jurisdiction, and those differences bite for First Amendment activity and for permitted special events. For a recreational ride they are largely academic however many people come, which is why nothing is surfaced there by default even though the same nuances technically exist and the info cards remain available to anyone who opens them.

**When jurisdiction reporting is on:**

- A state line crossing is reported, not warned about. The crossing itself is unremarkable; what changes at the line is which laws apply and which body issues a permit, and that is the whole of the concern. The report names the jurisdiction entered and links its info card, and it appears when a waypoint or control point is placed outside the home jurisdiction as well as in the summary afterward, so an organizer learns which authorities are now involved while there is still time to act. The crossing report supersedes the per-authority notice for the same crossing.
- Entering a federal enclave or other non-home police jurisdiction produces a notice at a per-authority level set by the server admin in that authority's info card: note or warning. Owner decision: the shipped default for every federal enclave inside DC is note, drawn as a map overlay and counted in the breakdown, because in practice passing through is rarely an issue. Admins may raise Capitol grounds or President's Park to warning for their server.
- A control point placed inside a federal enclave gets a note regardless of the pass-through level, because stopping is where problems arise.
- The route summary lists crossings in order with mile markers, miles per jurisdiction, and the count of distinct authorities. A state line crossing where the police authority is unchanged, such as Memorial Bridge onto the GW Parkway, carries the note "authority unchanged: US Park Police". Crossings can optionally appear in cue sheets as "Entering Montgomery County, MD" lines.

**When it is off:** nothing is surfaced. The boundary overlay and the info cards are still available to anyone who wants them, in every modality, because the nuances exist for recreational rides too and an organizer may want to read up regardless.

**Info cards.** Each authority has a community-maintained card: contact, typical lead time, links, notes, and the per-server notice level. Reviewer and above can edit; edits are versioned with author and timestamp and revertable by admins; each card shows "last edited" and the line "community-maintained notes, not legal advice, verify with the agency". The application states facts about jurisdictions and never makes legal claims in code.

## Route model

- **Structure.** A route has a name, description, tags, a modality snapshot, waypoints that shape the path, and control points with a type: start, finish, rest, regroup, marshal post, SAG or medical, sweep, bail-out. Control points are distinct from waypoints. A route has an owning guild, chosen by the owner at creation from the configured guilds the bot confirms they are in, defaulting to their only one, and an audience, a set of guilds that always includes the owning guild. Reviewers and server visibility, the routes index, and the Needs review queue resolve against the audience, so a ride co-organized by several clubs is reviewed by all of them. Per-server settings, the default purpose, and the per-authority notice levels come from the owning guild alone so they are never ambiguous. A single-guild deployment sees no difference. A route has an optional planning date and time, a planning speed defaulted from the modality, 6 miles per hour for a mass ride and riding pace for a group ride, for the reasons set out under the mass ride speed band, and an optional expected rider count. The planning date and time set `date_time` on routing requests, drive time-window scoring, and compute cue ETAs; the rider count feeds only the peloton length estimate, the front and rear marshal ETAs, and the self-crossing check. This is not an event.
- **Who can see this.** The tiers below are more state than a volunteer ride leader will hold in their head, so they are never presented as raw state. One panel shows plain-word labels, "Only me and collaborators", "Club reviewers", "My clubs", "Anyone with the link", and "Public", and renders the current combination as one sentence, such as "Anyone with the link can see the map, stats, and rider cue sheet. Reviewers in Club A and Club B can also comment." A preview-as switch renders the route as a member, a link holder, and an anonymous viewer would see it. Downloads are chosen from named presets rather than four checkboxes. The panel is the only place any of this is edited.
- **Visibility.** Private (owner and named collaborators), reviewers (owner, collaborators, and users with the reviewer role), server (all signed-in members of any audience guild), link (anyone with the link, unlisted), or public (listed and readable by anyone). The default tier for new routes is a per-server setting, shipping as private, and a club whose rides are mostly public sets it to reviewers or server so nobody clicks up from private every time. The setting cannot default to link or public: world-readable is a choice a person makes per route, with the confirmation described below, never a state a route arrives in. The tiers are cumulative: each admits everyone the tier below it admits. Link adds anyone holding the token, unauthenticated or not, to the audience-guild readers that server admits, and the read-only map, stats, and rider cue sheet with no comments describe what an unauthenticated viewer gets rather than a property of the tier, since a member of an audience guild opening the same link keeps the comments their standing already gave them, and public adds anyone at all; neither removes member access. Listing in the members' routes index and the Needs review queue follows audience-guild membership at every tier from reviewers upward, so a route shared outward is still found by its own reviewers; unlisted and listed describe only the public index and crawlers. Unpermitted rides commonly keep the route secret until ride day, so nothing about a route is broadcast without an explicit owner action. Link visibility exists because committees routinely need one outside person, an agency liaison or a club officer who is not on the Discord, to see a route; it renders a read-only interactive map, stats, and the rider cue sheet, with no comments, and downloads chosen by the owner from the rider cue sheet PDF (default on), the overview map PDF, and the intersection list PDF (default off, marshal assignment columns omitted), with the GPX track available at public only and also default off. Everything served to an unauthenticated link viewer comes from data stored per version: geometry, stats, compiled cues, and PDFs rendered by the worker when the version is saved; unauthenticated requests never trigger routing, geocoding, thumbnail rendering, or export jobs. Whether link visibility requires login is a server setting `link_requires_login`, editable on the admin settings page; when true the tier is labeled "members with link" and admits members of any audience guild and the unauthenticated surface reduces to the generic OpenGraph card. Owner decision: the shipped default is false. Both modes are covered by the visibility tests. Visibility governs who can open a route in every state; draft additionally excludes the route from the index, the queue, and Discord posting, so a draft at link visibility is reachable only through its link.
- **Public visibility.** Public is link visibility made discoverable and commentable. The route appears in a public index, is served to anyone without login, and is the only tier crawlers may index; every other tier stays `noindex`. Public routes get a stable slug URL alongside the token URL. The owner chooses downloads from the same list as link, extended with the GPX track, default off, since a published community ride wants riders to take the route with them but publishing is not by itself a decision to hand out the track. Operational detail is keyed to the viewer's resolved standing, never to the route's tier. The tiers are cumulative, so a tier-based rule reads backwards: it would suppress marshal data on a private route and serve it on a public one. Marshal post, SAG or medical, sweep, and bail-out control points, the marshal cue sheet, the marshal assignment columns, and any cue anchored to a suppressed point are served only to a viewer holding server standing or above on that route, meaning the owner, a named collaborator, a reviewer, a member of an audience guild, a guild admin, or an instance admin. Token holders, guests, and anonymous viewers never receive them at any tier, including on the owner's own public route. A page that plots where your people will be tells that to everyone, including agencies you have not spoken to. The intersection list is off by default at public and link, and its marshal assignment columns are omitted when an owner turns it on. Cue overrides anchored to a suppressed control point are omitted from the rider cue sheet for any viewer below server standing, since a cue reading "regroup at top" discloses exactly what hiding the regroup point was meant to protect. Reading stays unauthenticated and pre-rendered on the same terms as link: no routing, geocoding, rendering, or export jobs on an anonymous request. Writing requires a Discord login. A signed-in user who belongs to no audience guild has guest standing on a public route: they can comment and open issues, and nothing else. A server setting `public_tier_enabled`, default on, controls whether owners may choose public at all; turning it off stops new publication, de-lists existing public routes, and reverts them to link with their share tokens force-regenerated, which is what makes the lever mean something: reverting to link without regenerating would leave a previously crawled, slug-addressed route readable by anyone holding its old token, which is effectively everyone. The regeneration is part of the audit row. Even so the lever does not retract what is already out, since search-engine caches and social-card fetches hold the content, so a full lockdown pairs it with `link_requires_login`. Whether guests may write at all is a server setting `public_guest_comments`, default on, and an owner can turn it off for one route; with it off, public routes are read-only to non-members and the comment box explains why. Guest content is rate-limited more tightly than member content, is marked as from outside the organizing guilds wherever it appears, and cannot be confirmed into routing penalties by its author, since confirming remains a reviewer action. Choosing public asks the owner to confirm once, because an unpermitted ride's route is exactly what this tier publishes. Setting public on a draft is allowed and behaves as link until the route leaves draft, since draft already withholds a route from every listing. Lowering a route out of public takes effect on the next request, since every read checks current visibility: the slug stops resolving, the route leaves the public index, anonymous reads of its stored PDFs, GPX, and thumbnail are refused, and `noindex` is re-applied. Changing visibility in either direction is audited. Lowering visibility does not reach third-party caches: Discord, Slack, and the social platforms fetch and cache an OpenGraph image on first paste and keep serving it after the origin refuses anonymous reads, which matters directly here because the share card is designed to travel and the threat model includes unpermitted rides. Both the downgrade path and the share panel say so plainly. The confirmation dialog states that publication cannot be undone for copies already made, and names what becomes public: the map, stats, cues, the ride purpose, and the jurisdiction crossing list.
- **Attribution.** Routes are attributed by default, because designing a good one is work and people should get credit for it. The route page, the index, exports, cue sheets, share cards, and announcements name the author and the contributors who shaped it.
  Ride purpose is the exception. When a route's purpose is First Amendment assembly, authorship is suppressed by default on everything that leaves the organizing guilds: the link and public tiers, OpenGraph metadata and thumbnails, every exported file, the social share card, and announcements. Inside the owning guild attribution stays visible, since the committee already knows who drew what and needs to. Club attribution is a separate toggle, also defaulting off for this purpose, because an organization may well want to claim a ride the individual does not. An owner can re-enable either, per route.
  Suppression is a presentation rule, never a deletion. The audit log always records the real actor, approvals stay attached to the reviewer who gave them, and the owning guild's admins see both; the protection runs outward, not against the deployment itself. In files it means the GPX author element is omitted and the creator is the application rather than a person, while the OpenStreetMap copyright element is always preserved, because attribution to the map is required regardless.
- **Named collaborators.** Added and removed by the owner or an admin, and notified when added. A collaborator can view the route in any state, comment, open issues, and submit proposals against it. A named collaborator may be any signed-in Discord account, identified by user id or username, whether or not they belong to a configured guild. This is the path for a partner club that will not invite the bot, and it needs nothing from that club's admins. An owner-granted per-collaborator `edit` flag, recorded in the audit log, allows saving new versions, because committees often have two people drafting one route. A second per-collaborator `review` flag, also audited, lets that person record approve or request changes on that route alone, since approvals are the artifact a co-organized committee actually wants and a partner reviewer should not need a bot invite to give one. Adding a partner guild to the audience is the right choice for an ongoing partnership; a single co-organized ride is not worth it. Merge, reject, state changes, and Discord posting remain owner only. A viewer-role member added as a collaborator gains those abilities on that route only.
- **Share links.** A per-route 128-bit random token, revocable and regenerable by the owner. Unauthenticated OpenGraph metadata (name, distance, elevation) and the static PNG thumbnail are served for link and public visibility, since Discord fetches OpenGraph data whenever a link is pasted and for a secret route the thumbnail is the secret. At private, reviewers, and server visibility, unauthenticated requests receive a generic card with the name only and no route data, and the thumbnail is served only to logged-in users the visibility admits. Thumbnails are rendered by the worker when a version is saved on a route at link or public visibility or in review or published, cached per version. Share pages send `Referrer-Policy: same-origin`, and `X-Robots-Tag: noindex` on every tier except public; Caddy and API access logs redact the token segment of share-link paths.
- **Versions.** Every save creates a version with a history view. Published and in-review routes are never re-routed automatically; the owner may still save new versions. Geometry and compiled cues are stored per version, and re-routing happens only on an explicit owner action. Active closures and weekly rebuilds produce alerts on affected routes, never silent re-routes. The rebuild emits a drift report listing routes whose segments changed attributes or lost their edges.
- **States.** Draft, in review, published, archived. A draft at reviewers visibility is openable by reviewers but accepts comments and proposals only from named collaborators. Requesting review pins a version and requires visibility of at least reviewers; if the route is private, the request dialog prompts the owner to raise visibility first. Archived is read-only and hidden from lists; it accepts no new comments or proposals, existing threads stay readable, and share links still resolve subject to visibility.
- **Proposals.** A proposal replaces the sub-range between two points shared with the base version and is merged by splicing, which matches how committees actually work: "take your detour around Thomas Circle, keep the rest". A whole-route proposal is the degenerate case. Proposals carry `base_version_id` and a state: open, merged, rejected, withdrawn, or superseded, where superseded means the proposer pushed a rebased proposal against a newer base, closing the earlier one and linking to the replacement. A proposer can push new versions to an open proposal until it closes. Merging creates a new head version whose provenance records the proposal and author. If the base has advanced past the proposal's base, the compare view shows base, current head, and proposal, and the owner either asks the proposer to rebase or splices manually. A rejected proposal is retained and readable and can be reopened as a new proposal via fork.
- **Approvals.** Reviewers, and named collaborators holding the `review` flag, record approve or request changes against the pinned version. Approvals are advisory by default: a per-guild `approvals_required` setting, default zero, states how many a route should carry before publishing, and the summary shows the count against it rather than the state machine blocking on it. Request changes is a standing state that the summary surfaces until its author withdraws it or approves, so an objection cannot be lost by scrolling. Reviewers in the audience guilds are notified when review is requested and when the owner re-pins, and an approver is notified when the version they approved is superseded or when a merge lands on a route already published, since otherwise a reviewer learns of work only by returning to the queue. The owner can re-pin the current version from the review panel; existing approvals remain attached to the version they were recorded on, and the summary shows "approved on version N, current version M" and whether the current version differs from the last approved one.
- **Loop generation.** Recorded as a follow-up rather than left unstated, because it is how most of the reference rides were actually planned: all three rural loops start and finish at a parking lot and the weekly city ride is a target distance from a Metro station, so today an organizer hand-places waypoints until the mileage comes out right. A start point plus a target distance plus a modality yielding ranked candidate loops would reuse the layer 4 candidate machinery, the distance budget, and the beam search that Mountain Goat already needs. It is out of scope for first release and scheduled after it.
- **The anonymous surface.** Enumerated rather than implied, because issues are attached to map geometry and not to routes and would otherwise leak across the tier. An anonymous viewer of a public route sees its geometry, stats, compiled cues, the permitted downloads, and the public feedback thread. Of the issues touching that geometry they see title and category only: no description, no reporter identity, and no reporting-route context, which is served only to viewers holding server standing on the reporting route. A visibility test asserts that an anonymous request to a public route never returns the name or id of a non-public route.
- **Serving artifacts.** Every per-version artifact, the PDFs, the GPX, FIT and TCX files, the thumbnails, and the share cards, is served by the API, which resolves visibility per request and then hands off to Caddy by internal redirect; the uploads volume has no public route in the Caddyfile. Object paths carry a random per-version id rather than a sequential one. Responses below public carry `Cache-Control: private, no-store`, and at public a short max-age, because a downgrade cannot reach a CDN, a corporate proxy, or a browser that already holds the file, which is the same limit the share-card caching note records.
- **Ride day.** There is no native app and no offline mode, which is a scope call rather than an oversight, so the intended path is stated: a marshal carries the printed per-marshal card and, where they want the line on a screen, a GPX loaded into whatever app they already use. Nothing on the day depends on the site being reachable from a corner with no signal.
- **Published version.** Versions are pinned for review but riders need the same thing, because once marshal sheets and cue cards are printed a new save would silently change what the share link and the public page show while twenty marshals hold paper from the previous version. The share link and the public page resolve a published version pointer the owner advances explicitly. The owner sees "showing version N, current is M" with one action to publish, and every printed document carries its version number and save timestamp so a marshal in the field can tell whether their paper is current.
- **Forking.** Any contributor or above can fork a route they can see, subject to the source's own limits, since without them a link holder could fork a secret unpermitted route into a copy its owner cannot reach. A fork inherits the source's visibility tier as a ceiling that the forker may lower but not raise, inherits assembly purpose and attribution suppression, records provenance to the exact source version, and notifies the source owner. Forking a route below server visibility is audited.
- **Editor.** Draggable waypoints, insert and delete waypoints mid-route, snapped and freehand segments, reverse, close loop, out-and-back, split the route into two routes at a point, undo and redo, place search via Photon, nearest Metro, MARC or VRE station and nearest Capital Bikeshare dock surfaced when placing a bail-out point, since where someone can quit is a question every organizer fields, an elevation profile with hover synced to the map, cue override editing, control point placement and typing, the modality picker with the slider set and the collapsed Advanced panel, an explicit re-route action, since re-routing happens only on an owner action, "Find alternatives" with the ranked candidate picker showing each candidate's stats block, accepting or dismissing the regroup points Group Ride suggests, name, description, and tags, the GPX import entry point, overlay toggles for stress, boundaries, and crash history, visibility and collaborator management through the "Who can see this" panel, planning time, speed, and rider count inputs, delete route, and the share link. Ride purpose and the jurisdiction reporting controls join it in phase 3.
- **Closures.** A closure is an issue with a date range and a polygon or segment set. Confirmed closures feed the router as described in Routing model and produce alerts on routes that cross them. The closures table is seeded from a checked-in list of known long-term closures in the coverage area, verified at build time.

## Collaboration and peer review

**What "server" means.** The word is overloaded in this document and the settings it names sit at two different scopes, so they are listed rather than inferred. At **guild scope**, set by that guild's admin and applying only to routes whose owning guild it is: the role mapping, the admin contact address, the default ride purpose, the default modality, announcement channels, the guild's own review and approval settings including `approvals_required`, and whether that guild's owners may choose the link and public tiers. At **deployment scope**, set by an instance admin and applying to every guild at once: `public_tier_enabled`, `public_guest_comments`, the ban list, guest rate limits, the configured guild list, override approval, and the jurisdiction and info card tables. Where both exist the narrower one can only restrict: a guild may switch its own public tier off while the deployment leaves it on, never the reverse. "Server visibility" as a route tier is a third thing again and means the audience guilds, not either settings scope; the tier is named server for the members it admits. Every setting in the implementation carries its scope in its name, so `public_tier_enabled` is deployment-scoped and a guild's equivalent is a distinct field.

**Permissions.** Admin is scoped to a guild. A guild admin may, within their guild, delete or moderate routes whose owning guild is theirs, hide content on them, edit that guild's own settings and its role mapping through the dedicated audited mapping action, revert info cards, and suspend a user's access to that guild's routes. Instance admin is a deployment-level role that belongs to no club, which is the point once several clubs share a deployment: someone has to hold the powers that cross guilds, and no single club's admin should. It is the only role that may ban a Discord id deployment-wide, disable guest writing server-wide, approve override table rows (which change routing for every guild), and delete any route. Without this split, one guild's admin could moderate every other guild's routes. Every instance-admin action is audited.

Three properties make the role workable across clubs. It is **managed in the application**, not in a file: the environment holds one bootstrap Discord id for a new deployment, and that value grants standing only while the instance-admin list is empty. The first successful admin action writes the bootstrap id into the list and permanently disables the environment path, audited, after which anyone holding `.env` read access holds nothing. Instance admins are then added and removed in the admin, audited, with the last one impossible to remove so a deployment cannot lock itself out. Removing an instance admin other than yourself notifies every remaining instance admin and the removed party and takes effect after a delay, configurable and defaulting to an hour, during which any instance admin can cancel it; without that, one admin could remove every peer down to themselves in a single audited but unstoppable action. It is **independent of every guild**, deriving from the instance-admin list alone and never from guild membership, role mapping, the bot, or the membership cache, so the people who can fix a broken bot can still sign in when every guild is degraded; the only hard dependency is Discord's own login, and if that is down nobody signs in, which is the accepted cost of a single identity provider. It is **visible to the clubs it holds power over**: the current instance admins are listed to every guild admin, and a cross-club action, meaning a deployment-wide ban, a route deletion outside the actor's own guild, an override approval, or a server-wide setting change, notifies the affected guilds' admins with the audit row, the same way a guild remap already does. Holding instance admin does not confer guild admin anywhere; an instance admin who also runs a club holds that separately. In the table below, the Admin column is the guild admin; instance-admin actions are listed separately.

Role permissions:

Instance-admin actions, not available to guild admins: approve override table rows, delete any route in the deployment, ban a Discord id deployment-wide, disable guest writing server-wide, edit the configured guild list, issue a guild re-invite link, remap a configured guild id, and reclassify a guild loss.

Guest standing is a floor, not an alternative role: on a public route with `public_guest_comments` on, any signed-in user who does not already hold comment rights through an audience guild may comment and open issues. A viewer-role member of an audience guild gets the same floor, so a member a club deliberately held at viewer is never worse off than a stranger. Roles above contributor are unaffected. Guest standing grants nothing else: no forking, proposing, approving, or confirming, and no access to any route beyond public routes and any link route whose token the person holds.

Owner-scoped actions, available to the route owner and to admins of the owning guild: edit the route and save versions (also collaborators with the `edit` flag), change state, re-pin, merge or reject proposals, add or remove collaborators, add or remove audience guilds (only guilds the owner belongs to, recorded in the audit log), transfer ownership to a named collaborator who is a member of the owning guild (recorded in the audit log), set visibility, choose link and public downloads, regenerate the share link, post to Discord. Ownership transfers only to a collaborator who belongs to the owning guild, so the new owner can always manage the audience and is governed by settings from a guild they are in. To hand a route to a partner club, the owning guild's admins first reassign the owning guild to another audience guild, which is audited and notifies both guilds' admins. Adding an audience guild is a sharing action and the main way a secret route leaks, so the audience is shown on the route summary next to the visibility tier. Admins of the owning guild moderate the route; an admin of any other audience guild can remove their own guild from the audience, which is their only lever over someone else's route. Removing a guild revokes its members' access but retains their comments, issues, and approvals, which display as from a guild no longer in the audience and stop counting toward the approval total.

Comments, issues, and proposals are open on in-review and published routes. Draft routes accept comments and proposals only from named collaborators. Confirming an issue records reviewer id and timestamp in the audit log.

**Comments.** Belong to a route, record the version they were made on, and carry a map anchor (point, or way id plus offset, with geometry). On a later version, a comment is shown at its anchor if the segment is still on the route and listed as "from an earlier version" otherwise. Comments are never deleted by geometry changes. A splice merge carries control points by geometry anchor: those inside the replaced range that still lie on the merged route carry over, and those that do not are listed as dropped in the merge dialog, which shows that list beside the stats diff. Control points are what a mass ride committee cares most about, so they are never dropped silently. Comments on a proposal form the proposal thread; a merged proposal's thread is linked from the resulting version's history, and a rejected proposal's thread stays readable. Comments and issue descriptions are capped at 5,000 characters. Comments carry no @mentions, which is a scope decision rather than an oversight: a mention worth having would notify through Discord, and Discord DMs are out of scope, so an in-app-only mention would be a notification people do not see. The Needs review queue and the in-app notifications carry the same load. Guest comments on a public route form a separate public feedback thread, excluded from the Needs review queue's open-comment counts, because they are mostly rider logistics rather than route review. An owner or reviewer can promote one into a review comment or an issue. A comment thread carries a resolved flag, set by the route owner or the thread's author, since the Needs review queue counts open comments and without the flag every thread is open forever. A resolved thread shows who resolved it and when, stays readable, reopens on a new reply, and leaves the open count.

**Issues.** Attached to map segments or polygons, not to a route. Categories: safety, surface, closure, navigation, other. Lifecycle: open, confirmed, resolved, won't fix. Any route whose geometry touches an open or confirmed issue shows it. The reporting route is recorded as context but shown only to viewers that route's own visibility admits, and renders as "reported from a route you cannot see" to everyone else; an issue opened from a route below server visibility carries no route reference at all. Without that rule a member filing a safety issue from a secret unpermitted route would publish its existence onto every other club's routes, which is the hazard the guest `reported` gate was built for and which members can trigger just as easily. An issue opened by a guest starts in a `reported` state, visible only on the route where it was opened and to reviewers of that route's owning guild; a reviewer accepting it makes it an ordinary open issue on the shared map, and declining closes it with no map-wide effect. Without this step a stranger's report would surface on every other club's routes, private ones included, before any member had read it. Confirmed safety and surface issues feed the reviewer penalty tag at the next rebuild, which is a cross-guild effect produced by a guild-scoped role, so it is bounded rather than left implicit. A single guild's confirmation applies a capped penalty; it never sets access, never crosses the minimum ridable surface threshold, and never removes an edge. Raising a penalty past that cap, or applying one to a way outside the confirming guild's own routes, requires a second confirmation from a different guild or an instance admin, on the same footing as the override table. Info card bodies are global for the same reason: a reviewer in any guild may edit one, but reverting a shared card is an instance-admin action rather than a guild admin's, since a guild admin reverting shared text changes what every other club sees. A card is stored as a shared body plus per-guild notice levels, so a guild sets how loudly its own routes report an authority without touching anyone else's copy. Crash history informs that confirmation but never bypasses it, so the path from a crash record to a routing penalty always runs through a person.

**Discovery.** A routes index with list and map views filtered by state, modality, owner, distance range, start-area bounding box, and name text, showing only routes the viewer's visibility admits. A "My routes" view. A public index of public routes, reachable without login and the only listing crawlers see. A "Needs review" queue with two tabs. Routes lists in-review routes and open proposals sortable by age with counts of open comments and issues. Issues lists issues scoped to the viewer's guilds, filtered by reported, open, or confirmed, with the crash-history overlay link the safety-issue rule promises; without it the guest `reported` state has no reader and a stranger's report dies unseen. Both show the routes of every guild the viewer belongs to, with a per-guild filter. If several organizations repeatedly co-plan, an admin may define a named coalition, a saved set of guilds an owner can add to the audience in one action; this is convenience over the audience list and is not required for first release.

**Notifications.** In-app notification list. Events: proposal submitted (owner), proposal merged or rejected (proposer), comment or reply on a thread (owner and participants), guest activity on a public route (owner, as a daily digest rather than one notification per comment), issue confirmed or resolved (reporter), approve or request changes recorded (owner), review requested or version re-pinned (reviewers in the audience guilds), an approved version superseded or a merge landing on a published route (its approvers), collaborator saved a new version (owner), added as collaborator (collaborator), ownership transferred (new owner), route crosses a newly confirmed closure (owner and collaborators with the edit flag), drift report affects a route (owner and collaborators with the edit flag). Discord DMs are out of scope.

**Discord channel posting.** An explicit per-route action by the owner, never automatic, honoring visibility. The bot posts to the configured channel of whichever audience guilds the owner selects, defaulting to the owning guild's. A channel is validated when it is set and the bot's permission to post there is re-checked before each post, since a bot can sit in a guild without being able to speak in that channel; a failed post surfaces to the owner with the reason instead of failing silently. Posts set `allowed_mentions` to none, truncate user text to 500 characters, and are rate-limited to one message per route per 10 minutes.

**Moderation and abuse limits.** GPX uploads: max 20 MB, max 100,000 track points, capped at Caddy as well as in Django, parsed with `defusedxml`, rejected if not well-formed GPX 1.0 or 1.1. Parsing and map matching run as a worker job with a progress endpoint, never in the request path, since a hundred-thousand-point trace through the matching pipeline is not a request-path workload. Per-user rate limits enforced in the API: routing 60 per minute, import 10 per hour, export 30 per hour, comments and issues 30 per hour, and for guests on public routes 5 per hour with a total cap per route per day. A Discord account younger than a configurable age cannot post as a guest. Guild admins can hide guest content on their guild's routes and suspend a user's access to them; instance admins can ban a Discord id deployment-wide and disable guest writing server-wide. Every such action is audited. All user-authored text, comments, issue descriptions, cue overrides, and info card bodies alike, is stored and rendered as plain text: no HTML and no Markdown is interpreted anywhere, at any visibility. Autolinking is restricted to http and https, rendered with `rel="nofollow noopener external"` behind an interstitial, because an info card link is written by any reviewer and displayed to every guild, which makes it a stored phishing vector aimed at the whole deployment. Production settings carry a Content-Security-Policy of `default-src 'self'` with no inline script and `frame-ancestors 'none'`, asserted in CI alongside the existing cookie and host assertions. Every per-user and per-guest limit is counted in a PostgreSQL fixed-window table rather than in process memory, since gunicorn runs a worker per core and in-memory counters would multiply every stated limit by the worker count; at this scale a Postgres-backed store is adequate and avoids adding Redis to the stack. Unauthenticated paths, including the public index, OpenGraph, thumbnails, the read-only view, stats, cue sheet, and downloads, are limited in the application on the same store to 60 requests per minute per client address, with file downloads limited to 10 per minute. Caddy's standard distribution has no rate limiting, so it provides connection limits and request size caps only; if an edge limit is wanted later it takes a pinned custom image built in CI, which is a decision to record rather than assume.
  Every per-address control depends on trusting the forwarded header, so that boundary is pinned: Caddy overwrites rather than appends to it at the edge, Django resolves the client address from the rightmost untrusted entry with the Caddy container as the only trusted proxy, and a test asserts that a spoofed header does not change the observed address. Without it a client sets its own header and defeats the unauthenticated, guest, and abuse limits together. Mountain Goat and multi-pass searches cap candidates at a configured number. An `audit_log` table records actor, action, target, and before and after. It is append-only at the application layer, with no update or delete path in any admin or API surface. Rows carrying before-and-after payloads of user text grow without bound, so rows older than a configurable retention period, default two years, are archived to S3 under the same encryption as the dumps rather than kept online forever. A Django history package covers before and after on model rows, but about half of what must be audited is not a model change with a request user behind it: bans, revoke-now, loss reclassification, re-invite issuance, redemption and expiry, remap counts, grace-window lapses, and anything a worker does, which has no request and so no actor unless one is threaded in. Those are written explicitly to the same table with the actor passed in, and audit rows outlive the soft-delete purge. Covered events include issue lifecycle changes, closure confirmation, info card edits, override approvals, proposal merge and reject, approvals, collaborator changes, audience changes, ownership transfers, hide actions, role-mapping changes, and bans.

**Review is asynchronous.** Live collaborative editing is out of scope.

## Import and export

- **Import.** GPX tracks and routes. Tracks are downsampled or chunked to stay inside Valhalla's `trace.max_shape` and `trace.max_distance` limits, or the limits are raised in config. Run `trace_attributes` first to classify points as matched, interpolated, or unmatched; split at unmatched runs; `trace_route` each matched run; unmatched runs become freehand segments flagged in the UI. GPX routes with at most 25 route points (configurable, well inside Valhalla's default bicycle `max_locations` of 50) are routed through `/route` with each point as a `through` location, falling back to the track path if a point snaps to a `bicycle=no` way and the request fails; denser routes, which is how Ride with GPS, Komoot, and Garmin export them, are treated as tracks and map-matched. Imported waypoints are kept as generic cue overrides at their position along the route, or as control points when their name matches start, finish, or rest patterns, and the user can promote or discard them. The turn model emits an "Enter unmapped section, continue N mi" cue at the start of a freehand run and a normal cue at re-entry; freehand distance counts toward mile markers.
- **Compiled artifact.** Every export starts from one compiled route: Valhalla directions plus a per-route cue override layer where the owner can add a cue at a location, edit cue text, suppress a cue, or merge adjacent cues, so cues like "CAUTION rail tracks, cross at right angle", "single file on bridge", and "regroup at top" are first class. Overrides are anchored by a snapped geometry point, not by index or distance; distance-along is recomputed at compile time, so reverse, split, and out-and-back preserve them, and the compiler reports overrides whose anchor no longer lies on the route. Cue types: left, right, slight and sharp variants, straight, u-turn, roundabout exit with exit number and cross street, summit, valley, water, food, danger, generic, and jurisdiction. Each format has a documented mapping from these types. Bear-versus-turn thresholds are tuned against the reference routes because the L'Enfant diagonals produce acute intersections.
- **Formats.** GPX 1.1 track with waypoints for cues and attribution in `metadata/copyright`; FIT course with course points pinned to the nearest record; TCX; rider cue sheet as HTML and PDF; handlebar-format narrow cue sheet; marshal cue sheet with control points, regroup holds, and ETAs; intersection list as CSV and PDF; printable overview map PDF with numbered turns; and an agency packet PDF, offered where jurisdiction reporting is on and so in practice for a Mass Ride or a ride on assembly or special-event footing, rather than on every route, since a recreational ride has no agency to send one to. It is the shape an agency actually asks for and no earlier draft produced it, assembling the overview map, a street-by-street narrative of the course with entry and exit times per jurisdiction, start and finish points and times, expected rider count and estimated field length, and an organizer contact field. Everything in it already exists in the model. It follows the same viewer-standing rule as the other marshal material, with marshal posts suppressed exactly as the intersection list suppresses them. The marshal cue sheet and the marshal assignment columns are served only to viewers holding server standing or above on the route; see Public visibility. The intersection list covers every intersection with cross traffic, with mile marker, control type distinguishing signal, all-way stop, route stops, cross traffic stops, uncontrolled, and circle entry from OSM stop and direction tags, marked "unknown, verify" where tags are missing, turn direction, and, for Mass Ride, a computed hold duration of rear ETA minus front ETA and an arrive-by time of front ETA minus a configurable buffer defaulting to fifteen minutes, which is what a corker actually works from and what no earlier draft produced; alleys and driveways are excluded by default with a toggle. Marshal assignment is a stored field on the intersection row carrying a name and a contact rather than a blank column, so a twenty-corner ride is not managed on a printout and retyped into a group chat, and a per-marshal one-page card exports that marshal's corner, arrive-by time, expected front and rear times, hold duration, release condition, and a location map. The blank-column printout stays as the fallback. Both the assignment field and the per-marshal card follow the same viewer-standing rule as the rest of the marshal material. For Mass Ride, the marshal cue sheet and intersection list print front and rear ETAs computed from planning speed and the peloton length estimate. Exports accept a max-cue budget per device profile and drop lowest-priority cues first, since older head units truncate beyond roughly 200 course points; the budget applies to GPX waypoints as well as FIT and TCX course points, but for a different reason on each. Course points exist only in FIT and TCX. Garmin warns that waypoints in a third-party course file may not be preserved, and Garmin Connect does not turn GPX waypoints into course points, so GPX cue delivery is best-effort and per-device and is verified per profile rather than assumed. Because the cue override layer is the distinctive feature and would otherwise reach no head unit in the first release, FIT export ships alongside GPX in phase 2, with TCX beside it; only direct push stays deferred. A danger-type cue is generated automatically wherever the route crosses `railway=rail`, `tram`, or `light_rail` at a shallow angle, configurable and defaulting to under thirty degrees from the direction of travel, marked as auto-generated and overridable, and those crossings are added to the intersection list. The H Street streetcar rails, the CSX crossings in Ivy City and Hyattsville, and the Purple Line construction crossings drop riders every month and the geometry is already in OSM, so leaving it to an owner remembering to type a cue is leaving it to chance. Owner-added cues and danger-type cues are never dropped; where protected cues alone exceed a profile's budget the export warns and offers a split rather than silently truncating, since devices discard the excess without saying so. Per-profile point-count and file-size budgets sit beside the cue budget, because Garmin Connect downsamples large imports and TCX inflates badly, and one reference fixture already carries over seven thousand track points; simplification runs at a fixed tolerance asserted never to move the line off the way. The profile table lives in the repository with a last-verified date, defaulting to 200 course points, which is current Edge behavior rather than a property of older units.
  The canonical cue model and its per-format mapping are published in the spec, because the formats are not equally expressive and pretending otherwise produced a test that could never pass. The canonical set covers left and right at slight, normal, and sharp, u-turn, fork and keep left, right, or straight, merge, ramp or exit, roundabout with exit number, ferry, arrive, and the non-maneuver classes danger, control point, and jurisdiction crossing. Fork and keep are first-class because the Capital Crescent, W&OD, and Mount Vernon trails are full of junctions where a "keep left" rendered as "left" sends riders the wrong way, and FIT has `left_fork`, `right_fork`, and `middle_fork` for exactly this. Continue maneuvers and unnamed-junction straights are suppressed unless a danger or control point is attached. TCX collapses hardest: its course point type is a closed list of sixteen values with no slight, sharp, u-turn, fork, or roundabout, its point name is capped at ten characters and the course name at fifteen, and both time and position are required on every course point. So TCX maps slight and sharp onto Left and Right, u-turn and roundabout and fork and jurisdiction onto Generic, carries an abbreviation in the name field and the full cue text in `CoursePoint/Notes`. The mapping table names every collapse for every format. FIT files are written with fit-tool under BSD-3. The Garmin FIT Python SDK is rejected on license grounds rather than capability: the FIT Protocol License forbids making the licensed technology available to third parties, declares it confidential, and forbids distributing it such that any part becomes subject to a license requiring source disclosure, none of which survives publishing the source under MIT and shipping pinned images others run. The course message set Garmin requires is written out in the spec, since a course missing any of it will not load: a `file_id` of type course, a `course` message, a `lap` message carrying totals, the records, the course points, and start and stop events.
- **Social share card.** A rendered image of the route sized for social platforms, produced by the worker through the same headless renderer as thumbnails and cached per version, per style, and per size. Sizes: square at 1080 by 1080, portrait at 1080 by 1350, story at 1080 by 1920, and landscape at 1200 by 630, which shares its path with the OpenGraph thumbnail. A share panel on the route page previews the card, toggles its blocks, picks the size and a light or dark theme, and downloads or copies the result.
  Blocks are individually toggleable: the route line, name, distance, elevation gain, an elevation profile strip, the modality, the planning date, the owning club, and a QR code. The elevation profile and the QR code are both off by default, so a card is a picture unless someone asks for more. The profile is drawn from the same per-version samples as the stats block, so the card and the page can never disagree. Attribution for OpenStreetMap and the basemap is drawn into the image itself and stays legible at the rendered size, because an image posted to a social platform is a produced work that travels without the page's attribution.
  The card discloses no more than the public and link tiers do: start, finish, and rest control points only, never marshal posts, medical, sweep, or bail-out points, and no cue override anchored to a suppressed point. A start-only announcement style draws the start point, date, time, and distance with no route line, for the common case of announcing a meeting point without publishing the course. Generating a full-route card for a route below link visibility warns, in the same words as publishing, that the image discloses the route wherever it is posted and cannot be recalled. When the QR is turned on it encodes the share link, and only at link or public visibility, since a token rendered into a public image is the link; below those tiers the toggle is unavailable and says why.
- **Clean exports.** Attribution and incidental metadata are different problems and get different rules. A byline is a deliberate credit governed by the attribution rule above. Incidental metadata is everything a file picks up from the tools that touched it: author elements, athlete and account identifiers, device names and serial numbers, software creator strings, and recording timestamps. None of that is ever chosen by anyone, and it leaks identity into files that circulate, so no export carries any of it at any visibility or ride purpose.
  Every exported file is built from the compiled route rather than passed through from an import, which is what makes this reliable. An imported file's metadata is read for what the application needs, the route name and any waypoints worth promoting to control points, and then discarded; it is never retained for re-emission. A route imported from a member's Strava account therefore cannot carry that member's athlete identifier into the marshal documents a committee hands out. The same applies within a format's own conventions: a FIT course omits device serial and user profile fields, a GPX omits the author element and names the application as creator, and a cue sheet PDF omits document author and producer fields.
  What an export does carry is fixed and short: the OpenStreetMap copyright, which is required; the route name; the application as creator; and a byline only where attribution is on. Exports are reproducible, which makes caching honest and lets a test assert cleanliness against a known-good file, but the guarantee is scoped to what can actually carry it and the rules that make it true are stated rather than assumed. GPX, FIT, TCX, and CSV are byte-identical across runs: every timestamp is derived from the route version's stored timestamp and never from the clock, coordinates and elevations are written at fixed precision, XML attribute order is canonical with no whitespace variance, nothing carries a UUID, and the application and library versions are part of the cache key so a dependency bump produces a new artifact instead of a failing test. PDFs are reproducible only through a writer configured for determinism, with fixed creation and modification dates, a content-derived document id, and stable font subset prefixes; where that cannot be arranged the comparison normalizes those fields first. The social card is rendered through a GPU path whose output is not byte-stable across drivers or library versions, so for it the assertion is content equality rather than byte equality.
- **Delivery tiers.** Download with per-device instructions is the path for every route and every device, full stop, rather than a stage before something better. Manual upload to a hub the device syncs from is documented alongside it, per service: Garmin Connect, which is the largest destination by device population and accepts GPX, TCX, and FIT; Wahoo; Hammerhead; Ride with GPS; and Strava, where creating a route from an uploaded file is a paid-subscription feature and the instructions say so. There is no third tier: direct push is shelved, and the file already goes everywhere.
- **Integrations, recorded as findings rather than as a plan**, since push is shelved; every item below would need re-verification before any of it was built. Push targets investigated: Wahoo (Cloud API, `POST /v1/routes` with a FIT file, `routes_write` scope, sandbox then production review; pushes set `external_id` to the route id and `provider_updated_at` to the version timestamp so re-pushes update in place) and Hammerhead (Developer Platform public API, self-serve developer account and API license, supports webhooks). Garmin's Connect Developer Program has paused new partner applications; the Courses API is implemented only if the program reopens and is not scheduled. Ride with GPS's supported v1 API does not create routes, and Strava's API is read and export only for routes, so Ride with GPS, Strava, Komoot, and COROS are manual-upload hubs with per-service instructions. COROS and Komoot partner APIs are not attainable for a community app.
- **Connected accounts.** Per-user OAuth tokens per service, encrypted in the application layer as described in Operations. Each account records provider, provider user id, scopes, expiry, last refresh, and status: ok, reconnect required, revoked. Refresh is serialized per account with a row lock; a failed refresh sets reconnect required and stops pushes rather than retrying forever. A provider deauthorization webhook or a 401 on refresh sets status revoked and stops pushes. Each push records the provider route id and the version pushed, so a new version updates the remote route rather than duplicating it; archiving a route does not delete it remotely. Disconnect calls the provider revoke endpoint where one exists. Push logs are visible to the user and retained 90 days.

## Auth and community

- **Discord login, bot authorization.** Login uses Discord OAuth with the `identify` scope alone, which is a light consent prompt that asks for nothing but the account identity. The user's access token is used once to read that identity and is then discarded: no Discord token is stored, refreshed, or encrypted, so authorization never depends on a user token staying valid. Membership and roles are answered instead by a bot that sits in each configured guild and queries them with the bot token, server-side, at any time.
- **The bot.** One application bot with Public Bot enabled. Disabling it would gate Discord's authorize endpoint on the application owner's identity, so a guild admin holding Manage Server could not complete an install however good their link, which breaks both the re-invite path below and the remap precondition that the bot already be present in the new guild. Admission control is the configured guild list, not the Public Bot flag: a guild the bot is in but that is not configured is inert and auto-left, so an uninvited install grants nothing. The bot token is an instance-wide secret held like the other secrets in Operations. It needs the server members privileged intent, a portal toggle that is granted automatically below the scale at which Discord reviews it; verify the current threshold before launch, and treat crossing it as a launch-blocking item for the project owner. If the intent is denied or later revoked, the bot falls back to a per-user member lookup over REST on login and on each sweep, with the sweep interval shortened to an hour, so revocation lands within an hour instead of seconds. That sweep runs against an explicit request budget, because an hourly per-user lookup across several clubs' thousands of cached users would exhaust Discord's global and per-route limits; it prioritizes users with active sessions and recent activity, and the rule when the budget runs out is fail closed. A cached row the degraded sweep could not confirm within the maximum staleness bound grants no standing, and the shortfall is alerted to instance admins. the admin page records the degraded mode and instance admins are alerted. Alerting to instance admins never travels through the bot, since every alert that matters most is about the bot being unable to talk to Discord. It goes by Amazon SES to the addresses on file, from the web process rather than the worker, and a suppressed or bounced address is itself an alert on the admin page. A guild invites the bot when it wants its own roster, roles, index, and review queue in the deployment; reviewing one route needs only a named collaborator or a link, so a partner club is never blocked on a volunteer admin who reads Discord weekly and would balk at granting an intent that reads their whole roster. The bot also posts route and review announcements to configured channels, replacing the webhook, so posts carry the application's identity and can be edited later.
- **First run.** A new deployment starts with no guilds, no routes, and one bootstrap admin, and nothing so far said what that person sees. The admin's first screen is the onboarding checklist rather than an empty dashboard: verify the bot is online and its intent granted, add the first guild id, map its roles, set the deployment defaults, confirm the mail sender, and run the reference-route smoke check. Each item links to the page that satisfies it and reports done or not rather than being ticked by hand. A new guild admin gets the shorter version: invite the bot, map the roles, choose the guild's default purpose and notice levels, name an admin contact. A new member signing in for the first time lands on their own empty routes list with one action on it, which is to create a route or import a GPX, and the modality picker explains each preset in a sentence rather than assuming the vocabulary. None of this is a tutorial or a product tour; it is the difference between a first session that reaches a saved route and one that stalls on an empty page.
- **Guild lifecycle.** A guild joins in two steps: an instance admin adds the guild id to the configured list and sets its initial role mapping, then a guild admin invites the bot. Thereafter the mapping is the guild admin's to maintain, since role ids change as a server reorganizes and routing that through the deployment operator would not survive contact with a dozen clubs. It is maintained through one audited action rather than an admin change form: the form is read-only like every other authorization table, and the action revalidates each role id against the live guild, refuses ids the bot cannot see, writes an audit row with the prior mapping, and notifies the guild's other admins. Only an instance admin may map a role to instance admin. A guild the bot is in but that is not configured is inert, ingesting no members, caching nothing, and granting no standing, and the bot leaves it automatically after a configurable period; without this, anyone who could invite a bot would self-onboard their server and push an arbitrary roster into the database. Removing a guild from the configured list purges its cached membership rows. An instance admin can issue a per-guild re-invite link from the admin page, and the degraded and removal alerts sent to a guild's admins carry one; otherwise a guild admin who kicked the bot by accident, which is one right-click in the member list, would be stuck until the application owner answered on a Friday evening. The link is an OAuth install URL pinned to that guild id with guild selection disabled, carrying only the bot and application-commands scopes and the bot's fixed permission integer, wrapped in a single-use token expiring in 24 hours. It is not a login and confers no session, role, or standing, and whoever clicks it must already hold Manage Server in that guild, since Discord and not this application decides who may install a bot; that is what makes email an acceptable channel for it. Redemption, expiry, and revocation are audited and alert instance admins, and issuing a new link invalidates any outstanding one for that guild. Redemption re-admits the bot and nothing else: it does not extend a grace window, reclassify a loss, or restore standing, which resumes only from the backfill once the bot is back in. An instance admin can remap a configured guild id to a new one in a single audited action, so a club that rebuilds its server after a raid, moves off a founder's personal server, or merges two chapters does not orphan its routes; the owner-scoped reassignment cannot cover this, since it needs the old guild's admins to act and both guilds to be in the audience, and the old server may already be gone. Routes, owning-guild and audience references, server settings, and the guild's identity carry across. The role mapping and cached standing do not: role ids are per-guild snowflakes, so the old ones mean nothing in the new guild, and the cases this feature exists for are exactly the cases where the rosters differ, since a server rebuilt after a raid is rebuilt to shed accounts. The remap requires the bot to be present in the new guild with its initial backfill complete, which proves the new guild is real and reachable, and the admin must map the new guild's role ids before it grants any standing. Standing is rebuilt from the new roster, so a member of the old server who was not carried over gets nothing. While the mapping is incomplete the guild is configured but unmapped: routes remain, owners and named collaborators keep read-only access to their own routes for 72 hours, and no role-derived standing is granted. The confirmation names both guild ids, the new guild's name as the bot sees it, and the count of routes, audience rows, and collaborators affected, and the admin retypes the new guild id. Remapping onto a guild id already configured is refused; merging two configured guilds is a remap of one followed by adding the other to the audience. The audit row records actor, both ids, the counts, and the prior role mapping, route owners and both guilds' admins are notified, and an instance admin can reverse a remap within 7 days, restoring the prior ids and mapping but never cached standing. Reversal is an id remap rather than a state rollback: routes created, audience rows added, collaborators named, and settings changed under the new id all carry forward under the restored one. It is refused if the new guild id has itself been remapped since. A guild left unmapped beyond a configurable period, default 30 days, alerts instance admins and offers bulk reassignment or archival of its routes, so the 72-hour unmapped window cannot quietly become permanent inaccessibility.
- **Permission resolution.** A config table `guild_id, role_id, permission` maps Discord roles to application roles. Application permission is the maximum across configured guilds of the mapped roles. A user's permission on a given route is the maximum across only those audience guilds they belong to, so a reviewer in one club does not gain reviewer powers on another club's routes. Membership and role ids are cached in PostGIS per user per guild with the time they were last confirmed. The cache stores the guild id, role ids, timeout expiry, and last-confirmed time keyed by Discord user id, and nothing else: no usernames, avatars, nicknames, or join dates. For a tool whose threat model includes unpermitted rides, who organizes with whom is the sensitive part, so rows for people who have never signed in are purged after 30 days, and the cache is excluded from the nightly dump, rebuilt on restore by the bot's startup backfill and the sweep as set out in the restore runbook. Absence of a row is absence of standing; the cache is never read as unknown-therefore-allow, and the API refuses standing from a row older than the grace period. On start the bot backfills every configured guild before reporting healthy, and a guild whose initial backfill has not finished grants no standing.
- **Re-validation.** The bot holds a gateway connection and updates the cache from member add, update, and remove events, so a role change or a departure takes effect in seconds rather than waiting for a poll. Requests read the cache and never call Discord inline. A six-hourly worker sweep reconciles the cache against the bot's view and repairs anything the gateway missed during a disconnect, and a user's standing is confirmed on login regardless of cache age. Sign-in is open to any Discord account, because the public tier accepts comments from people outside the organizing guilds; membership in a configured guild is what determines standing, not whether a session may exist. A user in at least one configured guild holds the mapped role permission there. A signed-in user in no configured guild holds guest standing only, which grants nothing beyond commenting and opening issues on public routes with `public_guest_comments` on, and a banned Discord id holds no standing at all. Losing all configured-guild membership downgrades a user to guest standing rather than revoking their sessions, and immediately removes access to every private, reviewers, and server route and to any route where their only standing came from that guild. When a user loses their last standing in a route's owning guild, write access ends immediately, but the owning guild's admins are notified at once with a list of that user's routes in review or published and a one-click reassignment, the route's share links, exports, and cue sheets keep working, and the former owner keeps read-only access to routes they own for 72 hours, the window an accidentally degraded guild gets, so a ride three days out is not stranded with its marshal documents unprinted. Three member states are not plain membership and are treated as absent for standing: a member who has not cleared membership screening, shown as pending; a member serving a timeout, cached with its expiry timestamp and treated as restored automatically at that time, since Discord emits an event when a timeout is applied but none when it lapses; and any member of a guild the bot can no longer see.
- **When the bot loses a guild.** Accidental loss and deliberate removal are opposite signals and get different windows. Cause is read from Discord's guild-delete signal: an outage flag means accidental, its absence means removal. A guild found missing on reconnect with no such event is classified deliberate, since Discord marks outage guilds unavailable rather than omitting them; an instance admin can reclassify it as accidental from the admin page, audited, which restores the longer window, but only while the deliberate window is still open. Once standing has lapsed the remedy is re-inviting the bot and rebuilding from the backfill; reclassification never restores an individual role removal, timeout, or ban already processed. Accidental loss, meaning a gateway failure, a revoked intent, or a Discord outage, marks the guild degraded and honors cached standing for a grace period, default 72 hours running from the alert rather than the disconnection, granting nothing new or elevated during it. Deliberate removal of the bot from a guild ends that guild's standing within 15 minutes, because a guild that ejects the bot has left the deployment and because the slow path would otherwise be a moderation-evasion route: a member with Manage Server who is about to lose their roles could kick the bot and keep cached standing. Either way an instance admin, or an admin of the affected guild, can collapse the window at once with an audited revoke-now action, and role removals and timeouts already delivered by the gateway are never resurrected by a later degraded window.
  The affected guild's own admins are alerted in-app and by email at the same time as instance admins, because they are the only people who can fix it and the bot can no longer reach them in Discord. When a window lapses nothing is deleted: that guild's members lose access, share links and public routes keep resolving, owners keep read-only access to routes they own, and re-inviting the bot restores full standing on the next gateway sync, so a volunteer admin who removed the bot without understanding it loses nothing but access.
- **When the bot itself is down.** The same bound applies at the larger scope. Every configured guild is marked degraded as soon as the gateway has been disconnected for the same five minutes that raises the alert, and its window runs from that mark rather than from the end of a grace period. Marking only after a full grace period would stack two windows and leave the whole deployment carrying stale grants for twice as long as a single lost guild. The maximum stale-grant window is 72 hours from the alert, everywhere, and that is the only number. Authorization reads two things, not one. Each configured guild carries a standing row with a state of active, degraded, or revoked, the instant it entered that state, and the instant its standing expires; each cached membership row carries the time it was last confirmed. Standing is granted only when the guild row is active, or degraded and still inside its window, and the membership row was confirmed within the maximum staleness bound. The row-age check is the fail-closed backstop for a frozen database rather than the whole rule, because a row age alone cannot express a revoke-now, a window that runs from the moment an alert fired, or a deliberate removal that must bite within minutes while rows confirmed ten minutes ago still look fresh. Failing closed at once would let a single mistaken kick lock out an entire club, and failing open indefinitely would leave stale grants standing.
- **Revocation by the user.** Because no user token is retained, revoking the application in Discord's authorized-apps settings does not end a RouteMaker session. Sessions end by logging out, by admin suspension or ban, or by account deletion. The account page says so plainly and offers a sign-out-everywhere action.
- **One resolver, called everywhere.** Standing is decided by a single function taking a user and a route and returning a level, with one permission check built on it. Ban, deletion tombstone, guild state and window, membership row age, pending and timed-out members, the maximum across audience guilds, collaborator edit and review flags, the guest floor, owner, guild admin, and instance admin are all inputs to it in a stated precedence, rather than prose spread across sections that two engineers would order differently. Ban and deletion come first and no per-route grant overrides them; guild state and row age come next; per-route standing last. Every API view, every export path, and every admin queryset calls it rather than reimplementing a check, and the authorization tests exercise the resolver directly as well as through the views.
- **Denial messages.** A refusal names its cause rather than reading as a broken site: not a member of any club on this deployment; membership pending, accept that server's rules in Discord, which catches long-standing members who joined before the gate existed; access paused while a Discord timeout is in effect, with the end time; or that guild is temporarily unavailable. A guild admin viewing a member sees the same reason.
- **Sessions.** Django's server-side sessions, rows in Postgres referenced by an HttpOnly, Secure, SameSite=Lax cookie; 30 days idle, 90 days absolute. State-changing requests require a CSRF token, which Django's middleware supplies. Discord login is a custom authentication backend rather than a third-party social-auth package, because standing comes from the bot and not from the OAuth response.
- **Session revocation.** Django's database session backend has no user column, so nothing in it can enumerate one person's sessions and the only global lever is rotating the secret key, which signs everybody out. A custom session model carries an indexed user id, and the user row carries a session epoch that ban, suspension, deletion, and the sign-out-everywhere action all bump; middleware rejects any session whose stored epoch is stale. The same model carries the 90-day absolute expiry, which Django does not implement natively, alongside the idle expiry it does.
- **Account deletion.** Revokes all sessions immediately through that epoch and deletes the cached guild membership rows, which the hashed-id tombstone then keeps the bot from recreating on the next gateway event or sweep even though the person is still in the guild, assigns authored comments, issues, and proposals to an anonymous sentinel user, and retains only a tombstone of the Discord id for ban enforcement, computed as an HMAC keyed with the key-encryption key rather than a plain hash. A Discord id is a structured 64-bit value whose candidate set any guild's member list resolves directly, so an unkeyed hash of one gives no privacy against anyone holding a dump, which is the reason the membership cache was excluded from dumps in the first place. The key never appears in a dump, and the same keying applies to every other identifier retained after deletion. Owned routes with named collaborators or recorded approvals are transferred to the first collaborator who has the edit flag and belongs to the owning guild; if none exists, the owning guild's admins are notified to reassign within 30 days before purge, because route leads change every season. Owned routes with no collaborators and no approvals at private or reviewers visibility are soft-deleted and purged after 30 days, since no remaining viewer could fork them and an unpermitted ride's route should not outlive its owner; such routes at server, link, or public visibility are archived and remain forkable. Approvals, info card edits, and override rows keep their audit rows. Audit log rows keep the numeric actor id and display "deleted user".

## Operations

- **Secrets and tokens.** With direct push shelved and no Discord token retained, the system holds no per-user token of any kind, which is worth stating as a property rather than leaving as an absence: there is no third-party credential to encrypt, refresh, leak, or revoke on deletion, and a database compromise yields no access to anyone's account anywhere else. Reviving push would reintroduce that whole class, so the machinery is specified here to be built with it rather than retrofitted. Per-user OAuth tokens would be encrypted in the application layer with AES-256-GCM, never in SQL, with each ciphertext row carrying a `key_id` so rotation adds a new id, re-encrypts in a worker job, and retires the old.
  The key-encryption key is not conditional on any of that, since the deletion tombstone is keyed with it. It is stored as an SSM SecureString, which is KMS-backed, and read once at process start; locally it comes from the environment file. It is never written to the database and is not in dumps. Discord client secret, the bot token, the Django secret key, and partner app credentials get the same handling; rotating the Django secret key invalidates every session, which is the intended effect. Production settings are pinned and checked in CI: debug off, explicit allowed hosts and trusted CSRF origins, the proxy SSL header set for Caddy so cookies are marked secure and client IPs are read from the forwarded header rather than Caddy's own, and the session and CSRF cookie flags set to what Sessions states. The bot token is instance-wide and its rotation is a restart of the bot service, not a re-encryption job. S3 access uses the instance IAM role.
- **Backups.** A Procrastinate periodic task runs `pg_dump -Fc` through a sidecar with the matching client version, excluding the session table and the cached membership table, uploads to S3 with SSE-KMS and 30-day retention, verifies the upload with `pg_restore --list`, and writes a success row that the alert reads. A daily EBS snapshot of the data volume, retained 14 days, covers everything with state in it, since it is the volume everything durable binds under: uploaded GPX originals, exported PDFs and thumbnails, the PostGIS directory, and the tiles tree with the cached extracts, the elevation cache, the basemap, and the geocoder index. The root volume is not snapshotted, because it holds only the operating system, the images, and the checked-out code, all of which a rebuild reproduces from the pinned compose file and the repository. Those are nominally rebuildable, but re-deriving them means a manual 3DEP resample and a Nominatim import, which no four-hour recovery target survives, so snapshotting them is the cheap way to make the runbook true. The `.env` file, the key-encryption key, the bot token, and the Django secret key are stored in SSM so a host rebuild can recover everything it needs. Valhalla graphs are rebuildable from the snapshotted extracts and are not themselves backed up. Restore runbook: provision host, pull compose, restore secrets from SSM, `pg_restore` the latest dump, run migrations, collect static assets and rebuild the frontend bundle, restore the data volume from its snapshot, which brings back the tiles tree and its cached extracts, then rebuild Valhalla tiles from them, run the membership sweep to convergence before opening the site because restored membership is as stale as the dump and the gateway replays nothing, rotate the Django secret key and flush every session, and re-apply the ban list before the first request is served, and run the reference-route tests as a smoke check. Target RPO 24 hours, RTO 4 hours with the data volume restored from snapshot. Without that snapshot recovery is a cold rebuild, which exceeds the rebuild job's own six-hour timeout, so the fallback is a degraded open: the site up with routing and geocoding disabled behind a banner while tiles rebuild. The drill is timed against the snapshot path. A restore drill runs before first public release and quarterly.
- **Rebuild and swap.** Valhalla does not reload tiles at runtime. The rebuild writes tiles to a dated directory and packs a tile extract per variant, and writes the new segment table and derived attributes to a staging schema. It starts a second Valhalla container per variant against the new extracts and runs the reference-route tests against them. The segment and derived-attribute tables are unmanaged models, so migrations never create, alter, or touch the staging schema, and the connection's search path is what points the ORM at the live schema. On pass, the swap repoints the Valhalla upstreams per variant first, through a settings table the API watches, reloading its HTTP client without a restart, and renames staging to live second, so the inconsistency window is a live segment table describing the older graph rather than a graph nobody is serving; the reconciliation job tolerates that direction and the window is bounded by the rename. The rename is three steps rather than one, live to live_old then staging to live, inside one transaction with a `lock_timeout` and bounded retry, because `ALTER SCHEMA ... RENAME` takes an access-exclusive lock and would otherwise queue behind any in-flight read and then block every later one. The search path is set with `ALTER ROLE ... SET search_path` rather than per connection, so a recycled persistent connection cannot land on the wrong schema. Because the segment models are unmanaged, `migrate` creates nothing for them, so test and CI databases take their DDL from the pipeline rather than from migrations. The connection pool is flushed immediately after the commit, because persistent connections cache query plans against the renamed relations and would otherwise fail their first post-swap request. No table outside the swapped schema may hold a foreign key into it, so anchors reference segment keys as plain columns rather than as constraints; a cross-schema constraint would make the rename impossible. Rollback renames back and repoints the settings table. The old containers stop last. On fail, drop staging, keep the old tiles, and alert. The previous extracts are retained for rollback. The reconciliation job and drift report run after the swap against the live table. Disk is sized for two full sets of every variant plus build scratch, which phase 1 turns from an assertion into a measured table: a per-item figure against the volume for the PostGIS data directory with its staging copy, the three tile sets doubled at swap, the merged and clipped extracts with the retained previous ones, the elevation cache, the basemap, the geocoder index, uploads, and the per-version PDFs, thumbnails, and cards. The 80 percent disk alert becomes a hard gate: a rebuild that cannot fit two sets refuses to start rather than filling the volume. The rebuild container has memory and CPU limits, the latter because a six-hour build on an eight-core host would otherwise saturate every core and destroy both the preview latency target and the canary health check; it takes half the cores, runs in a low-traffic window, and latency and canary alerts are widened for its duration. The CI compose check fails any service missing either limit. Each variant container states its loki, thor, and odin worker counts, because the layer 4 candidate set is issued concurrently under a per-modality latency bound and a single thor worker would serialize it, while raising the count multiplies the resident tile working set against the container's memory limit. The limit is sized against the measured extract size for that variant, and the CI compose check asserts the worker count against the limit rather than merely asserting that a limit exists.
- **Privacy and retention**, which the plan required in substance and never stated. The application collects Discord user and guild ids, cached role ids, route geometry and its metadata, comment and issue text, and client addresses for the rate limiting and abuse controls. Client addresses are the ones nothing had a rule for: they are retained for 30 days in the rate-limit store and the request logs and then dropped, they are never joined to a route or shown in any UI, and the abuse controls keep a decision rather than the address behind it. Request logs rotate on the same 30 days; audit rows keep the actor and the action, never the address. A privacy notice states this plainly, in the same register as the rest of the site, and names the one thing that actually matters to the people using it: a route's geometry, its purpose, and who commented on it are the sensitive assets here, not the account identifiers, because for a ride on assembly footing the map is the disclosure. It restates the visibility model as the control the person actually holds, points at account deletion and what survives it, and says that the operator can read what is in the database, since a notice that implies otherwise would be false. The notice and the sign-in terms are versioned in the repository and a material change is announced rather than silently swapped.
- **Observability.** JSON logs to stdout with a request id propagated to worker jobs, Docker log rotation. Prometheus-style `/metrics` on API and worker: request latency, routing latency, queue depth, job failures. It binds to the internal network only and Caddy never routes it, since queue depth and latency are operational detail and a path-labeled Django metric would carry share-link tokens into the metric store; path labels are normalized so a token can never become a label value, matching the log redaction rule. `/healthz` returns a bare status with no component detail. A pinned scraper and dashboard are a recorded follow-up; until then structured logs and the alerts below carry the load, and the metrics endpoint exists for a local scrape. Health checks: PostGIS `SELECT 1`, Valhalla a canary route between two fixed DC points per variant, worker a heartbeat row, the bot a live gateway connection with the time of the last event received. External uptime check on `/healthz`. Alerts by email or an ops Discord channel, except that gateway and degraded-guild alerts go by email only, since the component being reported on is the one that would otherwise carry the message. Alert on: the bot's gateway disconnected for 5 minutes or any guild marked degraded, worker heartbeat silent for 10 minutes (independent of the backup alert, so a stalled worker is caught before the backup window), backup not succeeded in 26 hours, rebuild failed or not completed in 8 days, disk over 80 percent, canary route failing.
- **Host sizing and hardening.** Initial host: 8 vCPU, 32 GB RAM. Storage is split, which shapes both the sizing and the backups: a small root volume carries the operating system, the Docker images, and the checked-out code in its own directory, and a separate larger data volume, 200 GB gp3 and growable, carries everything with state in it. Every Compose volume binds under that mount, so nothing durable lives on root and the code directory holds no data. The measured size table from phase 1 is drawn against the data volume alone, the 80 percent alert and the hard rebuild gate apply to it per volume rather than to the host in aggregate, and the root volume gets its own alert, since a root filled by Docker images stops the stack just as effectively. Growing the data volume is an online resize and is the first response to the gate firing; the two-full-sets headroom is what the gate protects. Compose memory limits: each Valhalla 2 GB, Photon 3 GB, PostGIS 4 GB, rebuild 8 GB, renderer 1 GB, bot 512 MB, API 2 GB, worker 2 GB, Caddy 256 MB, migrate 256 MB; the rebuild container exits before the validation containers start, so the build and the duplicate Valhalla processes are never resident together, which is what keeps the peak inside the host; the sum including swap-time duplicate Valhalla containers must stay under host RAM, verified in CI by a script that reads the compose limits and fails on any service that has none. Security group allows 443 and 80 only, SSH via SSM Session Manager, unattended security updates, named volumes, all under the data mount, for PostGIS data, Caddy data for certificate persistence, tiles, and uploads.
- **Legal text.** ODbL and Protomaps attribution as in Region and data. A liability disclaimer that routes reflect map data and community reports, that jurisdiction information is community-maintained and not legal advice, and that riders are responsible for their own safety.

## Phases

0. **Before phase 1.** Request an ODbL waiver from the State of Maryland for the iMAP layers, in the pattern the OpenStreetMap Foundation uses with state agencies. It is a short request, it is routinely granted, and it removes the only conditional source in the pipeline; granted, the Maryland layer merges normally and the collective-database arrangement is deleted rather than maintained. This is the project owner's to send, and it gates nothing else, so phase 1 proceeds in parallel under the conditional arrangement.

1. **Foundation.** Preprocessing pipeline with stress classifier, jurisdiction tagger, sinuosity, border control node insertion and crossings table, Lua remap and its tests, segment table with staging swap; standard, no-trail, and e-bike tile variants built from the same clipped source extract with per-variant tag injection; elevation tiles; PostGIS schema with jurisdiction polygons and override table; Procrastinate worker; weekly rebuild with validated swap; Photon; thumbnail renderer; Docker Compose with migrate service; the admin for the configured guild list, the role mapping, and jurisdiction, override, and closure editing, with object-level querysets and the map widget, establishing the pattern every later admin surface follows, and the two admin-scoping assertions from the visibility tests; the rest of the admin, meaning moderation, override approval, audit browsing, and degraded-guild views, arrives with its features in phase 4; Discord login with the identify scope, the bot with gateway-driven membership and role caching, sessions, and the degraded-guild grace period; the map with self-hosted PMTiles and the stress overlay.
2. **Routing and editing**, split in two because as one block it is the product rather than a phase and offers no point at which a real organizer could try the thing. *2a*: the editor with waypoints and control points, Default, Group Ride, and Mass Ride, GPX import with map matching, GPX, FIT, and TCX export, the stats block, and private and server visibility. *2b*: the remaining presets, the cue sheets and intersection list, the link and public tiers with their leak tests, share links, and both indexes. Import is the half of these integrations a read-only API already permits, and it is not blocked by the partner approvals that shelved push: Strava's route endpoints are read and export only, which is exactly enough to pull an organizer's back catalogue in. It is shelved alongside push rather than separately, since the file import path covers the same need, but it is recorded as the first thing to revive if any of this is revisited, because it needs no partner's permission. Two facts would have to be re-verified against live documentation before anything here was built, both having been checked through secondary sources: whether Ride with GPS creates a route from a multipart file upload, which if true would move it from the manual tier to the push tier and bring with it the absence of any update-in-place endpoint, so every re-push would leave a duplicate rather than replacing the previous route; and whether Hammerhead route push is genuinely self-serve rather than partner-gated, which decides whether it is buildable at all. Wahoo's route creation takes the file as a base64 data URI rather than a conventional multipart field, which shapes the push job's memory profile and is recorded for that reason.

**Direct push is shelved**, which is an owner decision and not a deferral with a date on it. The file is the delivery answer: GPX and FIT cover every device in this audience, they ship in phase 2, and anyone who owns a head unit can import one. Push would save a step rather than extend reach.
  Shelving it rather than scheduling it follows from what is actually available. Garmin is the largest device population and its developer program is paused with no reopening date, so the most valuable target cannot be built at all. COROS and Komoot partner APIs are out of reach for a community application. That leaves Wahoo confirmed, Hammerhead unconfirmed as to whether route push is self-serve or partner-gated, and Ride with GPS unconfirmed as to whether it creates routes by file upload and, if it does, offering no way to update one in place, so every re-push would leave a duplicate. A phase built on one confirmed service and two unknowns is not worth carrying as a plan.
  Two things are recorded rather than discarded, because shelving is not the same as deciding against. Import by connection is the half most worth reviving first: Strava and Ride with GPS both expose route reads, a read-only API needs no partner approval, and pulling an organizer's back catalogue in would unlock something the file path does not. And if Garmin's program reopens, the Courses API is the one push target that would change the calculation on its own.

Events with dates, pacing, and RSVPs are out of scope.

## Quality bar

- **Unit tests** for the stress classifier, the conflation step, the jurisdiction tagger and crossing rules, the border control node insertion and crossings table, the directional conditional access remap for the parkway reversal, the Lua remap producing the intended Valhalla attributes for each stress tier, the turn model and left-turn classifier, and the cue type mappings per format.
- **Reference routes** live in `fixtures/reference-routes/` with a README recording their measured properties. Fifteen real routes are supplied across four sets, all anonymized before commit, and the README carries the measured table for each. Coverage outside the District is better than a first reading suggests, and the gap that remains is narrower and differently shaped. All three trail routes run well into Maryland, one of them from the District to Annapolis and BWI across 76 miles, so the Maryland stress layer and the manager-layer permitting are exercised. All three rural group rides are in Loudoun County, so the VDOT volume conflation is exercised. Trailmaxxing and Group Ride therefore each have references on both sides of the District line and the reproduction threshold applies to both in full.
  Mass Ride is the exception, and it is not a gap the owner can close. All four mass rides are in the District, because that is where the owner has organized: a mass ride outside DC runs under a different permitting posture, and the pace, field size, and marshalling practice that shape a route there are things the organizers who run them know and this project does not. So the Mass Ride preset is tuned on District geometry and says so. Its reproduction invariant applies to its District references, since those are real routes and the preset must still reproduce them. What is not claimed is that its defaults transfer: an owner planning a mass ride outside the District sees that the preset was tuned on DC rides and that the jurisdiction cards, not the preset, carry what is different. Reference routes from mass ride organizers in Maryland and Virginia are a standing request, and adopting them is an owner decision taken with those organizers rather than inferred from the routes alone. Four DC Bike Party mass rides are the ground truth for the Mass Ride preset. They bound it in ways the preset had left open: 5 to 7.5 miles, 63 to 164 feet of gain with brief pitches near 6 percent, 2.3 to 4.7 turns per mile, entirely within the District, point-to-point from a fixed start with a near-loop as the occasional case, and no route revisiting its own line. Three real trail routes are also supplied, of 15, 32, and 76 miles, and they bound Trailmaxxing quite differently: 701 to 2333 feet of gain, pitches to 12 percent, and a crossing of the District line on every one. Two design decisions rest on them. Grade tolerance is per-modality rather than global, since one cap would either reject these or be useless for mass rides. And the state-crossing penalty is rightly off by default for every modality including Mass Ride, because all three of these would fail to be reproduced with it on and because crossing a line is reported rather than avoided. Turn density, at 2.3 to 2.9 per mile, is the one measure that does not separate the two sets, so turn count alone never distinguishes a trail route from a road one. Five group rides complete the set. They are rides of roughly twenty at riding pace, which is why they sit between the other two presets: 12 to 35 miles, 347 to 985 feet of gain, pitches to 13 percent, all inside the District in these city examples. Three rural Loudoun rides cover the other setting: 24 to 30 mile loops climbing 74 to 91 feet per mile and reaching 19 percent, which is where Group Ride's grade tolerance comes from since a cap drawn from city riding would reject half a club's calendar. Turn density separates no preset, but it does separate setting: the same club's rural rides run 1.0 to 1.1 turns per mile against 2.4 to 3.3 in the city. The cause is the road network rather than the riding, since a rural route has far fewer roads to turn onto, which makes the measure a property of where a route is more than of what it is. Two consequences follow. Nothing in the application may infer a modality from it. And a turn penalty does correspondingly less work in a sparse network than in a grid, so any comparison of turn counts between routes must normalize by local road density or compare only routes in the same setting.
  One of them corrects a classification that looks obvious and is wrong. Three of the five are named Critical Mass, and by rider count their classification would be arguable, but under the roadway-takeover definition they are group rides. The definition does work the name cannot, so nothing in the application infers a modality from a route's title or headcount. For each, routing a derived waypoint set with its intended modality must reproduce the reference geometry within a buffer. The waypoint set has to be defined, because the fixtures arrive as tracks and carry no waypoints apart from December's `Midpoint`, so routing start to finish and expecting 80 percent overlap with a hand-drawn parade route or a 76 mile trail route would measure nothing. It is the route's control points plus N vias sampled at even spacing from the matched shape, with N recorded per fixture in the README, and the threshold is stated as a function of N so the test measures the router rather than the sampling, measured in both directions so neither a shortcut nor a detour passes: at least 80 percent of the generated route's length lies within 25 metres of the reference polyline, and at least 80 percent of the reference lies within 25 metres of the generated route. The fixtures README defines gain, turns, and revisits operationally, with a 3 metre hysteresis on gain, which is also the hysteresis the application uses, a 40 degree bearing change over 5 metres for a turn, and 25 metres apart while more than 400 metres separated along the route for a revisit; those definitions are normative and every invariant below uses them. Turn count has two definitions in play and they are not interchangeable: the geometric one above, and Valhalla's maneuver count from the stats source, which suppresses maneuvers where the road name continues and splits others. Each invariant names which it uses and computes both sides the same way; the reference-route bounds use the geometric definition, and the Fast-against-Default comparison uses maneuver counts on both sides. Fixture gain comes from Strava's elevation values while the application's comes from 3DEP, so the absolute gain bounds carry a systematic offset and are written with headroom rather than to the measured figures exactly. Per-modality invariants asserted on every reference route: Mass Ride includes zero trail-class distance, stays between 4 and 9 miles, keeps gain under 250 feet, carries at most 0.1 mile above the 6.5 percent grade cap and nothing above 8 percent, a cap set from the measured 6.2 and 6.3 percent pitches rather than below them, averages under 6 turns per mile, which the measured 2.4 to 4.7 leaves real headroom against, and revisits no location, each bound drawn from the reference routes with headroom; Group Ride includes zero distance on ways traversed at dismount speed and a trail-class share at most the reference route's own; Beginner includes zero top-tier stress distance, or where the router degraded to a penalty the stats block carries a gap warning and the flagged distance equals the top-tier distance; Recovery gain is at most Default gain; Mountain Goat gain is at least Default gain; a Group Ride with the hills slider toward seek gains more than the same Group Ride with it neutral while keeping its own surface, width, and turn behavior; Fast turn count is at most Default turn count; Trailmaxxing reproduces the trail routes within the same geometry threshold, reports road exposure greater than zero on each, and is not penalized for crossing the District line; Group Ride reproduces its reference routes in both settings, tolerates grades to 19 percent, is never rejected for revisiting its own line, and on the rural references does not penalize unpaved surface.

## Working conventions

- **Every phase ends with a review panel.** Owner instruction. When a phase's deliverables are complete, dispatch a panel of independent reviewers across the disciplines that phase touched, and revise until every one of them accepts. A phase is not finished when its code is written and its tests pass; it is finished when the panel accepts it. The panel reviews the code and the tests against this plan, not the plan alone, so a finding is either a defect to fix or a place where the plan was wrong and must be corrected with the reason recorded. Blocking findings are fixed before the phase closes; lesser findings are batched, reconciled where reviewers disagree, and applied before the next phase starts. Reviewer findings carry no authority of their own: one that contradicts an owner decision is rejected on the record rather than quietly adopted, which has already happened more than once.
- Ask before choosing between materially different approaches. Do not ask about routine implementation choices.
- Keep any Valhalla fork as a patch set with a documented rebase procedure.
- Document every external data source with its license, URL, and refresh procedure, and re-verify partner API terms before implementing each integration.
- Partner API registrations are not owner tasks, because push is shelved. Build the download path and the device file formats, which are the delivery answer rather than a stage before one, and do not stub the push adapters or carry a connected-account model against a future that may not come: an unbuilt adapter costs nothing, while a stub has to be kept compiling, migrated, and reasoned about in every authorization change.
- Never present jurisdiction, permit, or access information in the UI as a legal statement.
